# AGENT_TASK_DATASET_BASEMAP — задание: датасет «ортофотоплан ↔ спутниковая подложка»

**Дата:** 2026-08-28 · **Статус:** задание для агента-исполнителя (другая машина,
свой набор геопривязанных ортофотопланов) ·
**Основано на:** отработанной фабрике пар «орто ↔ орто»
(`scripts/orto_2_dataset/`, [DATASET_ORTO_PAIRS_PLAN.md](DATASET_ORTO_PAIRS_PLAN.md),
[AGENT_TASK_DATASET_PAIR.md](AGENT_TASK_DATASET_PAIR.md)), формат пары —
[DATASET_SPEC_FINETUNE.md](DATASET_SPEC_FINETUNE.md) §2.

Задача: собрать пробный обучающий датасет, где **сторона A — вид виртуальной
камеры БПЛА из ортофотоплана**, а **сторона B — кроп спутниковой подложки**
(Esri World Imagery или аналог) на ту же территорию. Это боевой тип пары:
именно так работает целевой тракт локализации.

Документ самодостаточен: в нём и конвейер, и все грабли, на которые мы уже
наступили на парах «орто ↔ орто». Читать целиком до написания кода.

---

## 0. Главное отличие от пар «орто ↔ орто»

| | орто ↔ орто | **орто ↔ подложка** |
|---|---|---|
| Вторая сторона | второй растр той же площадки | тайлы подложки (веб-Меркатор, зум) |
| Привязка | обе стороны в одной сетке, относительная геометрия точна | **разные системы**: ошибка привязки орто складывается с ошибкой ортотрансформации подложки |
| Типичный сдвиг | единицы метров | **5–16 м** (измерено на честных растрах против Esri) |
| Рельеф/здания | одинаково искажены на обеих сторонах, взаимно сокращаются | **не сокращаются**: подложка ортотрансформирована по своему DEM, высокие объекты «завалены» в другую сторону |
| Сезон | задаётся датами двух съёмок | сезон подложки фиксирован её версией; кросс-сезон даёт **сезон ортофотоплана** |
| Доступность | локальные файлы | сеть, лимиты, кэш, версия слоя |

Отсюда три следствия, которые определяют всю конструкцию:

1. **Гейт привязки обязателен.** Ортофотоплан допускается в фабрику только
   после визуальной проверки совмещения с подложкой (шахматка) и измеримого
   сдвига ≤ ~15 м, компенсируемого. Растр с неизвестной/фальшивой CRS —
   не годен вовсе.
2. **Равнинные участки и низкая застройка предпочтительны.** На высокой
   застройке разметка принципиально неточна (параллакс зданий), это шум
   разметки, а не ошибка кода.
3. **Подложку надо паспортизовать**: провайдер, версия/дата слоя, зум,
   условия использования — в мету каждого сэмпла.

## 1. Организация работы

- Отдельный каталог проекта, например `~/projects/ml/orto_basemap_dataset/`,
  внутри: `scripts/` (код + `scripts/tests/`), `tools/` (обслуживание),
  `dataset/`, `aux/` (кэши, поля сдвигов, отчёты), `logs/`, `.venv/`.
  **Ничего не класть и не запускать из домашнего каталога** — он общий и
  быстро превращается в свалку.
- Свой venv: `numpy scipy rasterio pillow opencv-python-headless pytest`
  (плюс `requests` для тайлов). Если системный Python слишком свежий для
  колёс rasterio — брать интерпретатор conda/miniforge как базу venv.
- Долгие прогоны — только в tmux, через **файл-лаунчер**, а не инлайн-командой.
- Если управляешь хостом из PowerShell по ssh: **инлайн-команды с кавычками
  ломаются** (PowerShell 5.1 срезает внутренние кавычки, а `` `t `` внутри
  строки превращается в табуляцию). Правило: любой нетривиальный код —
  файлом через scp, затем снять CR (`sed -i -e 's/\x0d$//'`), затем запуск.

## 2. Конвенции и ловушки данных (проверены на практике)

1. **Nodata бывает разным**: у одних площадок белый (255), у других чёрный,
   у третьих — **служебные заливки чистым цветом** (красные полосы по краям
   блоков съёмки). Последние коварны: (255, 0, 0) проходит и проверку на
   белое, и на чёрное. Рабочее правило валидности пикселя:

   ```python
   hi, lo = rgb.max(axis=0), rgb.min(axis=0)
   valid = (hi > 5) & (lo < 250) & ((hi.astype(np.int16) - lo) < 200)
   ```

2. **Единицы сетки ≠ метры.** Псевдо-меркаторская сетка растянута в
   `k = 1/cos(широты)` раз. Наземный GSD = `res · cos(lat)`, площади в
   сетке делить на `k²` (на широте 55° это ×3 — ошибка, которую легко не
   заметить: «61 км²» оказались 21 км²).
3. **Пиксель растра не квадратный** в единицах сетки (`res_x ≠ res_y`) —
   оси считать раздельно.
4. **Пиксель = центр**: `(0, 0)` — центр левого верхнего пикселя, главная
   точка кадра `((W−1)/2, (H−1)/2)`.
5. **Обзорная маска завышает покрытие.** Маска, построенная по усреднённому
   чтению (20 м/пикс), замазывает мелкие дыры: до 85% её «рабочей зоны»
   может оказаться пустотой. Кандидатов в узлы и якоря **проверять мелким
   нативным кропом** (256 px), а долю реального покрытия оценивать по
   выборке.
6. **Обзорное чтение больших растров — минуты** (11 Гпикс ≈ 5 мин,
   135 Гпикс ≈ час): результат кэшировать на диск, иначе каждый прогон
   платит заново.
7. **Тайлы подложки**: MPP на зуме `z` и широте `lat` —
   `156543.034 · cos(lat) / 2^z`. Зум выбирать так, чтобы MPP был близок к
   GSD стороны A. Тайлы кэшировать на диск (по `z/x/y`), запросы — с
   ретраями и паузами; при массовой выкачке уважать лимиты провайдера.

## 3. Гейт: какие ортофотопланы вообще годятся

Прежде чем строить пары, по каждому растру:

1. **Паспорт**: CRS, `res`, bounds, наземный GSD, широта, дата, сезон,
   доля валидных пикселей, лицензия источника.
2. **Проверка правдоподобия CRS**: перевести центр в широту/долготу и
   убедиться, что это ожидаемый регион. У нас 147 из 159 растров имели
   метку «EPSG:4326» с метровыми координатами — фальшивую; такие растры
   для пар с подложкой непригодны, пока система не разгадана.
3. **Шахматка против подложки**: взять 4 кропа ~300 м в разных частях
   растра, наложить на подложку, посмотреть глазами. Годен, если объекты
   совпадают или совпадают после компенсации сдвига ≤ ~15 м.
4. **Отсечь территории тестового набора** — площадки, из которых
   отрендерены тестовые кадры, в обучение не идут ни в каком виде.

Реестр годных площадок — в отдельном файле (`pairs.py`/`sources.json`) с
полями: пути, даты, сезоны, зум подложки, вердикт гейта.

## 4. Этап Р — поле сдвигов «орто ↔ подложка»

Смысл тот же, что в фабрике орто↔орто: **один раз на площадку** измерить,
как привязка растра смещена относительно подложки, и сохранить поле, из
которого генератор потом берёт компенсацию. Регистрация делается на
native-данных (обе стороны north-up, один масштаб, без перспективы) —
надёжнее и на порядок дешевле, чем замер на каждом сгенерированном кропе.

1. Рабочая зона = валидная площадь растра с эрозией ≥ 200 м от края.
2. Сетка узлов, шаг подбирается под целевое число узлов (~250) с учётом
   **реальной** доли покрытия (оценить по выборке, п. 2.5). Для узкого
   коридора это ~300 м, для широкой площадки — до 1.5 км.
3. В узле: кроп орто ~150 м (1536 native px) и кроп подложки на том же
   bbox, приведённый к тому же разрешению. Обе стороны → градиентные карты
   (Собель, клип по 99-му перцентилю, нормировка, зануление невалидного) →
   окно Ханна → **фазовая корреляция** с субпиксельным уточнением пика
   (парабола по трём точкам).
4. **Контроль остатка**: перечитать кроп подложки со смещением на
   найденный сдвиг и повторить замер — остаток обязан быть < 1 м.
5. **Правило компенсации на узел** (всё сразу, иначе узел пустой):
   `|сдвиг| ≤ 12 м`, `остаток < 1 м`, согласие с медианой соседних валидных
   узлов ≤ 3 м. Для пар с подложкой потолок можно поднять до ~20 м —
   абсолютные сдвиги здесь больше, чем между двумя своими датами.
6. Выход: `shift_field_<площадка>.npz` — узлы (x, y) → (dx, dy), флаг
   валидности, высота пика, плюс глобальная медиана как фолбэк-константа.
   Плюс HTML-отчёт: стрелочная карта поля, гистограммы, счётчики причин
   отбраковки.

**Важно про семантику знака.** Зафиксировать и покрыть тестом: «точка земли
имеет в растре координату g, а в подложке — g + (dx, dy)». Ошибка знака даёт
молча неверную разметку — это самое дорогое место конвейера.

**Ожидания по зимним/сложным сезонам.** На снегу корреляция часто не имеет
опоры: у нас на зимней паре валидными оказались лишь 28% узлов. Это не
повод чинить код — это свойство данных; компенсация тогда берётся из
глобальной константы, и об этом надо честно писать в отчёте.

## 5. Этап Г — генерация пар

Камера стороны A должна повторять **боевую/тестовую**: если целевые кадры
1920×1080 с объективом 16 мм на сенсоре 22.3 мм, то `f_px = 16·W/22.3`
и FOV ≈ 70°. Это принципиально: у нас первая редакция датасета имела
FOV 19° (f_px взяли «на глаз»), и кадр видел вчетверо меньше земли, чем
реальный борт — в кадр не попадали дороги, лесополосы, кромки полей.

Принятые параметры (перенести как есть, если камера та же):

| Параметр | Значение |
|---|---|
| Кадр A | 1024×576, `f_px = 735`, FOV 69.7° |
| Высоты | 250–400 м → GSD_A 0.34–0.54 м/px, **след кадра 348–558 м** |
| yaw | ±25° |
| pitch (наклон) | 0–10°, азимут 0–360° |
| Компоновка `inside` (65%) | след кадра **целиком внутри** кропа B, доля ширины A в B = 0.50–0.85 |
| Компоновка `partial` (35%) | кадр выходит за край B, **перекрытие 0.60–0.90** |
| Масштабы | `GSD_A / GSD_B = 0.85–1.20` (согласованы) |
| Сторона B | квадрат `b_px = 1024·scale/r`, 768–2048 px → 400–900 м земли |

Конвейер одного сэмпла:

1. **Якорь** — центр кропа B на сетке ~150 м по рабочей зоне.
2. **Подтяжка якоря вглубь съёмки**: если в окне размером с кроп B данных
   мало, пробовать смещения на 30 и 60% его размера по восьми направлениям
   и брать положение с наибольшим покрытием; якорь с покрытием < 90%
   отбрасывать. Без этого кропы у кромки съёмки захватывают край
   ортофотоплана — пустоту вместо данных.
3. **План сэмпла**: H, yaw, наклон+азимут, масштаб, `r`, отсюда `b_px` и
   `GSD_B`; для подложки — зум, ближайший к `GSD_B`.
4. **Размещение кадра**: для `inside` — случайная позиция в зоне, ужатой на
   габарит следа кадра; **учесть, что при наклоне след смещён относительно
   центра камеры на `H·tan(наклон)`** (иначе часть кадров вылезает за край —
   у нас этот баг поймал V-тест); для `partial` — двоичный поиск смещения
   под целевое перекрытие.
5. **Рендер A**: луч пикселя (K, R(yaw, наклон), позиция) → пересечение с
   плоскостью z = 0 → координаты сетки → выборка из растра. Окно растра
   читать в разрешении не мельче нужного (не тянуть полный масштаб зря).
6. **Кроп B**: мозаика тайлов подложки на bbox якоря, приведённая к `GSD_B`.
7. **Компенсация**: билинейная интерполяция поля сдвигов в точке якоря;
   вне валидной зоны поля — глобальная константа; нет и её — сэмпл в брак.
8. **Разметка**: `warp_ab` (пиксель A → земля → сетка + компенсация →
   пиксель B, float16, NaN вне маски), `mask_ab` (внутри B ∧ валидность A ∧
   валидность B), `covis_frac`, `area_frac`.
9. **Фильтры приёмки**: `inside` — след геометрически внутри B и
   `covis ≥ 0.90`; `partial` — `covis ∈ [0.60, 0.90]`; в обоих случаях
   покрытие кропа B ≥ 85%.
10. **Закрасить невалидное нейтральным серым** в обоих изображениях —
    иначе сеть цепляется за красные полосы и чёрные дыры как за признак,
    которого в боевой подложке нет.
11. **Запись** npz по спеке §2 + мета: помимо обычных полей —
    `pair_layout`, `area_frac`, `b_px`, `footprint_a_m`, `footprint_b_m`,
    `fov_deg`, `basemap_provider`, `basemap_version`, `basemap_zoom`,
    `compensation_m`, `compensation_src`, `anchor_id`.

**Контрольная ось.** Обязательно генерировать ~15% сэмплов, где сторона B —
кроп **того же ортофотоплана** (не подложки). На них разметка точна по
построению, и замер остатка обязан давать ~0.0 px. Это единственная
проверка, отделяющая ошибку кода от расхождения данных: у нас именно она
подтвердила геометрию (0.002–0.02 px), когда кросс-сезонные замеры не
работали.

## 6. V-тесты (писать до генератора)

Стенд раньше кода. Минимальный набор, каждый закрепляет конвенцию:

1. **Знак фазовой корреляции**: синтетический сдвиг `np.roll` → замер
   обязан вернуть тот же знак и величину.
2. **Тождество надира**: при нулевых углах и `H = GSD·f_px` наземные
   координаты = пиксельные, умноженные на GSD.
3. **Чистый yaw**: след поворачивается вокруг надирной точки, масштаб не
   меняется.
4. **Направление наклона**: центр кадра уходит в сторону азимута ровно на
   `H·tan(наклон)`; проверить все четыре стороны.
5. **Наклон — гомография**: четыре угла задают всё поле (сверить с
   аналитической гомографией по углам).
6. **Круговой тест**: земля → пиксель → земля возвращает исходную точку.
7. **Перекрытие**: для надира сверить с аналитической формулой
   прямоугольников; подбор смещения обязан попадать в цель.
8. **Компоновка inside**: след кадра целиком внутри кропа (включая случаи с
   наклоном и поворотом), и честный отказ, если кадр не помещается.
9. **По данным**: несколько сэмплов с B из того же растра → остаток < 0.5 px.

## 7. Отчёт и приёмка

Отчёт по корпусу (HTML, самодостаточный) должен содержать:

- **счётчики прогона**: принято, попыток, отсев по причинам (пустой якорь,
  дырявый кроп B, перекрытие вне диапазона), объём, средний размер сэмпла;
- **распределения осей**: высота, yaw, наклон, перекрытие, масштаб A/B,
  доля площади B под кадром, след кадра, покрытие кропа B;
- **метрики контроля разметки** — остаток между A и натянутой по `warp_ab`
  стороной B, **обязательно с числом состоявшихся замеров**;
- **галерею 70 примеров** четырьмя группами: самые структурные сюжеты,
  равномерный срез по корпусу, контрольные same-source, худшие по остатку.
  Панель: кадр A | кроп B | шахматка (B, натянутая на геометрию A).

Две вещи, без которых отчёт врёт:

1. **Гейт замера по высоте пика** (порог ~0.05). На сплошном лесу и ровном
   поле корреляции не за что зацепиться: она выдаёт «остаток 56 px» при
   пике 0.01. Это отказ замера, а не ошибка разметки — так и писать в
   подписи панели.
2. **Медиана всегда с `n`**, и при `n < 20` помечать её непоказательной.
   Иначе «0.04 px» по шести сэмплам читается как отличный результат.

Критерии готовности: V-тесты зелёные; поле сдвигов принято (доля валидных
узлов и медиана сдвига разумны); отсев объяснён; на контрольных
same-source сэмплах остаток ~0; галерея просмотрена человеком и шахматки
сходятся.

## 8. Чего не делать

- Не подтягивать компенсацию «к ближайшему решению»: замер вне потолка —
  это отказ корреляции, а не большой сдвиг. Правило приора из инвариантов
  проекта: **приор — ограничение, а не подсказка**.
- Не публиковать метрику без числа замеров.
- Не смешивать в один корпус площадки с непроверенной привязкой.
- Не брать территории тестового набора.
- Не менять принятые диапазоны параметров молча — любое отклонение
  выносить в отчёт вопросом.
