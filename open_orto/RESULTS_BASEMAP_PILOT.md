**Формат пары:** [DATASET_SPEC_FINETUNE.md](DATASET_SPEC_FINETUNE.md) §2

Что сделано: конвейер от сырого GeoTIFF до обучающих пар, где сторона A —
вид виртуальной камеры БПЛА из ортофотоплана, сторона B — кроп Esri World
Imagery на ту же территорию. Это боевой тип пары: именно так работает
целевой тракт локализации.

## 3. Этап Р — поле сдвигов

Главная техническая находка пилота: **на кропе ~150 м городская фактура
даёт ложные пики**. Разброс замеров на соседних узлах достигал ±17 м, при
том что реальный сдвиг ~2.5 м. Причина — повторяющиеся структуры (ряды
путей, одинаковые корпуса): корреляции не за что зацепиться однозначно.

Решение — **двухступенчатый замер**:

1. грубая ступень на кропе 307 м (GSD 0.30) с приором ±20 м — ловит сдвиг
   на большом уникальном рисунке;
2. тонкая ступень на кропе 154 м (GSD 0.15) в радиусе ±3 м вокруг грубого
   решения — уточняет до субпикселя;
3. расхождение ступеней служит **гейтом качества замера** (порог 3 м), а
   контроль остатка перечитывает подложку со сдвигом и требует < 1 м.

Плюс два решения по методу:

- **поиск пика ограничен радиусом приора** (`max_shift_px`): вне радиуса
  решение не «подтягивается», оно не рассматривается — инвариант проекта
  «приор — ограничение, а не подсказка»;
- **своя фазовая корреляция вместо `cv2.phaseCorrelate`**: её субпиксельное
  уточнение (взвешенный центроид) на гладких текстурах систематически врёт —
  замерено, истинный сдвиг 0.5 px читался как 1.3 px. Пик уточняется
  параболой по трём точкам, как и предписывает §4.3.

Результат первой редакции (шаг 300 м, порог соседей 3 м): 70 узлов, 46
валидных до фильтра соседей, **23 после**; сдвиг медиана **2.43 м**
(p10 0.66, p90 4.31), остаток медиана **0.015 м**, глобальная константа
(2.21, 0.99) м.

**Перекалибровка порога соседей.** Порог 3 м взят из задания, где он выведен
на парах «орто ↔ орто» — там обе стороны в одной сетке и поле однороднее. У
пар с подложкой абсолютные сдвиги больше, а поле неоднороднее (p90 4.3 м), и
порог 3 м выбивал половину валидных узлов. Порог поднят до 5 м как
перекалибровка под другой тип пары (регламент проекта: «смена условий —
смена калибровки порога»), и в поле теперь сохраняются **все** замеренные
узлы с флагом, чтобы перефильтровать без повторного прогона.

(отсекает служебные заливки чистым цветом заодно с чёрным и белым).

## 7. Редакция 3 (28.08, вечер): свободный курс и наглядные панели

Три доработки по замечаниям.

**1. Курс кадра — произвольный, ограничена разница курсов сторон.** Раньше
кроп подложки был жёстко north-up, а кадр имел курс ±25° — то есть взаимный
поворот и абсолютная ориентация кадра были связаны одним параметром. Теперь
курс кадра берётся из всей окружности (0–360°), кроп подложки **поворачивается
вслед за ним**, а ограничена только разница: `|yaw_A − yaw_B| ≤ 25°` — ровно
столько остаточной невязки курса допускает боевой тракт после предповорота.
Замерено на корпусе: курс кадра покрывает все 8 секторов окружности,
максимальная разница курсов 24.9° при медиане 12.5°.

Технически это потребовало обобщить сетку на поворот (`Grid.rot_deg`, оси,
`pixel_from_world`, углы) и считать **перекрытие следа в системе кропа B**:
повёрнутый кроп — не axis-aligned прямоугольник в мире, и сравнение по
габаритам давало бы неверный ответ. Всё покрыто тестами (круговой тест
повёрнутой сетки, азимут осей, сохранение масштаба, перекрытие в повёрнутой
рамке).

**Дефект, найденный при первом же прогоне.** Мозаика подложки заказывалась по
стороне сетки, а повёрнутая сетка занимает в мире прямоугольник до √2 раз
шире — углы кропа вылезали за скачанное окно и приходили серыми (`valid_b`
≈ 0.84, часть сэмплов браковалась). Исправлено: окно мозаики берётся по
габариту сетки; после правки `valid_b` ≈ 1.0. Закреплено тестом.

**2. Наложение — меньшего на большее.** В третьей колонке панели теперь
**кадр натянут на подложку**, а не наоборот: кроп B крупнее, и видно, куда
именно лёг кадр. След кадра обведён жёлтым. Натяжение считается гомографией,
снятой с самой разметки (сцена плоская, связь строго проективная; МНК по
сетке валидных точек устойчивее к субпиксельному шуму warp).

**3. Стороны в натуральном размере.** Панель больше не подгоняет кадр и кроп
под общую высоту — обе стороны кладутся как есть на общий холст, поэтому
видно реальное соотношение масштабов (кроп подложки заметно крупнее кадра).
Это перенято из отчёта первого агента по парам «орто ↔ орто».

**Корпус пересобран** (160 пар, 396 МБ, 2 отказа из 162 попыток):

| метрика | редакция 2 | **редакция 3** |
|---|---|---|
| контроль same-source | 0.020 px (n = 12) | **0.026 px (n = 14)** |
| пары с подложкой | 2.81 px (n = 108) | **3.21 px (n = 106)** |
| замеров не состоялось | 0 из 120 | 0 из 120 |
| компоновки | 110 / 50 | 109 / 51 |

Остаток на контрольной оси остался ≈ 0 — **свободный поворот сторон
геометрию не сломал**. Небольшой рост остатка у пар с подложкой (2.81 → 3.21
px) ожидаем: при произвольном курсе кадр чаще ложится под углом к сетке
подложки, и ресемплинг обеих сторон добавляет полпикселя размытия; вклад
параллакса зданий при этом никуда не делся.

## 8. Редакция 4 (28.08): высоты понижены до 175–300 м

По запросу диапазон высот съёмки сдвинут вниз: **175–300 м** вместо 250–400.
Кадр стал ближе к земле, и это ближе к нашим боевым низковысотным кадрам
(DRZ снимались с ~90 м), где малый наземный контекст — измеренно трудный
режим для матчеров.

| параметр | редакция 3 (250–400 м) | **редакция 4 (175–300 м)** |
|---|---|---|
| высота, медиана | 328 м | **234 м** |
| GSD кадра | 0.34–0.54 м | **0.24–0.41 м** (медиана 0.32) |
| след кадра | 348–558 м | **248–418 м** (медиана 326) |
| след кропа B | 400–900 м | **256–752 м** (медиана 483) |
| зум подложки | z19 (0.15 м/пкс) | **z18 у 135 пар, z17 у 7** |
| контроль same-source | 0.026 px (n = 14) | **0.027 px (n = 14)** |
| пары с подложкой | 3.21 px (n = 106) | **6.78 px (n = 106)** |

Корпус: 160 пар, 392 МБ, 2 отказа из 162 попыток; состав по компоновкам и
типам прежний (109/51, 142 с подложкой + 18 контрольных).

### Почему остаток вырос — и почему это не дефект

Контрольная ось не изменилась (0.027 px): **геометрия и разметка верны**.
Рост у пар с подложкой — 3.21 → 6.78 px — объясняется двумя множителями,
и оба физические.

1. **Мельче пиксель.** GSD подложки упал с ≈ 0.45 до ≈ 0.31 м, так что одна
   и та же ошибка в метрах даёт больше пикселей. В метрах рост скромнее:
   1.44 м → 2.10 м.
2. **Сильнее параллакс — главный вклад.** Кадр рендерится на плоскость
   z = 0, а здания реально торчат над ней. Смещение верхушки здания высотой
   `h` в кадре равно `h/H · r`, где `r` — удаление от надирной точки: при
   H = 175 м оно **в 1.7 раза больше**, чем при H = 300 м. Подложка же
   ортотрансформирована по своему рельефу и «валит» здания в свою сторону,
   и эти два искажения не сокращаются. На плотной городской застройке это и
   даёт основной рост.

Практический вывод: **понижение высоты честно усложняет корпус** — ровно тем
способом, каким его усложняет реальность. Для обучения это скорее плюс
(трудный режим ближе к боевому), но два следствия надо держать в голове:

- порог инлайеров при обучении и оценке на этом корпусе должен быть мягче:
  шум разметки вырос с ≈ 3.2 до ≈ 6.8 px, и метрика inl3 здесь уже
  бессмысленна — читать inl10;
- **метрический DSM стал нужнее**: сейчас параллакс зданий не снимается
  ничем, а на низких высотах он доминирует в остатке. С DSM его можно и
  учесть в рендере, и замаскировать высокие объекты в разметке.

Отдельно стоит отметить смену зума подложки: при GSD 0.31 м автоматика
выбирает z18 (0.30 м/пкс на этой широте) вместо прежнего z19 — то есть
подложка теперь приходит в своём натуральном разрешении, без даунсемпла.

## 9. Редакция 5 (28.08): объём выводится из площади, а не назначается

Прежние редакции задавали корпус числом («сделать 160 пар»), и это неверный
способ: одно и то же место попадало в датасет столько раз, сколько скажет
счётчик, а плотность покрытия нигде не контролировалась. Правильная величина —
**сколько пар приходится на квадратный километр съёмки**.

Новый режим генератора работает так:

1. рабочая зона режется на **непересекающиеся квадратные ячейки**
   (`--cell-m`, по умолчанию 400 м; для этой площадки взято 350 м);
2. ячейка проходит, если данными ортоплана покрыто ≥ 85 % её площади —
   покрытие сначала грубо по обзорной маске, затем нативной пробой (обзорная
   маска систематически завышает его, §2.5 задания);
3. в каждой ячейке делается **свой рефайнмент привязки**: если валидных узлов
   поля сдвигов рядом мало, сдвиг меряется прицельно в центре ячейки тем же
   двухступенчатым методом (§3) и добавляется в поле — соседние ячейки им
   тоже пользуются;
4. из ячейки берётся **3–5 пар** (`--per-cell`), якорь каждой джиттерится в
   пределах четверти стороны, чтобы это были разные виды места, а не кадры
   одной точки; высота, курс, наклон, компоновка и масштаб разыгрываются
   независимо.

Объём корпуса при этом — следствие: `плотность = пар с ячейки / площадь
ячейки`. Для 350 м и 3–5 пар это 24–41 пар/км².

### Что получилось на этой площадке

| величина | значение |
|---|---|
| ячеек 350 × 350 м с покрытием ≥ 85 % | **55** |

## 10. Редакция 6 (28.08): две новые площадки и три исправленные ловушки

Добавлены два ортофотоплана Манитобы (Канада, UTM 14N, GSD 3.1–3.2 см):
`68b9250f…` — гольф-клуб с озером, 1232 × 1465 м; `69faa4b8…` — посёлок,
907 × 1038 м. Обе площадки втрое-вчетверо мельче петербургской, и это сразу
вскрыло три места, где конвейер был настроен под первую площадку.

### Ловушка 1 (главная): подложки на нужном зуме там просто нет

Первый же гейт дал сдвиги 14–36 м при остатках до 38 м. Причина оказалась не
в привязке: **Esri на z19 в этом районе отдаёт серую заглушку «Map data not
yet available»**, и фазовая корреляция мерила шум. Проект эту ловушку знает
(`max_zoom` провайдера — предел пирамиды, а не гарантия покрытия), но в нашем
источнике подложки проверки не было.

Теперь `BasemapSource` перед первым чтением выясняет **самый детальный зум с
реальной съёмкой** (`deepest_imagery_zoom` по центру растра), ограничивает им
выбор зума, а если съёмки нет вовсе — поднимает `NoImageryError`, а не строит
пары по чистому листу. Для новых площадок предел — **z18 (0.379 м/пкс)**,
для петербургской по-прежнему z19 (0.15).

### Ловушка 2: ступени замера были привязаны к разрешению первой подложки

Разрешения 0.30/0.15 м/пкс выведены под z19. На z18 тонкая ступень шла по
**вдвое апсемпленной** подложке — субпиксельного пика там нет, и контроль
остатка не проходил: на площадке `69faa4b8` — 0 валидных узлов из 14. Тот же
класс ошибки, что «порог чужой калибровки»: параметр, снятый на одних данных,
перенесён на другие. Ступени теперь задаются **относительно фактического
разрешения подложки** (грубая — вдвое грубее, тонкая — родное).

### Ловушка 3: размер узла в пикселях не помещался в маленький растр

При 1024 px и подложке 0.379 м/пкс грубая ступень требовала кроп 776 м,
который на площадке 1.2 × 1.5 км почти всегда упирался в край съёмки:
**21 узел из 25 браковался** по «мало данных ортоплана». Размер узла задан
в метрах земли (400 м грубая, 200 м тонкая), число пикселей подстраивается
под разрешение. После всех трёх правок: 12 валидных узлов из 25 и 5 из 14.

Четвёртая, более мягкая правка: **сторона B не апсемплится**. Если самый
детальный доступный зум грубее запрошенного GSD, кроп читается в родном
разрешении подложки с сохранением охвата земли, а в мету пишется фактический
`scale_ratio` (и запланированный — отдельным полем). Иначе интерполяция
рисует детальность, которой в подложке нет.

### Что показали новые площадки

**Остаток разметки на сельской местности в 4–100 раз меньше городского**
(1.51 и 0.05 px против 6.40). Это прямое подтверждение диагноза §8: главный
источник остатка — **параллакс зданий**, а не привязка и не код. Там, где
застройка малоэтажная, разметка почти идеальна.

**Кросс-сезонность пришла даром.** Ортопланы сняты в другую фазу, чем
подложка: у гольф-клуба кадр — сочная летняя зелень против жёлто-бурой

подложки. Это ровно тот appearance gap, ради которого затевается дообучение,
и он появился без всяких усилий с нашей стороны.

**Появился разрез по территории.** Три площадки в двух странах — уже можно
резать held-out по площадке, а не по ячейкам одной территории.

## 11. Редакция 7 (28.08): корпус same_source на 119 площадках

поддержки, а не смешаны молча.

### Почему `same_source` считается отдельно и дёшево

У этих пар обе стороны берутся из одного растра, поэтому **подложка не нужна
вовсе**: ни сети, ни тайлов, ни поля сдвигов, ни гейта привязки. Разметка
точна по построению, и это позволяет две вещи, недоступные парам с подложкой:

- **наклон до 20°** вместо 10 (`SAME_SOURCE_TILT_MAX`): у пары с подложкой
  большой наклон упирался бы в параллакс зданий, здесь его нет;
- **цветовая аугментация стороны A** тем же приёмом, что в конвертере
  OrthoLoC: сезонная фотометрия по вегетационной маске (winter/autumn/spring),
  применяется после закраски невалидного — чтобы серые заплатки остались
  нейтральными и не приобрели сезонный оттенок. Геометрия не трогается.

## 12. Что дальше

- **вторая площадка** — сейчас корпус с одной территории, сплиты по
  территории строить не из чего;
- при появлении **метрического** DSM (float32 с высотами, а не картинки) —
  маскировать высокие объекты и снять параллаксную часть остатка;
- прогнать корпус через матчеры (как `bench_ortholoc.py` для OrthoLoC) —
  получить внешнюю точку сравнения именно на боевом типе пары;
- по мере роста корпуса — свести с парами OrthoLoC в одну обучающую смесь
  (формат записи у них общий, канонический).

## 13. Как воспроизвести

```bash
# 1. гейт привязки: годится ли растр
python open_orto/scripts/gate_check.py --raster open_orto/data/<файл>.tif --points 4

# 2. поле сдвигов (один раз на площадку, ~25 мин на 92 узла)
python open_orto/scripts/shift_field.py --raster open_orto/data/<файл>.tif --step 250

# 3. корпус пар
python open_orto/scripts/generate.py --raster open_orto/data/<файл>.tif \
    --shift-field open_orto/work/shift/shift_field_<stem>.npz --count 160 --seed 1

# 4. отчёт с галереей и контролем разметки
python open_orto/scripts/report.py --dataset open_orto/dataset

# V-тесты
python -m pytest open_orto/scripts/tests/ -q
```

Оговорка по среде: каталог `aux/` из задания на Windows создать нельзя
(зарезервированное имя устройства AUX) — рабочие артефакты лежат в
`open_orto/work/`.
