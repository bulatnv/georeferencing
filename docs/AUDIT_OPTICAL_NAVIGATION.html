01 · Резюме

Что это и в каком оно состоянии

optical-navigation — прототип бортового сервиса коррекции инерциальной навигации по аэрофотоснимку. Постановка обратна нашему image_localization: не «найти, где сделан снимок», а «исправить уже примерно известную позицию». На вход — кадр и телеметрия (координаты prior, высота, углы, фокус, сенсор); на выход — поправка delta_x/delta_y и набор GCP-точек «пиксель ↔ координата». Ошибка prior в рабочем сценарии — 40–80 м.

  • работает  Код зрелый и опрятный: сервис, симулятор и подготовка тайлов разделены; отказ — честный HTTP 422; есть профилирование стадий.
  • есть данные  На диске 107 ГБ подложки и полные eval-результаты: 7 экспериментов × 200 кадров, с итоговым XLSX и графиком.
  • не запустится как есть  Конфиги унаследованы от чужой машины: пути /home/zhenya/… в .env, сломанный .venv, стек Docker остановлен.
  • качество зависит от высоты  Success rate растёт со 100 м (15–18%) до 300 м (82–89%); на «чужих сезонах» медианная ошибка подскакивает до ~60 м.
02 · Архитектура

Три блока и конвейер /match

Проект состоит из сервиса-ядра, симулятора для генерации синтетики и оценки, и утилит подготовки тайлового кэша.

correction-service — ядро (FastAPI, Docker, GPU)

Один контейнер на базе nvcr.io/nvidia/pytorch:24.11-py3, порт 8002→8001. Обработка POST /match целиком в памяти, без временных GeoTIFF:

кадр + телеметрия→ pitch-adaptive crop→ warp в UTM→ мозаика тайлов вокруг prior→ MINIMA-RoMa Large→ RANSAC + предикаты→ GCP + Δx/Δy
  • Кроп по pitch (matching_crop.py): при |pitch| ≤ 30° кадр не режется, дальше кусочно-линейно до центральных 50% при 60°+ (узлы 30→1.0, 40→0.75, 50→0.60, 60→0.50); размеры сенсора уменьшаются пропорционально. Дальняя зона наклонного кадра после warp растягивается и портит матчинг — её просто отрезают.
  • Warp (warp.py): cameratransform строит лучи через углы кадра, пересечение с землёй даёт 4 GCP «пиксель фото → UTM», затем билинейный reproject через rasterio. UTM-зона выбирается автоматически по lat/lon. Если лучи не пересекают землю (широкий FOV при большом наклоне) — явная ошибка, не мусорный результат.
  • Мозаика (tiles.py): XYZ-тайлы из локального каталога (TILE_DIR) или по URL-шаблону; зум подбирается автоматически в [12, 18], чтобы длинная сторона мозаики была ~2048 px; защитные пороги — максимум 5000 тайлов, минимум 80% покрытия, иначе 422.
  • Матчер (matchers/minima.py): MINIMA-RoMa (model_type="roma", model_size="large") в fp16; в боевой конфигурации max_size=864, до 1000 точек. RANSAC у модели отключён — геометрию проверяет сервис: findHomography (порог 10 px, 10 000 итераций, conf 0.995) плюс два масштабных предиката.
  • Предикаты масштаба — знакомая нам идея «prior — ограничение»: сингулярные числа аффинной части гомографии сравниваются с ожидаемым масштабом warp↔карта; решение с неправдоподобным масштабом отбрасывается целиком, а не «подтягивается».
  • Лимиты запроса: радиус поиска ≤ 1000 м, сторона кадра ≤ 20 000 px, диагональ footprint ≥ 150 м.
  • В образ вшиты веса: minima_roma.ckpt, minima_loftr.ckpt (запасной LoFTR-матчер), DINOv2 ViT-L/14 в hub/checkpoints — чекпоинт на месте. Библиотека матчинга — vendored image-matching-models; cameratransform ставится без зависимостей из-за пина numpy 1.26.4.
  • Есть вариант для Jetson Orin (docker-compose.orin.yml, лимит 16 ГБ RAM) — целевая платформа бортовая.

simulator — синтетика и оценка

  • Рендер кадров из ортофотоплана по позе камеры: data_sampler.py (cameratransform + rasterio) и более точный ray_trace_sampler.py; генератор облачности clouds.py, тепловизор Boson (boson_camera.py, simulator-termal.ipynb).
  • Модель полёта: маршрут из KML, ИНС с дрейфом (inertial_navigation_system.py), ground-truth навигация, периодическая коррекция через API сервиса (optical_correction_client.py).
  • VPR-клиент (vpr_client.py): когда неопределённость больше max_range сервиса, область режется на окна-гипотезы — грубая локализация перед точным матчингом, аналог нашей retrieval-фазы.
  • Ноутбуки: mk-video-dataset → mk-frame-dataset → eval-frame-dataset (главный сценарий оценки), плюс profile.ipynb и profile-match.py для профилирования. Есть юнит-тесты клиента и ray-trace-сэмплера.

tiles — подготовка подложки

download_tiles.py качает XYZ-тайлы по bounds растра или KML-маршрута (с буфером), параллельно и с докачкой; формат каталога <zoom>/<x>/<y>.jpg. Альтернатива локальному каталогу — раздача через nginx и TILE_TEMPLATE_URL.

03 · Оценка

Методика eval и фактические результаты

Методика (docs/eval-frame-dataset.md): к ground-truth позе каждого синтетического кадра добавляют случайное смещение 40–80 м (seed 42), отправляют кадр с «ошибочной» телеметрией в /match и меряют остаточную ошибку после поправки. На машине лежат готовые результаты семи прогонов — конфигурация offset_40_80 · imgsize 864 · 1000 kpts, по 200 кадров каждый. Пересчитано из CSV при аудите:

Все 644 отказа — один и тот же честный HTTP 422: algorithm does not converge: геометрическая проверка не пропустила решение. Из чисел видно три закономерности:

  • Высота решает. На 100 м footprint кадра мал относительно мозаики и success проваливается до 15–18%; на 300 м — 82–89%. Рабочая зона текущей конфигурации — от ~200 м.
  • Сезон и источник данных бьют по точности, а не по success. Осенний и «2021-й» наборы сходятся так же часто (56–59%), но медианная ошибка успешных кадров вырастает с ~5.5 м до ~59 м — матчер уверенно цепляется, но за сместившуюся фактуру. Знакомый нам режим «уверенно-неверных» решений.
  • P95 тяжёлый везде (до 160 м) — хвост грубых промахов фильтрацией пока не срезан; поле для доработки quality-контроля.

05 · Связь с image_localization

Пересечения и что можно позаимствовать

Задачи комплементарны: наш проект решает глобальный поиск без надёжного prior (retrieval по большой области), этот — точную коррекцию при ошибке ≤ 80–1000 м. Вместе они складываются в двухэтажную схему, которую мы сами описали в статье: грубая локализация → точная привязка.

  • Общий матчер. Здесь в бою тот самый MINIMA-RoMa, который мы разбирали в docs/MODEL_MINIMA_ROMA.html — есть готовый стенд, чтобы сравнить его с нашими SIFT/LightGlue на одних кадрах.
  • Идеи в нашу сторону: pitch-adaptive кроп перед warp; выбор зума мозаики под целевой размер; предикаты правдоподобия гомографии по сингулярным числам (родня нашему инварианту «приоры — ограничения»); VPR-окна как формализация перехода между этажами.
  • Идеи в их сторону: наш quality-контроль (эллипс ковариации, NCC/DINO-проверка) мог бы срезать тяжёлый P95-хвост и «уверенно-неверные» решения на чужом сезоне.
  • Готовая синтетика. Симулятор с ИНС-дрейфом, облаками и тепловизором — то, чего у нашего стенда нет; его можно направить на наши ортофотопланы.
