## 1. Сделано до экспериментов

**Ф1.** `RoMaMatcher` снимает перцентили поля certainty до `sample()`:
`certainty_p10/p50/p90/p99`, `certainty_frac_gt005/gt050` — по образцу
`overlap_field_*` у v2. Колонки добавлены в `probe_matcher.py`.

**Ф2.** Голый литерал `min_conf=0.5` у v1-линии заменён именованной константой
`ROMA_V1_MIN_CONF` с комментарием про no-op по построению.

**Ф3.** Имя `roma` проходит в `create_matcher`/пробу/стенд без оговорок
(реестр: `RoMaMatcher(checkpoint=None)`); штатные веса `roma_outdoor.pth`
(425 МБ) скачаны и закешированы.

**И1 — S найдена, hook в v2 не обязателен, но `match()` не годится.**
По исходникам установленного `romav2`: модуль `Matcher`
(`_compute_match_embeddings`) считает `attn_AB_logits = cos_sim(f_A, f_B)/temp`
(temp = 0.1) и кладёт в свой выход **`attn_AB_logits` формы
(B, H_A, W_A, H_B, W_B)**; верхний `RoMaV2.match()` пересобирает словарь и
эти ключи отбрасывает. Снимаем forward-hook-ом с модуля `matcher`.
У v1-линии аналог — якорная классификация
**`decoder.embedding_decoder` → `gm_warp_or_cls` формы (2, 4096, 40, 40)**
(батч 2 — symmetric-режим: [0] = A→B), от которой `cls_to_flow_refine` берёт
argmax по 4096 якорям (mode) и усредняет только 5 соседей моды. Механизм
Г-арх, заявленный в спеке, существует в исходниках буквально: у v2 argmax
нигде не берётся (softmax → einsum с координатными эмбеддингами → DPT).

**И2.** `scripts/probe_modes.py` (opt-in): argmax_hit_frac / warp_hit_frac /
identity_frac_6px / best_wrong_consensus одним кодом для всех ядер; поддержаны
Э2.2 (`--side-px`, обрезка обеих сторон) и Э2.3 (`--ref-zoom-offset`).
Чистая геометрия проверена 16 аналитическими тестами
(`tests/test_probe_modes.py`). Дым на тождественной случайной паре
(ванильная v1, CPU): argmax_hit = 0.977, top10 = 0.994, warp_hit = 1.0,
identity_6px = 1.0 — тракт метрик согласован.

**И3.** `--dump-field` пишет поля warp/уверенности и карту argmax в `.npz`;
в `evidence` массивы не кладутся.

## 2. Инцидент среды (Э1.0) — зафиксировано до вердиктов

Контроль Э1.0 упёрся не в код, а в машину. Диагноз по шагам:

- Полный `pytest` падает `Windows fatal exception: access violation` при
  загрузке весов MegaLoc (`safetensors` → `torch.storage`); воспроизводится
  **на чистом master** — правки Ф1–Ф3 не при чём. Сьют без
  `test_retrieval.py` зелёный (exit 0); изолированные megaloc-тесты зелёные.
- `regress.py` (боевой прогон) падает тем же access violation на первом кейсе
  — причём точка падения **дрейфует** между повторами внутри стройки
  ViT-large (обычные CPU-аллокации `nn.Linear`).
- Причина найдена: **исчерпание системного коммита** — 351.8 из 360.5 ГБ
  (97.6%), при 70 ГБ свободной физической памяти. Процессы держат 89 ГБ,
  ядро 12 ГБ; ~250 ГБ висят в разделяемых секциях. `nvidia-smi` показывает
  18–20 ГБ VRAM занятыми **при нулевом списке живых compute-процессов** —
  мёртвые CUDA-контексты сегодняшних аварий не освобождены драйвером, и в
  WDDM каждая их VRAM-аллокация подпёрта системным коммитом.
- Следствие: `cudaMalloc` на 1.11 ГБ падает OOM при «18 ГБ свободно» — GPU
  недоступен для прогонов любого размера. CPU-прогоны в пределах ~8 ГБ
  оставшегося коммита проходят (весь pytest без retrieval, дымы, CPU-пробы).

**Лечение — перезагрузка машины** (освобождает и коммит, и висящие
CUDA-контексты). До неё GPU-эксперименты не проводятся; сделанные сегодня
замеры выполнены на CPU и помечены как предварительные.

## 3. Э1.1 — оракульная проба, предварительные CPU-числа

Плечи v1-линии сняты 2026-08-24 на CPU (`--device cpu`, колонка `device` в
CSV): `eval_out/probe_roma_vanilla_cpu.csv`, `eval_out/probe_minima_roma_cpu.csv`.
Позы — канонический `eval_out/eval.csv` (провенанс: matcher=minima_roma).
Плечи v2 требуют GPU и будут сняты той же командой после перезагрузки; для
финального вердикта **все четыре плеча перепрогоняются одной GPU-сессией**.

| кейс | ванильная roma: инл / ошибка | minima_roma: инл / ошибка |
|---|---|---|
| `DRZ_00755` | **1058 / 1.3 м** | 1582 / 1.1 м |
| `Ufa3` (кросс-сезон) | **1411 / 5.2 м** | 1305 / 5.0 м |
| `Ufa2` | нет позы | нет позы |
| `Volgograd3` | **761 / 0.3 м** | 657 / 0.7 м |

Отрицательное плечо (`--offset-m 300`): у обоих ядер отказ на
DRZ_00755/Ufa3/Ufa2; на Volgograd3 оба дают позу в сдвинутом окне
(96 и 121 инл, ошибка ~284–286 м) — окна там перекрываются (отпечаток
~370 м > сдвига), поведение одинаково у обоих плеч.

**Предварительное чтение (не вердикт).** На четырёх оракульных кейсах
ванильная v1 берёт столько же кейсов, сколько MINIMA-RoMa (3 из 4), и на
единственном кросс-сезонном кейсе даёт **больше** инлайеров (1411 против
1305, отношение 1.08 — в пределах 1.5×). Это профиль **исхода D спеки
(«дообучение почти не дало»)** — обязательного к записи. До вердикта нужны:
плечи v2/v2-raw (GPU), сквозной Э1.2 и повтор всех плеч одной сессией.

**Вклад Ф1 — висящий вопрос `cover_thresh = 0.5` закрыт измерением.**
На верных парах медиана certainty 0.009–0.32, `frac_gt050` = 0.002–0.31;
у ванильной v1 верная пара DRZ_00755 с 1058 инлайерами имеет
`certainty_cover` = **0.00195**. Порог 0.5 стоит выше рабочего диапазона
величины — «верные локализации доходят до нуля по cover» (веха 2026-07-29)
подтверждено; решение «`certainty_cover` в связку не брать» теперь опирается
на замер. Разделение верное/ложное при этом живёт ниже: `frac_gt005`
(0.15–0.85 на верных против 0.004–0.25 на ложных у обоих ядер).

## 4. Э2 — природа залипаний

Сторона v2 требует GPU (пакет `romav2` жёстко использует `autocast("cuda")`
в `features.py:140` — на CPU не запускается; и по скорости это было бы
непрактично). **Плечо сравнения — v1-линия — снято на CPU** (Э2.1,
`eval_out/modes_roma_cpu.csv`, `modes_minima_roma_cpu.csv`; поля — в
`eval_out/modes_fields/*.npz`):

| кейс | ядро | argmax_hit | top10 | warp_hit | identity_6px | RANSAC: инл / rot / scale / err |
|---|---|---|---|---|---|---|
| `DRZ_00755` | roma | 0.049 | 0.156 | 0.085 | 0.125 | 1227 / 1.7° / 0.85 / **1.2 м** |
| `DRZ_00755` | minima | 0.134 | 0.206 | 0.099 | 0.054 | 1588 / 2.3° / 0.87 / **1.1 м** |
| `DRZ_01018` | roma | 0.042 | 0.050 | 0.058 | 0.028 | 622 / 4.2° / 0.86 / **4.5 м** |
| `DRZ_01018` | minima | 0.091 | 0.175 | 0.138 | 0.051 | 839 / 3.8° / 0.88 / **4.8 м** |
| `DRZ_06498` | roma | 0.009 | 0.000 | 0.001 | 0.001 | 407 / 0.9° / 0.98 / **6.9 м** |
| `DRZ_06498` | minima | 0.018 | 0.000 | 0.025 | 0.000 | 927 / −5.7° / 0.88 / **8.3 м** |
| `Volgograd3` | roma | 0.546 | 0.706 | 0.852 | 0.120 | 834 / −0.6° / 0.95 / **0.6 м** |
| `Volgograd3` | minima | 0.759 | 0.863 | 0.868 | 0.098 | 695 / −0.0° / 0.95 / **0.4 м** |

Снятый тензор v1: `decoder.embedding_decoder.gm_warp_or_cls`,
форма (2, 4096, 40, 40) — батч 2 это symmetric-режим ([0] = A→B), 4096 —
якоря классификации, сетка 40×40. `best_wrong_consensus = 0` во всех восьми
строках: **свободный RANSAC (масштаб 0.3–3, поворот свободный) у v1-линии
даёт верную позу на всех кейсах, включая оба, где v2 залипала на
+121°/масштаб 1.79**. У ванильной v1 и MINIMA картина одинаковой формы —
залипание v2 не воспроизводится всей v1-линией.

Замечание к чтению долей: `argmax_hit_frac` на маленьких окнах (352–420 px,
патч ≈ 9–10 px) численно ниже, чем на большом Volgograd3 (патч ≈ 31 px), —
допуск ±1 патч в пикселях там жёстче. Сравнивать надо argmax против warp
**внутри кейса** и v2 против v1 **на том же кейсе** — решающая пара чисел
v2 будет снята после перезагрузки.

`Volgograd3`, обе стороны обрезаны согласованно (`--side-px`), GSD неизменен:

| сторона, px | roma: argmax / warp / err | minima: argmax / warp / err |
|---|---|---|
| 1236 (родное) | 0.55 / 0.85 / 0.6 м | 0.76 / 0.87 / 0.4 м |
| 1000 | 0.52 / 0.81 / 1.4 м | 0.67 / 0.85 / 1.7 м |
| 800 | 0.45 / 0.70 / 0.7 м | 0.64 / 0.84 / 0.5 м |
| 600 | 0.28 / 0.48 / 4.2 м | 0.49 / 0.64 / 1.7 м |

Доли деградируют с сужением (меньше контекста и жёстче пиксельный допуск),

малом окне. Появится ли залипание у v2 на этих же размерах — вопрос
GPU-сессии.

### Э2.3 — рассогласование масштаба, контроль v1-линии (CPU)

Ступень **тоньше** (`+1`) для этих кейсов геометрически недоступна: их
рабочий зум уже на потолке провайдера (z19 у Esri), запрос z20 честно
отвергается `fetch_basemap`. Снята ступень **грубее** (`−1`, истинный
масштаб q→r = 0.5):

| кейс | ядро | argmax / warp | RANSAC scale / err |
|---|---|---|---|
| `DRZ_00755` | roma | 0.10 / 0.14 | 0.44 / **1.0 м** |
| `DRZ_00755` | minima | 0.15 / 0.20 | 0.45 / **0.5 м** |
| `Volgograd3` | roma | 0.51 / 0.83 | 0.48 / **0.8 м** |
| `Volgograd3` | minima | 0.71 / 0.87 | 0.48 / **0.6 м** |

Рассогласование масштаба вдвое v1-линию не ломает: доли argmax/warp почти
не проседают против согласованного масштаба, RANSAC восстанавливает
масштаб ~0.44–0.48 и верную позу. Усиливает ли то же рассогласование
залипание v2 — вопрос GPU-сессии.
