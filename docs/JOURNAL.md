## Оптимизированный конвейер PCA+FAISS (рецепт «как сейчас лучше всего»)

Стабильная сводка рекомендованной конфигурации — что собрано из вех ниже в единый
рабочий поток. Две фазы: **офлайн** (карта строится один раз, кэшируется) и
**онлайн** (поиск снимка по карте, реальное время).

```
ОФЛАЙН (один раз на район, кэшируется на диск)
  регион подложки → нарезка на клетки (≈ footprint кадра, перекрытие 50%)
    → MegaLocEncoder (VPR: DINOv2-B + SALAD)         ← сильный дескриптор
    → PCAReducer.compress(1024, whiten=False)         ← память ÷8, ранг ↑ (49→15)
    → FaissAnn (HNSW, inner-product = косинус)         ← поиск O(log N)
    → TerrainIndex.save(map.npz)                       ← кодировки клеток на диске

ОНЛАЙН (на каждый кадр)
  TerrainIndex.load(map.npz)  ← без пере-кодирования и докачки тайлов
    → кадр → prerotate(−yaw) → MegaLoc → PCA → FAISS top-K клеток   (Этаж 1, ~десятки мс)
    → LightGlue-поза на каждом кандидате (мультигипотеза) + ECC       (Этаж 2, доминирует)
    → quality.assess: связка  инлайеры≥8 И NCC≥0.12 И эллипс≤порога   ← 0 ложных
    → принять только LOCALIZED (в поиске по карте)
```

**Команды.**
```
# офлайн+онлайн разом: строит/грузит карты кластеров, ищет все снимки, мерит время
python scripts/map_benchmark.py --data for_binding/DRZ --map-radius-km 2 --top-k 25
# одиночный широкий приор со всеми оптимизациями и разбивкой таймингов
python scripts/localize_wide.py --image test_images/00049.JPG --offset-km 2 \
    --encoder megaloc --pca-dim 1024 --faiss --top-k 25 --min-inliers 6
```

**Каждая оптимизация и что она даёт (измерено, MegaLoc, DRZ):**

| Оптимизация | Роль | Эффект |
|---|---|---|
| MegaLoc вместо сырого DINOv2 | различимость Этажа 1 | ранг верной клетки 506→2 (город), 139→1 (поле) |
| plain PCA→1024 (whiten off) | память + ранг | 206→25 МБ (÷8.2); ранг 49→15 ⇒ top-25 вместо top-60 |
| FAISS/HNSW | скорость поиска | O(log N); recall=numpy; выигрыш на 1e5..1e6 клеток |
| персистентная карта (.npz) | убрать пере-кодирование | офлайн 357 с → **онлайн-поиск ~2 с** |
| связка инлайеры∧NCC | отсечь ложные | ложняк 2126 м → отказ, **0 ложных** |

**Что где живёт по времени:** офлайн определяется кодированием клеток (O(N),
кэшируется); онлайн — веером LightGlue Этажа 2 (O(K), режется меньшим top-K, т.е.
лучшим рангом); ретривал-запрос и FAISS/PCA онлайн ничтожны. **Рычаги независимы:**
офлайн ускоряет только кэш карты, онлайн — только меньший top-K.

**Границы (честно):** whitening вредит (дефолт off); связка ценой полноты режет
слабые кросс-дата кадры (0 ложных важнее); ±5 км без PQ-кванта упирается в память;
Ufa-кросс-сезон вне локализуемости по Esri. Детали и числа — в вехах ниже.

## 2026-08-30 (вечер) — Пары с подложкой на 267 площадках: разметку здесь проверяет матчер, а не корреляция

**Что.** Собран корпус боевого типа — **2294 пары «ортоплан ↔ спутниковая
подложка» с 267 площадок** (4.86 ГБ) против 305 пар с трёх площадок до этого.
Конвейер площадки: привязка (этап Р) → гейт по валидным узлам → генерация,
параллельно пулом воркеров (441 площадка за 67 минут на пяти).

**Зачем.** `same_source` учит инвариантности к ракурсу, но не переносу между
источниками — а именно он и есть наша задача. Домен пары «надир ↔ Esri»
воспроизводится только такими парами.

**Результат в числах.** Аудит независимым арбитром (MINIMA-RoMa на выборке пар
каждой площадки): **250 площадок — разметка подтверждена**, расхождение с
матчером 4.53 px (p90 8.58); 39 — привязка сдвинута, 10 — без структуры, 7 —
проверено частично. Пары «сдвинутых» уведены в карантин. Гейт привязки до
генерации отсёк ещё 128 площадок из 441: там подложка с ортопланом не
совмещается вовсе.

**Следствие 1 — у пар с подложкой другой класс точности разметки.** 4.5 px
(≈1.5 м) против 0.025 px у `same_source`. Это не дефект конвейера, а предел
двух независимых источников (геопривязка орто, мозаика Esri, параллакс,
разный рельеф). При смешивании корпусов это надо держать в уме: порог 3 px на
таких парах соизмерим с шумом самой разметки.

**Следствие 2 — привычный контроль здесь не судья.** Фазовая корреляция по
градиентам на смене фактуры (орто зимой, подложка летняя) вырождается в шум и
показывает 37 px там, где матчер уверенно даёт 3 px. Мера «пик над фоном» не
разделяет: пилотные площадки 11.0, кросс-сезонные 7.5. Поэтому арбитром взят
матчер — но строго как **измеритель**: его соответствия никуда не
записываются, иначе модель обучалась бы на собственных предсказаниях. Три
исхода различаются по согласованности матчера с самим собой и с нашим GT:
разметка подтверждена / привязка сдвинута / без структуры.

**Ловушка, стоившая половины корпуса.** Шаг сетки узлов привязки считался по
паспортной площади растра, а узлы ставятся только в рабочей зоне после эрозии
края — она втрое-вдесятеро меньше. Заказывалось 15 узлов вместо 60, и площадки
с нормальной долей валидных замеров (0.22) не набирали пяти. Отказ выглядел
содержательным («привязка не строится»), а был артефактом расчёта. Повторный
прогон вернул 128 площадок из 256.

**Побочно: привязка к производительным ядрам.** На гибридном CPU (i7-12700)
планировщик Windows 10 кладёт счётные процессы на энергоэффективные ядра;
замерено на нашей нагрузке — E-ядро медленнее P на 32–37 %. Пул теперь ставит
маску по `EfficiencyClass`, дочерние процессы её наследуют.

Коммиты: `8c7bfd2` (конвейер), `d44a4e3` (аудит), `8115f50` (ядра), `499a7dc`
(шаг по рабочей зоне). Подробности — `open_orto/RESULTS_BASEMAP_PILOT.md`
(редакция 9).

## 2026-08-30 — Свой корпус пар: 435 площадок, разметка 0.025 px, генерация параллелится по площадкам

**Что.** Собственный конвейер `open_orto/` (гейт привязки → поле сдвигов →
генератор пар) доведён с трёх пробных площадок до **корпуса same_source на 435
площадках: 2257 пар, 5.63 ГБ**, канонический формат `DATASET_SPEC_FINETUNE §2`
— тот же, что у конвертера OrthoLoC, значит смешивать их в одну обучающую
выборку можно без адаптеров. Генерация распараллелена по площадкам
(`run_parallel.py`, 5 процессов): **320 площадок за 4 минуты** против
оценочных ~3.5 часов однопоточно.

**Зачем.** Дообучение — линия, выбранная треком F, — упирается не в код
обучения, а в данные нашего домена: надир↔подложка, низкие высоты, кросс-дата.
OrthoLoC даёт внешнюю точку сравнения, но чужой домен; свой корпус строится из
открытых ортофотопланов, где разметка выводится геометрией, а не размечается
руками.

**Результат в числах.** Контроль разметки на паре «ортоплан сам на себя» —
**остаток 0.025 px** (n = 600) — и он не сдвинулся при росте корпуса вчетверо:
геометрия рендера от площадки не зависит, чего и ждали. Наклон до 20°
(45 % пар свыше прежнего потолка 10°), цветовая аугментация на 59 % пар,
высоты 175–300 м, медиана 4 пары с площадки. Разброс площадок — на порядок
(0.5–45 км²), поэтому части нарезаются жадной раскладкой по площади, а не
подряд: иначе одна корзина работала бы вдвое дольше прочих.

**Следствие.** Две ловушки записи, которые стоит помнить в любом массовом
прогоне: (1) **один npz из 2195 записался с битым CRC** при внешне нормальном
размере — пара, которая не читается, свалит обучение на середине эпохи, а
искать будут в загрузчике; проверка CRC встроена в слияние; (2) генератор
**дописывает** манифест, и остаток прошлого прогона влился в общий второй раз
— 217 дублей, при этом файлы на диске были в порядке. Инвариант после каждого
прогона: строк в манифесте ровно столько же, сколько файлов, имена уникальны.

Главный источник остатка на парах **с подложкой** остался прежним — параллакс
зданий (город 6.40 px против 1.51 и 0.05 px на сельских площадках); снять его
можно только метрическим DSM, не алгоритмом.

Коммиты: `77f22e4` (параллельная генерация), `2b1ac80` (проверка целостности),
`186f4ef` (защита от двойного слияния). Подробности —
`open_orto/RESULTS_BASEMAP_PILOT.md` (редакция 8).

## 2026-08-25 — Пять ядер на внешнем OrthoLoC: слабость v2 у нас — это Esri, а не надир

**Что.** Скачаны test-сплиты датасета OrthoLoC (NeurIPS 2025; 1591 пара
UAV-кадр ↔ ортофото с плотным попиксельным GT из point_map) и прогнаны все
пять ядер по соответствиям против GT (`scripts/bench_ortholoc.py`,
`docs/BENCH_ORTHOLOC.md`, данные — `docs/DATA_ORTHOLOC.html`).

**Зачем.** Внешняя точка сравнения баз перед дообучением + проверка, чем
именно наш домен труден для v2 (надиром или подложкой).

**Результат (медианы inl5 по сэмплам).** romav2 доминирует везде: 0.86 на
штатных парах, 0.40 на кросс-источниковых, **0.82 в надирной зоне ≤15°** —
против 0.09/0.06 у v1-линии там же; LoFTR-линия на этом домене не работает
совсем (0.00 у обеих арм). Ванильная v1 снова ≥ MINIMA (0.71 против 0.63 на
R; 18 против 51 px EPE) — третья независимая точка паттерна D. Сцена L51
(1269 сэмплов xDOP) не даётся никому.

**Следствие.** Слабость v2 на нашем стенде — **не «надир вообще»**: на
чужом надире с качественным ортофото она первая с большим отрывом. OOD для
неё — вид нашей второй стороны пары: спутниковая подложка Esri + окна
350–430 px (уточнение к Г-дан трека F). Выбор базы (линия v1) не меняется —
он сделан по боевому домену; OrthoLoC становится (а) источником трудных
xDOP-пар для смеси дообучения и (б) готовой нулевой точкой для проверки, не
ломает ли наше дообучение общую способность. Быстрый режим MINIMA-LoFTR на
этот класс данных не переносится — знать при любых разговорах о переносимости.

## 2026-08-24 (поздний вечер) — F2: на линии LoFTR вклад MINIMA велик; исход D — свойство RoMa, не переноса

**Что.** Спецификация `RESEARCH_F2_LOFTR_BASE.md`: тот же вопрос «база против
дообученной», но на LoFTR — сети, которую MINIMA дообучала целиком (забывание
−23.7 AUC против −0.9 у RoMa). Оракульная сверка Э-L3 сомкнулась с прежними
числами (тракт не менялся), главный прогон Э-L1 — оба плеча сквозняком при
полностью снятых порогах (coarse_thr=0, min_conf=0, окно 640), одной сессией.

**Зачем.** Проверить, является ли исход D трека F («вклад дообучения MINIMA
мал») общим свойством переноса MINIMA на наш домен — независимая репликация
на другой архитектуре, с зафиксированным до прогона предсказанием
(|разница| > 1 места) и защитой от соблазна лёгкой репликации (§7 спеки).

**Результат (числа).** Э-L1: ванильная LoFTR — 30/30 поз, 22 верных,
**3 ложных принято** (424/206/50.1 м, dino 0.39–0.43); MINIMA-LoFTR — 30/30,
**27 верных, 0 ложных**. Разница +5 верных в одну сторону (Ufa3, Volgograd4,
DRZ_03149/06401/18912), выше оценки шума 1–3 кейса; оракульный намёк
«ванильная сильнее на Ufa3» (112 против 56 инл) сквозняком опровергся —
ванильная теряет верное окно (1999 м). Э-L2 (операционные пороги, один
квантиль ~p88, обе доли ~12%): на 640 плечи близки (23/24 верных, 0 ложных),
на 1024 ванильная разваливается (19 верных, 5 ложных) при 26/2 у MINIMA.

**Следствие.** **Исход B**: репликации D нет — «вклад MINIMA мал» было
свойством линии RoMa (дообучен только декодер при замороженном DINOv2), а не
переноса MINIMA вообще; величина эффекта пропорциональна доле перестроенной
сети (предсказание подтверждено, знак — «помогло»). Для трека E ожидания
скорректированы **вверх** при достаточной разморозке, «сколько слоёв
размораживать» — главная ручка (правки: STRATEGY §2.2, план E §1). Быстрый
режим остаётся на MINIMA-LoFTR — ванильная kornia не заменяет её ни по
верным, ни по ложным. Формулировка для статьи: вклад кросс-модального
дообучения измерен на двух архитектурах — от +1 (RoMa, частичное) до
+5 и −3 ложных (LoFTR, полное). Отчёт: `RESEARCH_F2_REPORT.md`.

## 2026-08-24 (вечер) — Трек F завершён: база — линия v1; залипания v2 — данные, не архитектура

**Что.** После перезагрузки (среда очистилась: коммит 11.3 ГБ, VRAM 0.4 ГБ,
полный pytest зелёный, regress 0 регрессий) выполнен полный протокол спеки F:
Э1.1 — четыре плеча одной GPU-сессией, Э1.2 — сквозной nogate ванильной
roma на 30 кейсах, Э2.1–Э2.3 — решающий тест argmax против warp у v2 с
контролем v1-линии.

**Зачем.** Вердикты по заранее зафиксированным критериям — какую базу
дообучать и лечится ли залипание v2 дообучением.

**Результат (числа).** Оракул (4 кейса): ванильная v1 **3/4** (Ufa3:
1522 инл — 2.8× к v2), MINIMA 3/4 (1396), v2 2/4 (539), v2 raw 2/4.
Сквозняк nogate: ванильная v1 **29/30 поз, 25 верных, 0 ложных принято,
медиана 3.6 м** — против 22/30 и 16 верных у v2 в том же протоколе и 26
верных у боевой MINIMA. Решающий тест: на залипающих кейсах у v2
`argmax_hit ≈ warp_hit ≈ 0.001` при 0.02–0.13 у MINIMA тем же кодом —
матрица сходства v2 сама не знает ответа (тензор `matcher.attn_AB_logits`
(1,50,50,50,50)); залипание воспроизведено на рабочем Volgograd3 простым
сужением окна до 800 px (−174°/масштаб 0.49/135 м), у v1-линии на всех
размерах и при масштабе 0.5 — верные позы, 20/20.

**Следствие.** По критериям: **исход B** (база — линия v1: +9 верных
сквозняком) и **исход D** (вклад дообучения MINIMA мал: +1 верное место)
одновременно; по Э2 — **Г-дан + контекст, Г-арх опровергнута** (гипотеза
автора спеки, сформулированная постфактум, решающим тестом снята — записано
без смягчений). Для трека E: дообучать линию v1, ожидания прибавки
пересмотреть вниз; «вернуть argmax перед DPT» из вариантов исключить;
боевой дефолт (MINIMA-RoMa) не меняется. Побочно: `cover_thresh=0.5` выше
рабочего диапазона certainty (верная пара с 1097 инл — cover 0.002), вопрос
июля закрыт замером. Отчёт: `RESEARCH_F_REPORT.md`.

## 2026-08-24 — Трек F начат: ванильная RoMa v1 впервые измерена; v1-линия не залипает нигде

**Что.** Принята к исполнению спецификация `RESEARCH_F_BASE_CHOICE.md` (выбор
базы под дообучение). Сделаны патчи Ф1–Ф3 (перцентили `certainty` у v1 до
`sample()`; именованный `ROMA_V1_MIN_CONF`; проход имени `roma`) и
инструментация И1–И3: opt-in `scripts/probe_modes.py` снимает у плотного ядра
`argmax_hit_frac` (верна ли матрица сходства S до усреднения) против
`warp_hit_frac` (доносит ли ответ warp) — одним кодом для всех ядер, S
хук-ами (`attn_AB_logits` у v2; `gm_warp_or_cls` (2,4096,40,40) у v1),
16 аналитических тестов на геометрию. Прогнаны CPU-доступные плечи: Э1.1
(v1-линия), Э2.1–Э2.3 (v1-контроль).

**Зачем.** Сравнение «v2 22/30 против MINIMA-RoMa 30/30» — это сырая v2
против дообученной v1; честного плеча ванильной v1 в проекте не было ни разу.
Без него база под дообучение выбиралась бы по подмененному сравнению.

**Результат (числа, CPU, предварительные).** Оракульная проба (4 кейса):
ванильная v1 берёт 3/4 — как MINIMA, — и на кросс-сезонном `Ufa3` даёт
**1411 инлайеров против 1305 у MINIMA** (1.08×, в пределах 1.5× критерия D).
Свободный RANSAC у v1-линии верен на **всех** кейсах, где v2 залипала на

## 2026-08-21 — Вход эксперимента получил провенанс: закрыта утечка eval.csv

**Что.** Исполнена инженерная задача `FIX_EVAL_ARTIFACT_LEAK.md` (источник —
протокольная находка перепроверки GIM-LightGlue). Частичный прогон стенда
(`--cases X`) молча перезаписывал канонический `eval_out/eval.csv` — вход
оракульных проб (`--poses`) у `probe_matcher.py` и `e_sigma_ransac.py`; на
затёртом файле пробы либо тихо теряли manual-кейсы (так выпал `Volgograd3`),
либо — форма хуже — взяли бы позы, порождённые другим ядром, и это не было
видно нигде.

**Зачем.** Та же болезнь, что молчаливый no-op весов и порогов, — этажом выше:
веса проверяем счётчиком тензоров, пороги читаем обратно из модели, а файл, из
которого эксперимент берёт вход, не проверял никто. Провенанс при этом уже
писался (`*.config.json`) — его просто никто не читал.

**Результат.**

- Ф1: частичный прогон пишет `eval_cases_<slug>.csv` и говорит об этом;
  молча попасть в `eval.csv` частичным прогоном нельзя (явный `--out` в канон —
  с громким предупреждением).
- Ф2–Ф4: общий загрузчик `scripts/poses_provenance.py` — отказ с подсказкой
  вместо тишины (файла нет / manual-кейсы не покрыты), предупреждение при позах
  от небоевого ядра, эскейп-хатч `--allow-partial-poses`; колонки
  `poses_src/matcher/n_cases/mtime` доезжают до CSV обоих потребителей, пропуск
  кейса — строка `skipped_no_pose`, а не только печать.
- Ф5: 11 тестов (`tests/test_eval_artifacts.py`), всего 635 зелёных.
- Приёмка: сценарий воспроизведения (канон не тронут, mtime/размер совпали);
  сценарий отказа (урезанный файл — внятная ошибка); затёртый на машине
  `eval.csv` (1 строка `Volgograd4`) пересоздан полным прогоном боевого ядра.

**Следствие.** Третье правило регламента, рядом с двумя из перепроверок:
**вход эксперимента обязан нести провенанс наравне с весами** — «кем, когда и
каким ядром сделан», с ответами в выходной таблице. Артефакт без провенанса —
тот же молчаливый no-op, только этажом выше. Отчёты, снятые до починки, не
переделываются; пробы manual-кейсов после затирания помечены в отчёте
LightGlue как восстановленные из `regress.csv`.

иначе откалиброванную величину, — теперь с двумя порогами разом, причём

снятых порогах** — до любых выводов о качестве.

certainty_cover v1). Остаток направления: `precision_median` — диагностика в
отчёте (уже есть); повторить эксперимент имеет смысл, только если проект
перейдёт на эпиполярную оценку (рельеф, наклонная съёмка). Разбор —

## 2026-07-29 — «0 ложных» верно ТОЛЬКО внутри конверта приора: контрольный замер

**Что.** Продолжение разбора `DRZ_06262` (90 м AGL, отпечаток 124 м). Владелец
попросил прогнать с σ = 1.5 км и **уточнённым центром**. Центр взят в 247 м от
истины — то есть заведомо внутри района, ретривал имел верную клетку в доступе.

**Результат — контрольная пара, где менялась только σ:**

| центр от истины | σ | клеток | статус | ошибка |
|---|---|---|---|---|
| 247 м | **0.5 км** (по регламенту) | 484 | ЛОКАЛИЗОВАНО | **1.2 м** ✓ |
| 247 м | 1.5 км (втрое шире) | 5184 | ЛОКАЛИЗОВАНО | **1883 м — ЛОЖНОЕ** |

Связка пропустила ложную позу с запасом: 268 инлайеров при пороге 185, dino 0.437
при пороге 0.35, эллипс 0.04 м. `certainty_cover` = 0.0, но он, как показано ниже,
разделяющей способности не имеет.

**Зачем это принципиально.** До сих пор считалось, что выход за конверт приора
стоит **отказов**: место тонет среди похожих, поза не собирается, гейт молчит.
Замер показывает иное: за конвертом появляются **уверенно-неверные точки** — самый
дорогой из исходов по шкале проекта. Разница между «система не найдёт» и «система
соврёт» принципиальная, и раньше она была сформулирована неверно.

**Следствие: главный результат проекта переформулирован.** «16/16 поз, 0 ложных»,
а затем «30/30, 0 ложных» — верно, но только **внутри регламента «высота → σ»**,
по которому и построен стенд. Стенд задаёт радиус района из приора кейса, то есть
нарушения конверта он не проверяет **никогда**. Это дыра в измерении, а не в
формулировке: гарантия существовала, но её границы не были ни измерены, ни
записаны.

**Следствие 2: это же объясняет обе сегодняшние ложные точки на одном кадре.**

| центр | σ | что произошло |
|---|---|---|
| 777 м | 1.5 км | верный отказ — 972 м |
| 777 м | 0.45 км | ложное 960 м: истина ВНЕ карты (радиус 675 м < 777 м) |

## 2026-07-29 — σ — это обещание, а не ручка: как совет «сузьте приор» породил ложную точку

**Что.** Владелец запустил `DRZ_06262` с приором 51.21/6.16 и σ = 1.5 км. Получил
НИЗКОЕ ДОВЕРИЕ. Инструмент при этом напечатал совет сузить приор — и следование
этому совету **превратило верный отказ в ложное срабатывание**.

| запуск | статус | ошибка |
|---|---|---|
| σ = 1.5 км (владелец) | НИЗКОЕ ДОВЕРИЕ | 972 м — **верный отказ** |
| σ = 0.45 км (по совету) | ЛОКАЛИЗОВАНО | **960 м — ЛОЖНОЕ** |

**Причина.** Центр приора отстоял от истины на **777 м**, а район строится
радиусом 1.5σ, то есть при σ = 450 м всего 675 м. Сужение вынесло верное место за
пределы карты: система искала там, где ответа не было в принципе, нашла похожее
место (240 инлайеров, dino 0.446) и связка его пропустила.

**Первый дефект — в самом совете.** Ориентир считался как
`recommended_sigma_m(altitude)`, а владелец задал `--gsd`, отчего высота осталась
подставной (500 м). Регламент по выдумке выдал **4 км** — то есть совет предлагал
приор **расширить** там, где надо сужать. Лечится тем, что ориентир теперь
считается из **числа клеток** (`sigma_for_cells`, клеток ∝ σ²): величина известна
точно и допущений не содержит. Проверено: 1500 м при 5625 клетках → 447 м, что
сходится с регламентом (500 м), но без единого предположения о высоте.

**Второй дефект — принципиальнее, и он в формулировке.** Совет трактовал σ как
ручку производительности: «клеток много — сузьте». Но σ — это **утверждение о
знании**: «центр верен с такой точностью». Сузить σ под неверным центром значит
солгать системе, и защита пропадает — приор ведь ограничение, а не подсказка.
Совет переписан: сужать допустимо, **только если уверен в центре**; если центр
неточен, лечится не σ, а центром.

**Проверенная и отвергнутая гипотеза: `certainty_cover` как страховка.** У ложной
позы `certainty_cover = 0.0` — RoMa прямо говорила «перекрытия нет». Соблазнительно
добавить сигнал в связку. Замер по 30 кейсам это закрывает:

| | n | min | p10 | медиана |
|---|---|---|---|---|
| верные | 26 | **0.00000** | 0.00005 | 0.00564 |
| неверные | 4 | 0.00000 | 0.00000 | 0.00016 |

Верные локализации доходят до нуля: `DRZ_06498` — **6.5 м при cover 0.00003**,
`DRZ_03149` — верная поза при ровно 0.0. Разделяющей способности нет; порог вырезал
бы верные вместе с ложными. Сигнал остаётся диагностикой, в связку не идёт.

**Следствие.** Связка качества **не тронута**: она отработала ровно так, как
устроена, — при неверном приоре уверенно-неверная точка возможна, это записанная
граница, а не новый баг. Изменены совет и документация. Золото не затронуто:
ложное срабатывание получено на приоре владельца, а не на конфигурации стенда.

**Урок.** Совет, выданный инструментом, — такая же часть продукта, как число на
выходе, и ошибиться в нём можно ровно так же дорого. Этот совет был хуже
молчания: он звучал авторитетно, опирался на подставное число и вёл к худшему из
исходов, какие у проекта есть.

## 2026-07-29 — Конверт приора подтверждён замером; целостность кэша тайлов

**Что.** Владелец запустил `test_images/DRZ/DRZ_00755.JPG` (Германия, 90 м AGL,
GSD 3 см), задав приором **секунды** из EXIF-тройки — `58.37 / 9.306` вместо
`51°12'58.37" / 6°10'9.31"` = `51.21621 / 6.16925`. Поиск ушёл в Скагеррак.
Инструмент отказал за секунды с причиной «нет съёмки в этом районе» — проба,
добавленная часом раньше, окупилась сразу. Тайл в точке: ровная синева, std 0.0;
в 40 км севернее, у берега, тот же цвет уже со std 19.

**Зачем.** Разбор дал две вещи ценнее самой опечатки.

**Результат 1: конверт приора подтверждён на границе.** Регламент «высота →
допустимая σ» (веха от 2026-07-27) выводился аналитически и на низком узле не
проверялся. Замер на независимой сцене:

| приор | клеток | уникальность | инлайеров | `certainty_cover` | dino | исход |
|---|---|---|---|---|---|---|
| ±2 км (вчетверо за конвертом) | 10 000 | 0.0092 | 129 | 0.000 | 0.390 | отказ, истина в 2275 м |
| ±0.5 км (по регламенту) | 625 | 0.0320 | 1089 | 0.015 | 0.506 | **1.7 м** |

Узкое место — Этаж 1, не матчер: отпечаток 120×90 м режет район ±3 км на десять
тысяч почти одинаковых пригородных клеток. Сборка карты заодно упала с 12 минут
до 13 секунд. **Третий раз подряд dino прошёл порог на заведомо неверном месте**
(0.390 при пороге 0.35) — отвергла геометрия; довод против ослабления связки до
одного сигнала копится.

**Результат 2: четыре дефекта кэша тайлов.** Первая сборка умерла на ассерте
OpenCV `!buf.empty()`, потеряв 12 минут. Воспроизвести не удалось, но разбор
вскрыл: неатомарную запись (`write_bytes` сначала обрезает файл); `get`,
возвращавший `b""` как данные — одна пустышка травила бы район навсегда; стек
`imgcodecs` вместо внятной причины; отсутствие повтора — один битый тайл убивал
всю сборку.

**Отдельная находка.** Очевидная правка — атомарная запись через `os.replace` —
**сама оказалась хуже болезни**: на Windows при одновременном чтении падают
**228 из 300** подмен и 115 чтений (измерено). Показал это собственный тест на
гонку, повесив прогон насмерть: писавший поток умирал от `PermissionError` и не
снимал флаг остановки. Верным оказалось не переписывать готовый тайл вовсе —
`(z, x, y)` есть неизменяемое содержимое, и класс гонок убирается целиком, а не
смягчается.

**Следствие.**

- Конверт приора получил эмпирическое подтверждение; в USAGE узкий приор для
  низких высот назван прямо, а не оставлен читателю.
- Кэш тайлов: пустой файл — промах, готовый тайл неприкосновенен, битый
  перекачивается ровно один раз, чтение терпит `PermissionError` как промах.
- `DRZ/` — кандидат на расширение тестового набора: независимый регион, низкая
  высота, истина из EXIF. Решение за владельцем, золото молча не трогаем.

## 2026-07-29 — «Тайл есть, съёмки нет»: подложка как источник уверенно-неверной позы

**Что.** Владелец запустил инструмент на `DSC00045` с приблизительным приором и
получил НИЗКОЕ ДОВЕРИЕ при пустой второй панели оверлея. Разбор показал, что
пусто там не из-за отрисовки: в точке 56.77/52.78 Esri на z19 отдаёт **HTTP 200 и
серую заглушку** вместо снимка — 60 из 60 проверенных тайлов района. Кадр с GSD
6.5 см запросил самый детальный уровень пирамиды, получил чистый лист и был
честно с ним сопоставлен.

**Зачем это принципиально.** `max_zoom` провайдера — предел **пирамиды**, а не
гарантия покрытия. Пайплайн этого не различал, и получался худший вид отказа:
подложка формально получена, все стадии отработали без ошибок, поза построена — а
смысла у неё нет. Инвариант «честный отказ дороже красивой точки» здесь нарушался
не в логике решения, а **на входе в неё**.

**Результат (числа).**

| | z19 (что было) | z18 (после спуска) |
|---|---|---|
| подложка | заглушка | настоящая съёмка |
| dino | 0.145 | **0.416** — порог 0.35 прошла |
| инлайеров | 22 / 1920 | 54 / 1165 |
| `certainty_cover` | 0.003 | 0.0 |
| исход | НИЗКОЕ ДОВЕРИЕ | НИЗКОЕ ДОВЕРИЕ |

Побочное наблюдение, важнее самого бага: **dino прошёл порог на заведомо неверном
месте**. Обе картинки — «типичная деревня сверху», и семантический сигнал на это
купился; отвергла позу геометрия. Аргумент против ослабления связки до одного
сигнала.

**Чем ловить — и чем нельзя.** Измерено по кэшу проекта (3000 случайных тайлов):
у заглушки std 5.4, у настоящей съёмки медиана 29, но **минимум 3.0 и первый
процентиль 4.8** (вода, тёмный лес). Порог по дисперсии в одиночку эти случаи не
разделяет. Зато все 166 попавшихся заглушек оказались **байт-идентичны** — две
настоящие съёмочные плитки так совпасть не могут. Отсюда два независимых признака
пустоты (байтовое равенство ∨ отсутствие структуры) и вывод по **набору** из
девяти проб — центр района плюс кольцо по краю, чтобы озеро в центре не осудило
весь район.

**Следствие.**

- `basemap.probe_imagery` / `deepest_imagery_zoom`; инструмент проверяет уровень
  **до** сборки карты района (девять тайлов против минут работы по пустоте) и сам
  спускается. Съёмки нет во всём диапазоне до z14 — честный отказ с этой причиной.
- Там, где съёмка есть, не меняется ничего: проверено на реальном кэше — Ижевск
  19 → 18, Волгоград остаётся на 19.
- Эллипс ошибки убран у непринятой позы. «ellipse: 0.45 m» рядом со словом
  `low_confidence` читается как «зато очень точно», хотя это разброс подгонки,
  проверку не прошедшей.
- Флаг `--max-zoom` для ручного потолка.
- Место `DSC00045` не найдено и после спуска — шахматка рвётся на границах клеток.
  Отказ верен, но теперь по существу, а не из-за пустой подложки.

**Урок.** Третий раз за трек живой запуск нашёл то, чего не видели зелёные тесты
(до этого: боевой сигнал качества вместо библиотечного дефолта; сводка по пачке).
И снова дефект был **на стыке** — между тем, что провайдер обещает, и тем, что
отдаёт. Тесты проверяют наши инварианты; чужие обещания проверяет только прогон.

## 2026-07-29 — Инструмент владельца: снимок и координаты → отчёт с картой

**Что.** Развитие ядра приостановлено; сделан инструмент, которым владелец сам
запускает локализацию и оценивает результат глазами. Одна команда:

```bash
scripts/locate.py --image DJI_0123.JPG --lat 54.81 --lon 56.09 --sigma-km 1.5
```

На выходе `report.html` (открыть двойным кликом), `overlay.png`, `result.json`,
`footprint.kml` для Google Earth и `.geojson` для QGIS. Инструкция —
[USAGE.md](USAGE.md), план — [TOOL_PLAN.md](TOOL_PLAN.md), все шесть этапов
закрыты.

**Главное содержание работы — не новый код, а сборка готового.** Пайплайн,
`Camera.from_gsd`, чтение EXIF/XMP, оверлей на четыре панели и кэш карты района
уже существовали, но были разложены по скриптам оценки. Ядро не тронуто:
регрессия 16/16.

**Три решения, принятые ради честности, а не удобства.**

1. **GPS из EXIF не подставляется в приор молча.** Если взять координаты снимка
   как приор и «найти» его рядом с ними, проверка ничего не доказывает — система
   искала там, куда ей же и указали. Нужен явный `--from-exif`, и тогда отчёт
   помечает результат как НЕ независимую проверку.
2. **Отказ формирует такой же полноценный отчёт, как успех**, с причиной и
   советом, выведенным из этой причины. Без этого владелец читает `NOT_LOCALIZED`
   как поломку.
3. **Отпечаток кадра в метрах печатается до запуска.** Неверный GSD — самая
   частая ошибка ввода, и она даёт не отказ, а уверенно-неверный масштаб. «Кадр
   покрывает 517 × 345 м» — единственное место, где это видно сразу.

**Оверлей поймал настоящую ошибку на первом же запуске.** В шапке стояло `ncc`, а
не `dino`: инструмент шёл на **библиотечном** дефолте сигнала качества вместо
боевого, то есть владелец получил бы не ту конфигурацию, на которой заморожено
золото. Ошибка была видна только глазами, на картинке — ровно то, ради чего
оверлей и делается.

**Проверено на реальных снимках.** `Volgograd3`: локализован, 1.2 м против
истины, 423 инлайера, марина с понтонами узнаётся с первого взгляда. `Ufa2`:
гейт отверг позу — и отверг **верно**, она была в 1164 м от истины; отчёт при
этом полноценный.

**Побочно устранены два дублирования**, каждое из которых уже имело историю
расхождений: геометрия карты района (была в приватных функциях харнесса → 
`aero_geoloc/region.py`) и приведение кадра к разрешению подложки (было написано
дважды, понадобилось бы трижды → `camera.resample_to_mpp`).

**Честно помечено то, что не работает.** Флаг `--no-index` (поиск окном вместо
карты района) остался с синтетического стенда и на реальных кадрах не
подтверждён: `Volgograd3` отказывает при любом ядре и любом приоре. Это написано
и в справке флага, и в USAGE — вместо того чтобы выдавать его за равноценный путь.

Кросс-сезон считался известной границей.

| трек | результат |

### Главный содержательный вывод

**Целевое дообучение на инвариантность вида решает здесь больше, чем сила общего
матчера.** Получено на трёх независимых парах одинаковых архитектур с разным
обучением, две из трёх — с разрывом в порядки. Направление «искать ядро
посильнее» этим и исчерпано: дальше либо дообучение под наш домен, либо смена
данных (подложка под сезон кадра).

### Чему сессия научила про метод

Половина заходов дала **отрицательный результат**, и это оказалось не потерей, а
основным способом продвижения. Но заметить их удалось только потому, что каждый
замер сверялся с чем-то независимым:

1. **Числа, попадающие в вывод, надо считать, а не прикидывать.** Дважды получил
   неверный размер окна точного уровня «в уме» (2700 «по полклетки» — случайно
   верно; 1733 «по 0.15·footprint» — неверно). Настоящие 2666 px увидены только
   дампом того, что реально подаётся матчеру. Оба раза работа уходила не туда.
2. **Молчаливый откат опаснее падения.** `load_state_dict(strict=False)` стерпел
   бы любое несовпадение имён, и A/B сообщил бы «кандидат не помог» про кандидата,
   которого в вычислении не было. Счётчик совпавших тензоров поймал GIM-LoFTR.
3. **Правдоподобное объяснение — не доказательство.** Гипотеза «плотная сетка
   заполняет top-K копиями одного места» звучала убедительно и оказалась неверной:
   при o = 0.79 шаг сетки больше запаса окна, соседние клетки дают разные окна.
4. **Сторож окупился на первой же самопроверке**, поймав нестабильность
   `Volgograd4` вокруг порога плотного ядра. Без него она бы всплыла через месяц
   как «регрессия непонятно откуда».
5. **Инвариант выдержал.** Семь полных замен ядра матчинга, замена сигнала
   качества, смена геометрии — **ни одного ложного срабатывания** ни в одной
   конфигурации, кроме той, где плотное ядро пришло со старым порогом инлайеров;
   там его поймал прогон, и порог был перекалиброван.

### Что осталось честно открытым

* `Ufa2` не берёт ни одно из семи ядер: соответствия есть, подобия нет.
* Кросс-сезонных кадров в наборе **два**, одной сцены. Вывод остаётся
  направлением, а не доказательством.
* Порог плотного ядра (185) стоит в **13 инлайерах** от ложных поз.
* Известный дефект передачи Этаж 1 → Этаж 2: запас окна берётся как «полклетки» и
  не зависит от перекрытия сетки. Лечение измерено и **не принято** (10/16 против
  11/16, нестабильно).

## 2026-07-29 — База переведена на MINIMA-RoMa

**Что.** По решению владельца ядром по умолчанию стал `minima_roma`; золото
перезаморожено на нём. Прежняя база — `lightglue` — остаётся доступной одним
флагом и никуда не делась.

**На чём заморожено.** Прогон на **дефолтных** параметрах (радиус 1.5 км, top-K
15, `min_inliers` 6, сигнал качества `dino`) — специально без подбора под лучший
результат:

| | было (LightGlue) | стало (MINIMA-RoMa) |
|---|---|---|
| поз найдено | 11/16 | **16/16** |
| принято гейтом | 11/16 | **13/16** (в золоте 12 — см. ниже про `Volgograd4`) |
| верных мест | 11 | **13** |
| **ложных** | **0** | **0** |
| медиана ошибки | 8.8 м | 8.4 м |
| онлайн, медиана | 8.4 с | 24.5 с |

Дифф против прежнего золота: **+2 улучшения, 0 регрессий** — `Ufa3` (отказ → 4.9 м,
кросс-сезон) и `Volgograd` (отказ → 124.3 м). Три непринятых кейса — `Ufa2`,
`Ufa_sample1`, `train_SB_0023` — гейт отверг **верно**: у всех троих поза
неверная, и это ровно та работа, ради которой связка существует.

**Что это стоит.** Три вещи, которые надо знать до того, как они удивят:

1. **Втрое дороже по времени**: ~24 с на кадр против 8.4 с. Для одиночного кадра
   приемлемо, для потока — нет.
2. **Сторож регрессии теперь требует тяжёлых зависимостей**: `romatch`, веса
   MINIMA-RoMa (445 МБ) и DINOv2 ViT-L (1.13 ГБ). Раньше он ходил на
   `lightglue`. Кто хочет лёгкую проверку — `--matcher lightglue`, но тогда это
   другая конфигурация, и сторож честно откажется выдавать вердикт.
3. **Порог инлайеров плотного ядра держится на тонком запасе — и это уже
   сработало.** `Volgograd4` прошёл с 191 инлайером при пороге 185, а на
   повторном прогоне тех же настроек **не прошёл**. Ложные позы в замере давали
   ≤178: между ними и верной позой 13 инлайеров, и RANSAC этот зазор
   перешагивает.

   Поймал это сам сторож на первой же самопроверке — ради таких случаев он и
   делался. `Volgograd4` заморожен по **пессимистичному** исходу («гейт отверг
   верную»): тогда удачный прогон показывает улучшение, а не ложную регрессию, и
   при этом настоящая деградация ниже этого уровня по-прежнему видна. Повторная
   проверка после перезаморозки прошла чисто.

   Заодно уточнён сам сторож: у позы, которую гейт **правильно** отверг как
   неверную, «ошибка» — это расстояние до истины у заведомо чужого места, и
   сравнивать её между прогонами бессмысленно. Раньше такое сравнение давало
   шумное предупреждение (`Ufa2`: 1071 → 1632 м).

**Почему всё-таки переключено.** Ложных срабатываний ноль, а полнота выше на два
кейса, включая первый в истории проекта кросс-сезонный кадр. Для сервиса, чья
заявленная ценность — честная локализация одиночного снимка, полнота важнее
времени; выбор сделан владельцем осознанно и с этими числами на руках.

## 2026-07-29 — RoMa v2 на замороженном DINOv3: не переносится на наш домен

> **НЕВАЛИДНА в части чисел (2026-08-21).** Все замеры вехи шли через фильтр
> `min_conf = 0.5` от v1, тогда как `overlap` v2 живёт в сотых — модель не была
> измерена. Действительная картина — в вехе от 2026-08-21 и в
> `RESEARCH_A_RESULTS.md` §7. Веха сохранена как есть: ловушка ценнее вывода.

**Что.** Проверено направление, которое владелец просил проверить направленно, и
которому обзор трека A давал сильнейший априор. `RoMaV2Matcher` подключён за тем
же интерфейсом (`create_matcher("romav2")`). **Результат отрицательный и не
пограничный**: на парах, где MINIMA-RoMa даёт ~2000 соответствий и сотни
инлайеров, RoMa v2 даёт 0–29 соответствий и ни одной позы.

**Доступ оказался проще, чем ожидалось.** Риск «упереться не в код, а в доступ»
не реализовался: `romav2` тянет один чекпоинт (~1.02 ГБ) из релиза
MIT-лицензированного репозитория `Parskatt/RoMaV2`, и **замороженный DINOv3 лежит
внутри него** — gated-репозиторий Meta на HuggingFace (`gated=manual`) не нужен.
Юридическую оговорку всё же записываю: код под MIT, а веса бэкбона остаются под
собственной лицензией Meta, и для проприетарного использования это отдельный
вопрос.

**Интеграция проверена и исправна.** На контрольной паре (шум со сдвигом) RoMa v2
даёт 2048 пар, сдвиг восстановлен точно, медиана `overlap` 0.97. То есть код
работает, и отрицательный результат ниже — про домен, а не про обёртку.

**Замер.** Оракульные пары, порог инлайеров 8:

| кейс | RoMa v2: соотв. / инлайеры | MINIMA-RoMa: соотв. / инлайеры / ошибка |
|---|---|---|
| `00049` | 8 / позы нет | 1860 / 283 / 8.4 м |
| `Ufa3` | **0** / позы нет | 2035 / 1334 / 5.2 м |
| `Saratov` | 29 / позы нет | 2022 / 613 / 2.3 м |
| `Volgograd3` | **0** / позы нет | 2041 / 775 / 3.7 м |

**Сигнал уверенности тоже не работает.** Без фильтра по уверенности RoMa v2
возвращает свои 2048 пар, но `overlap` у них 0.03–0.08 — и, что решает вопрос,
**у чужого места выше, чем у верного** (`Ufa3`: 0.053 верная против 0.082
ложная). Это не «мало уверенности», это отсутствие сигнала.

**Проверена и отвергнута очевидная гипотеза про цвет.** DINOv3 обучен на цветных
изображениях, а мы подаём grayscale — казалось бы, вот и причина. Подача
настоящего цвета (кадр и подложка как есть) делает **хуже**: `Ufa3` 0.010 против
0.057 на сером, `Saratov` 0.010 против 0.027. И в обоих режимах чужая пара
остаётся выше верной. Так что «решение про RGB» из плана здесь ни при чём.

**Вывод.** RoMa v2 — более сильный матчер *в своём домене*, но он не дообучен под
кросс-модальность, а наш домен именно такой: надирный кадр БПЛА против спутниковой
подложки, снятой в другой сезон, другим сенсором и с другой обработкой. Это
третье подряд подтверждение одного и того же правила на этом наборе:

* MINIMA-LightGlue (173 инлайера на `Ufa3`) > GIM-LightGlue (2 соотв.) > LightGlue (6);
* MINIMA-RoMa (1334) ≫ RoMa v2 (0).

**Целевое дообучение на инвариантность вида решает здесь больше, чем сила общего
матчера.** Это и есть главный вывод трека A, и он получен на трёх независимых
парах кандидатов.

**Следствие для плана.** Направление «сильнее общий матчер» исчерпано: проверены
LoFTR, GIM, MINIMA-LightGlue, MINIMA-LoFTR, MINIMA-RoMa, RoMa v2. Победитель —
`minima_roma`. Дальше имеет смысл не искать ещё более сильное ядро, а
**дообучать под наш домен** (та самая линия MINIMA, но на наших данных) либо
менять данные — подложку под сезон кадра. Код `RoMaV2Matcher` оставлен в реестре:
отрицательный результат должен быть воспроизводим одной командой.

## 2026-07-29 — certainty от RoMa: проведена до гейта, в решение не взята

**Что.** Плотная уверенность RoMa доведена до связки качества и попадает в
диагностику и CSV. В **решение** она не входит — замер показал, что она сужает
запас гейта, а не расширяет.

**Как она вообще сюда попала.** У `Correspondences` появилось поле `evidence` —
свидетельства уровня **всей пары картинок**, а не отдельных точек. Оно понадобилось
потому, что не всё, что знает матчер, ложится на точки: плотное ядро оценивает
уверенность по всему полю, и доля уверенной площади — свойство пары. У разреженных
ядер поле пустое, и это штатный случай.

**Первая попытка не дала ничего, и это важно.** `Correspondences.conf`, который
RoMa возвращает из `sample`, оказался **константой 1.0000** — на верных и на
заведомо чужих парах одинаково. Причина в самом `romatch`: режим сэмплирования
содержит `threshold`, и он обрезает всё выше порога в единицу. Сигнал живёт в
плотном поле **до** сэмплирования, поэтому сводка снимается там: `certainty_mean`
и `certainty_cover` (доля пикселей выше 0.5).

**Сигнал есть — но не там, где нужен гейту.** На произвольных парах окон он
разделяет на порядок:

| кейс | верная пара (mean / cover) | окно в 1.5 км (mean / cover) |
|---|---|---|
| `Ufa3` | 0.349 / 0.312 | 0.049 / 0.0002 |
| `Volgograd3` | 0.233 / 0.094 | 0.007 / 0.0000 |
| `Saratov` | 0.143 / 0.025 | 0.007 / 0.0000 |
| `Ufa2` | 0.110 / 0.026 | 0.012 / 0.0000 |

А вот **среди поз, которые уже собрались**, — перекрывается. На 15 верных и 27
ложных позах:

| сигнал | верные min | ложные max | запас | |
|---|---|---|---|---|
| **`n_inliers`** | **283** | **168** | **1.68×** | разделяет |
| `certainty_mean` | 0.0252 | 0.0708 | — | перекрытие |
| `certainty_cover` | 0.0000 | 0.0026 | — | перекрытие |
| `n_inliers × cover` | 0.0000 | 0.2558 | — | перекрытие |
| `n_inliers × mean` | 7.12 | 6.94 | 1.03× | хуже счётчика |
| `inlier_ratio × mean` | 0.0038 | 0.0035 | 1.08× | хуже счётчика |

**Вывод, который я не собирался получать: в связку её брать нельзя.** Любая
комбинация с certainty **сужает** запас гейта (1.68× → 1.03–1.08×) или ломает
разделение вовсе. Объяснение простое и, задним числом, очевидное: ложные позы
собираются как раз там, где RoMa нашла *хоть какую-то* согласованную структуру, —
то есть где certainty и так повышена. Условие «уверенность высокая» у них
выполнено, а различает их только то, **сколько** точек уложилось в подобие.

**Где её место на самом деле.** Она отделяет пары окон, которые вообще стоит
матчить, от безнадёжных — на порядок, ещё **до** дорогого точного прохода. Это
рычаг скорости (веер top-K сейчас гоняет плотное ядро по всем кандидатам, 22–30 с
на кадр), а не качества. Отдельная работа, и теперь для неё есть измеренные числа.

**Побочно найден и исправлен тихий дефект.** Свидетельства пропадали у половины
кейсов: `_match_prerotated` пересобирал `Correspondences` после предповорота и
терял `evidence` — ровно у тех кадров, где известен курс. Диагностика молча
исчезала там, где её как раз ждали. Перенос закреплён тестами
(`tests/test_evidence.py`) для всех трёх мест, где соответствия пересобираются:
фильтрация точек, предповорот, обёртка рабочего разрешения.

**Заодно уточнён результат RoMa.** Прогон с `--min-inliers 8`: **16/16 поз
найдено, 13/16 принято, все 13 верны, 0 ложных** — на два больше золота, включая
кросс-сезонный `Ufa3` (5.0 м). Гейт не отверг ни одной верной локализации.

## 2026-07-29 — MINIMA-RoMa: кросс-сезон взят сквозным пайплайном

**Что.** Фаза 3 из [ROADMAP.md](ROADMAP.md): плотный матчер за тем же интерфейсом
`Matcher`. `RoMaMatcher` (`aero_geoloc/matcher.py`) поверх пакета `romatch` с
весами MINIMA — `create_matcher("minima_roma")`, всё выше матчера не меняется.

**Зачем именно плотный.** У разреженных ядер на смене сезона рассыпается
**повторяемость ключевых точек**. Плотное поле повторять нечего: RoMa предсказывает
warp и попиксельную certainty, а разреженные пары получаются сэмплированием.
Побочно приходит та самая certainty, которую обзор направления B предлагал как
сигнал качества, — она доходит до `quality.assess` в `Correspondences.conf`.

**Интеграция.** Веса `minima_roma.pth` (445 МБ, Apache-2.0) легли **603/603
тензора**. В чекпоинте только обучаемая часть (`encoder.cnn` + `decoder`);
замороженный DINOv2 ViT-L (1.13 ГБ) `romatch` тянет отдельно — так задумано
авторами RoMa, и это же объясняет «всего 445 МБ». На Windows нет
`fused-local-corr`, `romatch` сам переключается на обычную корреляцию.
Зависимости ставились `--no-deps`: штатный список тянет `opencv-python`, который
конфликтует с нужным проекту `opencv-contrib-python` (AKAZE живёт в `xfeatures2d`).

**Первый замер — критерий отсева трека A.** Оракульная проба, `Ufa3`:

| матчер | соответствий | инлайеров | ошибка |
|---|---|---|---|
| LightGlue (база) | 24 | 6 | — |
| MINIMA-LightGlue | 242 | 173 | 4.9 м |
| **MINIMA-RoMa** | **2037** | **1437** | **5.1 м** |

**Сквозной прогон вскрыл вторую половину задачи.** Первый прогон: 16/16 поз
найдено (**ни одного отказа Этажа 2**), но **два ложных срабатывания** —
`Ufa2` принят с ошибкой 1632 м, `Ufa_sample1` с 594 м. Плотное ядро на любой паре
картинок даёт сотни «инлайеров»: они укладываются в подобие просто потому, что
поле гладкое. **Порог `MIN_INLIERS_HARD = 8` для него не значит ничего.**

Перекалибровка на 15 верных и 28 ложных позах (`scripts/e2_geometry.py`):
`n_inliers` разделяет **идеально** (AUC 1.000 в обоих режимах), у верных ≥ 234, у
ложных ≤ 178. Введён `MIN_INLIERS_DENSE = 185`, и порог стал **свойством ядра**
(`localize.hard_inlier_threshold`): признак плотного ядра — наличие бюджета
сэмплов, а не имя класса, чтобы следующее плотное ядро попало в нужную ветку само.

**Результат.**

| | золото (LightGlue) | MINIMA-RoMa |
|---|---|---|
| поз найдено | 11/16 | **16/16** |
| принято гейтом | 11/16 | **12/16** |
| верных мест | 11 | **12** |
| **ложных** | **0** | **0** |
| медиана ошибки | 8.8 м | 8.9 м |
| онлайн, медиана | 8.5 с | 29.7 с |

Поимённо: **`Ufa3` — 5.0 м, первый кросс-сезонный кадр, взятый сквозным
пайплайном за всю историю проекта**; `Volgograd` — 124.2 м (верно). Цена: гейт
отверг верный `Volgograd4` со 180 инлайерами при пороге 185 — это отказ, а не
ложная точка.

**Три оговорки, которые нельзя опускать.**

1. **Запас порога тонкий: 178 против 195.** Он держится на одном наборе и двух
   ложных срабатываниях. При пополнении данных пересчитать, а не унаследовать.
2. **`Ufa2` по-прежнему не взят.** RoMa даёт на нём 1976 соответствий, но они не
   складываются в подобие: это не «мало данных», а несогласованные данные. Из двух
   кросс-сезонных кадров взят один.
3. **Втрое дороже по времени** (29.7 с против 8.5 с). Для одиночного кадра
   приемлемо, для потока — нет; это довод держать оба ядра, а не заменять одно
   другим.

**Что это меняет в картине.** Впервые за проект вина Этажа 2 обнулилась: 16/16
поз найдено, отказов по «поза не сошлась» нет вовсе. Узкое место переехало на
**связку качества** — теперь она решает всё, и именно её пороги стоили и двух
ложных, и одного отвергнутого верного. Это ровно тот трек B, который до сих пор
был вторичным.

## 2026-07-29 — Передача Этаж 1 → Этаж 2: причина найдена, лечение пока хуже болезни

**Что.** Найдена настоящая причина, по которой кросс-сезонный кадр не проходил
пайплайн, и она **не в матчере и не в размере окна как таковом**. Лечение
реализовано, измерено на всём наборе и **не принято**: даёт 10/16 вместо 11/16.
Код возвращён в проверенное состояние (регрессия 16/16), находка записана здесь.

**Как нашли.** Перехват точного уровня на каждом кандидате `Ufa3` показал
кандидат в **20 м от истины с нулём соответствий** — при том, что оракульная
проба на тех же 20 м давала 76 соответствий и 18 инлайеров. Значит дело во
входе. Дамп того, что реально подаётся матчеру: окно подложки **2666 px**, а не
1733, как я насчитал вехой ранее.

**Причина.** Запас окна считается как `max(6·coarse_mpp, 0.15·footprint)`, а
`coarse_mpp` для retrieval-пути равен `cell_footprint/12`. То есть
`6·coarse_mpp = cell/2` — **полклетки, независимо от перекрытия сетки**.
Комментарий в коде честно это и говорил: «истинный центр может лежать где угодно
в клетке». Но при перекрытии `o` ближайший центр клетки отстоит не на полклетки,
а на `0.707·(1−o)·cell`. Запас **никогда не узнаёт про перекрытие**, поэтому:

* при o = 0.5 он завышен вдвое (114 м вместо 81) — окно 2666 px вместо 2278;
* при любом уплотнении сетки окно **не сужается вообще**.

Отсюда и провал прошлой проверки уплотнения: она меняла одну половину связки, а
вторая держала окно широким. А широкое окно измеренно разваливает кросс-сезон:
`Ufa3` при 1733 px даёт 35 инлайеров, при 2000 px — 2 соответствия.

**Лечение и его цена.** Связка замкнута: индекс запоминает своё перекрытие,
кандидат несёт `0.707·(1−o)·cell` как неопределённость положения, окно строится
из неё, а требуемое перекрытие выводится обратно из штатной ширины окна
(`0.707·(1−o) ≤ 0.15` ⟹ `o ≥ 0.79`). Геометрия становится согласованной: окно
всегда 1.30 отпечатка, промах клетки всегда меньше запаса.

**Первый результат был тем, ради чего всё делалось: `Ufa3` локализован сквозным
пайплайном — 84 инлайера, ошибка 5.3 м.** Первый кросс-сезонный кадр за всю
историю проекта.

Но полный прогон это не подтвердил:

| | золото (LightGlue) | нов. геометрия, LightGlue | нов. геометрия, MINIMA |
|---|---|---|---|
| принято | **11/16** | 10/16 | 10/16 |
| ложных | 0 | 0 | 0 |
| `Volgograd3` | 4.1 м | отказ | отказ |
| `Ufa_sample4` | 4.7 м | отказ | отказ |
| `Volgograd` | отказ | **123.2 м** | **125.2 м** |
| `Ufa3` | отказ | отказ | отказ (в изолированном прогоне — **5.3 м**) |

**Две причины не принимать.** Во-первых, сквозной размен отрицательный: два
кейса потеряны, один приобретён. Во-вторых — и это важнее — **`Ufa3`
локализовался в изолированном прогоне и отказал в полном при тех же
параметрах**. Нестабильность на границе принятия хуже, чем стабильный отказ:
пока она не объяснена, числу нельзя верить ни в ту, ни в другую сторону.

**Проверенная и отвергнутая по дороге гипотеза.** Предположение, что плотная
сетка заполняет top-K копиями одного места и лечится пространственным
подавлением кандидатов, — **неверно**. При o = 0.79 шаг сетки 48 м больше запаса
окна 34 м: соседние клетки уже дают **разные** окна, а не дубликаты.
Реализованное подавление ухудшило Recall@5 (0.88 против 0.90) и откачено.

**Что остаётся знать следующему.**

1. Запас окна и перекрытие сетки связаны, и связь **разомкнута в коде**: запас
   берётся как полклетки и не зависит от плотности. Это дефект, а не решение.
2. Замыкание связки даёт согласованную геометрию (окно 1.30 отпечатка) и на
   кросс-сезоне однажды сработало (5.3 м), но теряет два кейса и нестабильно.
3. Третья нога связки — **не** подавление кандидатов, а что-то в ранжировании
   Этажа 1 на плотной сетке: `Volgograd3` уходит в вину Этажа 1, хотя клетка в
   индексе есть.
4. Ловушка, стоившая двух заходов: **размер окна надо смотреть в дампе, а не
   считать по формуле в уме**. Я дважды получил неверное число (2700 «по
   полклетки» — случайно верное; 1733 «по 0.15·footprint» — неверное), и оба раза
   вывод шёл не туда. Настоящее число — 2666 px — увидено только перехватом
   входа матчера.

## 2026-07-29 — Окно точного уровня: гипотеза проверена целиком и отвергнута

**Что.** Задача звучала как «подогнать окно точного уровня под предел MINIMA».
Проверено — и **предел окна оказался не при чём**. Настоящая связка тройная:
запас окна ↔ плотность сетки ↔ `top_k`, и трогать первые две без третьей нельзя.

**Как выяснилось.** Прежняя веха оценивала окно пайплайна для Уфы в ~2700 px «по
полклетки» — это была прикидка, а не расчёт. Фактическое окно считается как
`footprint + 2·margin`, где `margin = max(6·coarse_mpp, 0.15·footprint)`, и для
`Ufa3` даёт **1733 px**. На нём MINIMA-LightGlue выдаёт 127 соответствий и
**35 инлайеров** — вчетверо больше порога. То есть окно уже было рабочим.

Что действительно ломает кадр — **смещение центра окна** от истинного центра
кадра. Замер на `Ufa3` при неизменном окне:

| смещение центра, м | 0 | 20 | 40 | 57 |
|---|---|---|---|---|
| соответствий | 127 | 76 | 12 | 16 |
| инлайеров | **35** | **18** | нет позы | 6 |

**Найдено рассогласование двух функций.** `_fine_pass` строил окно с запасом
34 м, а `required_cell_overlap` при выборе плотности сетки подставляла прикидку
`coarse = footprint/12` — для Уфы 19 м/px вместо реальных 0.68 — и «ожидала»
запас 115 м. Из-за этого сетка с перекрытием 0.5 объявлялась достаточной, хотя
допускала смещение центра клетки до **81 м** — вдвое дальше, чем накрывает окно
и втрое дальше рабочего диапазона матчера. Две величины, обязанные выводиться из
одного числа, выводились из разных.

**Теория исправлена, проверена на всём наборе и отвергнута.** Согласованный
расчёт даёт перекрытия 0.84 вместо 0.5/0.75 — сетка плотнее в 3–10 раз. Карты
пересобраны (1173 с, ~215 тыс. клеток), прогон полный:

| | было | с согласованной сеткой |
|---|---|---|
| принято гейтом | **11/16** | 10/16 |
| ложных | 0 | 0 |
| `Volgograd3` | 4.1 м | **отказ** |
| `Ufa3` | отказ | отказ |

**Потерян ровно тот кейс, ради которого связка когда-то и выводилась.** Причина —
в том, чего формула не знает: при перекрытии 0.84 окрестность точки покрывают
~38 почти одинаковых клеток, и первые 15 кандидатов оказываются **одним и тем же
местом в пятнадцати копиях**. Плотная сетка повышает покрытие одной клетки ценой
разнообразия кандидатов, и на этом наборе размен отрицательный. Побочно видно и
по диагностике: ранг ближайшей к истине клетки у `Ufa2` уехал с 1 на 44 — при
плотной сетке «ранг верной клетки» перестаёт быть осмысленной метрикой.

**Что оставлено в коде.**

* `fine_margin_m` — запас окна считается **в одном месте**; `_fine_pass` берёт
  его оттуда. Рассогласование, стоившее этого разбора, больше невозможно.
* `max_fine_window_px` — потолок окна стал параметром `localize` и флагом
  харнесса вместо константы. Дефолт прежний (4000 px, замерен на LightGlue).
* `required_cell_overlap` — **измеренная политика**, а не вывод формулы, с
  записанной в docstring причиной: 0.75 там, где потолок окна связывает, 0.5 у
  мелких кадров. Прежние значения восстановлены, поведение совпадает с золотом
  16/16.
* Тесты `tests/test_window_grid.py` пиннят **расхождение теории и замера**, чтобы
  следующий читатель не «починил» политику заново по формуле.

**Следствие для трека A.** Кросс-сезонный `Ufa3` по-прежнему не проходит, и
теперь известно, что дело **не в размере окна**. Оставшиеся подозреваемые:
разнообразие кандидатов (`top_k` против плотности сетки) и точность центра
клетки, которую даёт Этаж 1. Это переводит задачу из трека A обратно в связку
«Этаж 1 ↔ Этаж 2», и решать её надо тройкой параметров сразу, а не по одному.

**Цена ошибки в оценке.** Прикидка «окно ~2700 px», сделанная в прошлой вехе без
расчёта, отправила работу не туда. Числа, которые попадают в вывод, надо считать,
а не оценивать на глаз, — даже когда оценка выглядит безобидной.

## 2026-07-29 — GIM и MINIMA: MINIMA впервые сдвинула кросс-сезон, но упирается в окно

**Что.** Дешёвая часть трека A ([ROADMAP.md](ROADMAP.md), фаза 2): те же сети,
другие веса. Подключены `gim_lightglue`, `minima_lightglue`, `minima_loftr`
(`aero_geoloc/weights.py`), каждый — один флаг `--matcher`.

**Что пришлось сделать до эксперимента.** ``load_state_dict(strict=False)`` молча
терпит любое несовпадение имён: сеть останется на базовых весах, матчер
отработает, A/B покажет «кандидат не помог», и вывод будет сделан о кандидате,
которого в вычислении не было. Ровно так уже дважды получался неверный вывод о
LoFTR. Поэтому :func:`weights.apply_state_dict` **считает совпавшие тензоры по
имени И форме** и падает, если покрыто меньше 90%.

| чекпоинт | лицензия | лёг |
|---|---|---|
| `gim_lightglue` | MIT | 251/252 LightGlue + 24/24 SuperPoint |
| `minima_lightglue` | Apache-2.0 | 251/252 LightGlue (SuperPoint штатный) |
| `minima_loftr` | Apache-2.0 | 211/211 в `kornia.feature.LoFTR` |
| `gim_loftr` | MIT | **114/211 — отвергнут**: у GIM свой backbone (`backbone.encode.*`), 261 лишний тензор. Это другая архитектура, а не другие веса; нужен код сети из репозитория GIM |

Перекладка имён нужна одна: у GIM и наследующей ему MINIMA внимание разложено по
спискам `self_attn.{i}` / `cross_attn.{i}`, у cvg — собрано в
`transformers.{i}.{self|cross}_attn`. Формы совпадают полностью.

**A/B на всех 16 кейсах.**

| | LightGlue (база) | GIM-LG | MINIMA-LG | MINIMA-LoFTR |
|---|---|---|---|---|
| принято гейтом | **11/16** | 9/16 | **11/16** | 6/16 |
| верных мест | 11/11 | 10/10 | 11/11 | 6/6 |
| **ложных** | **0** | **0** | **0** | **0** |
| онлайн, медиана | 8.5 с | 5.7 с | 8.9 с | 3.0 с |
| дифф к золоту | — | −2 (`00049` в гейт, `Volgograd3` в отказ) | −1 `Volgograd3`, +1 `Volgograd` | −6, +1 |

Сквозного выигрыша нет ни у кого: **база не меняется**. GIM даёт больше инлайеров
там, где и так всё работает (`Saratov` 46 против 29, `Saratov2` 41 против 16), но
теряет два кейса. MINIMA-LightGlue ровно размённая: `Volgograd` за `Volgograd3`.

**Главный результат — не в этой таблице.** Критерий отсева трека A звучал так:
кандидат обязан **сдвинуть `Ufa2`/`Ufa3` с нуля инлайеров**. На оракульном
выравнивании с окном по размеру кадра:

| матчер | `Ufa3` соотв./инлайеров | `Ufa2` |
|---|---|---|
| LightGlue (база) | 24 / **6** | 37 / позы нет |
| GIM-LightGlue | 2 / позы нет | 2 / позы нет |
| LoFTR | 16 / 5 | 25 / позы нет |
| MINIMA-LoFTR | 0 | 0 |
| **MINIMA-LightGlue** | **242 / 173, ошибка 4.9 м** | 2 / позы нет |

**MINIMA-LightGlue — первый кандидат, который берёт кросс-сезонный кадр**: 173
инлайера против 6 у базы, поза верная. Это в 29 раз больше и качественно другой
режим, а не улучшение на проценты.

**Почему пайплайн всё равно отказывает — измерено.** Свип по размеру окна
подложки на `Ufa3` (кадр 1337 px, отпечаток 230 м):

| окно, px | 530 | 795 | 1060 | 1590 | 1620 | 1855 | 2000 |
|---|---|---|---|---|---|---|---|
| инлайеров (кроп) | 173 | 185 | 100 | 61 | 40 | — | — |
| инлайеров (полный кадр, предповорот) | | | | | **63** | | — |

До ~1620 px (≈280 м земли) матч держится и на **штатном входе пайплайна** —
полном кадре с предповоротом: 256 соответствий, 63 инлайера. На 2000 px он
рушится до 2 соответствий. А пайплайн строит окно вокруг клетки-кандидата с
запасом в полклетки, то есть ~2700 px. **Блокер переехал с матчера на размер окна
точного уровня.**

**Следствие.** Это ровно тот пункт, который в [ROADMAP.md](ROADMAP.md) записан в
фазу «смычка треков»: пересчёт `MAX_FINE_WINDOW_PX` и `required_cell_overlap` под
фактический предел нового ядра, причём **синхронно** — перекрытие сетки жёстко
связано с запасом окна, и за эту связь уже терялся `Volgograd3`. Менять это
сейчас, в конце длинной сессии, без пересборки индексов и пере-приёмки нельзя;
но число, которого не хватало, теперь есть: **≈1600 px (280 м) для
MINIMA-LightGlue на кросс-сезоне**.

**Границы вывода.** Кросс-сезонных кадров по-прежнему два, и `Ufa2` не берёт
никто — у него и у базы 37 соответствий не складываются в позу. Один взятый кадр
из двух — это направление, а не решение. GIM на кросс-сезоне даёт 2 соответствия
при полностью корректной загрузке весов (проверено счётчиком тензоров) и при этом
исправно работает на летних кадрах, так что дело в весах, а не в интеграции.

## 2026-07-29 — E3: NCC в связке качества заменена косинусом плотных DINO-фич

**Что.** Фотометрический член связки качества стал **сменной мерой**: связка
больше не знает, что внутри именно NCC, — оркестрация выбирает меру, а
`quality.assess` знает лишь её значение, имя и порог. Боевая конфигурация
переведена на косинус плотных патч-токенов DINOv2 с порогом **0.35**
(`quality.MIN_DINO`).

**Зачем.** Живой дефект: `00049` (немецкое поле) локализуется верно с ошибкой
8.5 м, но режется гейтом, потому что его NCC при **верной** позе равен −0.018
при пороге 0.12. E1 объяснил причину: у NCC на верных парах разброс от −0.03 до
0.66, то есть разброс **между кадрами** больше сезонного, и единого порога у неё
нет в принципе.

**Как выбран порог.** Не по оракульным значениям E1, а по тем числам, что реально
считает пайплайн: 36 верных поз и 9 ложных, собранных матчером
(`scripts/e2_geometry.py`). На них dino даёт **AUC 0.990** против 0.962 у NCC и
0.937 у счётчика инлайеров.

| | dino | NCC |
|---|---|---|
| слабейшая ВЕРНАЯ поза | 0.377 (`00049`) | −0.162 |
| сильнейшая ЛОЖНАЯ поза | 0.454 (6 инлайеров) | 0.286 |
| ложных с ≥8 инлайеров выше порога | 1 | 1 (та же) |

Порог 0.35 пропускает все 36 верных поз. Выше него остаются 6 ложных, но у пяти
из них 4–6 инлайеров, и их снимает второе условие связки; единственная ложная
поза с 8 инлайерами (`Ufa_sample4`, сдвиг 150 м) проходила и по NCC. То есть
замена **ничего не ослабляет** и возвращает `00049`.

**Результат прогона (16 кейсов, LightGlue, радиус 1.5 км).**

| | было (NCC 0.12) | стало (dino 0.35) |
|---|---|---|
| принято гейтом | 10/16 | **11/16** |
| верных мест | 11/11 | **11/11** |
| **ложных** | 0 | **0** |
| верных отвергнуто гейтом | 1 (`00049`) | **0** |

`00049` принят с ошибкой 8.5 м, его dino на найденной позе — 0.491. Дифф против
золота: **ровно одно изменение, ноль регрессий**. Золото перезаморожено с этой
конфигурацией — это первый случай осознанной перезаморозки, ради которого сторож
и различает «улучшение» и «регрессию».

**Приёмка фазы 1 из [ROADMAP.md](ROADMAP.md) выполнена:** `00049` перестал
резаться гейтом при сохранении нуля ложных.

**Побочно измерено (осторожно).** Онлайн-медиана 8.5 с против 11.8 с у NCC.
Правдоподобное объяснение: NCC считается по всему окну точного уровня (до
4000 px) в numpy, а dino ужимает вход до 518 px и работает на GPU. Но это **не
контролируемый замер скорости** — прогоны шли в разное время и с разной
прогретостью кэша; принимать за факт «dino быстрее» пока нельзя.

**Что осталось от исходного замысла E3.** Обучаемая связка (логистическая
регрессия с изотонической калибровкой поверх вектора сигналов) **не сделана и
пока не нужна**: замена одного члена конъюнкции закрыла дефект целиком, а обучать
фьюжн на 36 верных и 9 ложных позах — это подгонка под шум. Вернуться к ней имеет
смысл, когда появятся кросс-сезонные позитивы, то есть после трека A.

**Границы вывода.**

* Порог держится на **одном** кадре: запас слабейшей верной позы над границей —
  0.027. При пополнении набора порог надо пересчитать, а не унаследовать.
* Дефолт **библиотеки** остался `ncc`: пакет не должен тянуть torch ради оценки
  качества, и синтетический стенд ходит на SIFT без него. `dino` — дефолт
  **харнесса оценки**, то есть боевой конфигурации.
* Кросс-сезон не сдвинулся ни на шаг: `Ufa2`/`Ufa3` по-прежнему отказывают, и
  причина прежняя — Этаж 2 не собирает позу. Мера качества тут ни при чём.

## 2026-07-29 — A/B всего набора: LoFTR быстрее втрое, но теряет 3 локализации

**Что.** Первая подмена ядра из трека A ([ROADMAP.md](ROADMAP.md), фаза 2, пункт 1)
проверена на **всех 16 кейсах** сразу, а не на одной паре: LightGlue против LoFTR
на рабочем разрешении 640 и 1024. Сравнение — через сторож фазы 0
(`scripts/regress.py --from-csv`), то есть по классу исхода каждого кейса.

**Зачем.** У LoFTR была отдельная от кросс-сезона гипотеза: на контролируемой паре
`Ufa2`/`Ufa_sample4` он дал **103 инлайера против 41** у LightGlue и оказался
впятеро быстрее. Отсюда предположение «LoFTR лучше как матчер по умолчанию».
Проверяется оно одним прогоном набора.

**Предварительно пришлось закрыть ловушку в коде, а не в скрипте.** `LoFTRMatcher`
подаёт в ядро полное разрешение; в пайплайне окно точного уровня доходит до
4000 px. Добавлен `ResizedMatcher` (`aero_geoloc/matcher.py`): обе картинки
уменьшаются **одним** коэффициентом, точки возвращаются в исходные пиксели,
размеры добиваются до кратности 8. Общий коэффициент — не деталь: раздельная
нормировка кадра и окна вносит расхождение масштабов (у нас 1.5×) и уже давала
11 инлайеров вместо 103. Обёртка понадобится и всем плотным кандидатам дальше
(RoMa, MatchAnything, MINIMA), поэтому она в модуле, а не в эксперименте.

**Результат.**

| | LightGlue | LoFTR-640 | LoFTR-1024 |
|---|---|---|---|
| принято гейтом | **10/16** | 8/16 | 7/16 |
| верных мест | 10/10 | 8/8 | 7/7 |
| **ложных** | **0** | **0** | **0** |
| медиана ошибки | 23.0 м | 43.4 м | 34.1 м |
| онлайн, медиана | 11.8 с | **5.0 с** | **3.5 с** |

Поимённо (LoFTR-640 против базы): **потеряны** `Volgograd3` (4.1 м → отказ),
`Volgograd4` (45.7 м → отказ), `Volgograd2` (2.3 м → отвергнут гейтом),
`00049` (отвергался гейтом → отказ вовсе); **приобретён** `Volgograd` (отказ →
117.2 м, верно). Там, где оба работают, точность практически совпадает
(`Saratov` 1.2 / 0.8 м, `Saratov2` 53.2 / 52.7 м, `Ufa_sample3` 8.8 / 8.2 м).

**Вывод — гипотеза не подтвердилась.** Преимущество LoFTR на одной паре не
переносится на набор: −3 локализации при втрое меньшем времени. **Матчером по
умолчанию остаётся LightGlue.** Разрешение 1024 не спасает, а ухудшает (7 против
8) — дело не в настройке, а в самом ядре на этих данных.

**Что подтвердилось независимо.** Ни одна из трёх конфигураций не дала ни одного
ложного срабатывания. Инвариант «честный отказ дороже красивой точки» держится
при полной замене ядра матчинга — это первая его проверка сменой компонента.

**Кросс-сезон не сдвинулся ни на шаг**: `Ufa2`, `Ufa3` отказывают у всех трёх
конфигураций. Критерий отсева трека A («сдвинуть `Ufa2` с нуля инлайеров») LoFTR
не проходит, что согласуется с прежним замером на контролируемой паре (6
инлайеров против 4).

**Следствие.** LoFTR остаётся полезен как **быстрый вариант** там, где втрое
меньшее время важнее трёх локализаций (например, последовательностный режим, где
кадры идут потоком и промах компенсируется соседями). Как замена по умолчанию —
нет. Следующие кандидаты трека A (GIM, MINIMA, RoMa v2) проверяются той же
командой: один флаг `--matcher`, один прогон, один дифф против золота.

## 2026-07-29 — E1/E2: чем заменить NCC. Победил косинус плотных DINO-фич

**Что.** Первый шаг трека B ([ROADMAP.md](ROADMAP.md), фаза 1) — два эксперимента
на **оракульном выравнивании**: верная поза строится из истины, а не ищется
матчером (`aero_geoloc/oracle.py`). Это даёт то, чего пайплайн дать не может, —
**кросс-сезонные позитивы**: `Ufa2`/`Ufa3` при заведомо верной позе. У кадров с
EXIF оракул чист (центр и курс из метаданных, подложка не участвует); у кадров
без EXIF курс взят у позы, подтверждённой владельцем.

**Зачем.** Обзор `RESEARCH_B_VERIFICATION.md` разделил две работы NCC: метрика
выравнивания и дискриминатор «то место или не то». Какая из них ломается сезоном —
вопрос эмпирический, и E1 отвечает на него без единого нового матча.

**E1 — результат.** Семь мер (`aero_geoloc/similarity.py`) на 14 верных и 168
ложных пар:

| мера | AUC в сезон | AUC кросс-сезон | сдвиг шкалы | верная > всех своих ложных |
|---|---|---|---|---|
| ncc | 0.871 | **1.000** | 0.50 | 11/14 |
| grad_ncc | 0.922 | 0.938 | 0.65 | 11/14 |
| cfog | 0.931 | 0.500 | 0.27 | 11/14 |
| ngf | **0.955** | 0.500 | 0.95 | 10/14 |
| nmi | 0.844 | 0.854 | 0.99 | 9/14 |
| edge_dice | 0.670 | 0.062 | 0.46 | 5/14 |
| **dino** (плотный DINOv2) | 0.909 | **1.000** | **0.81** | **13/14** |

Три вывода, каждый меняет картину:

1. **NCC не перестаёт различать на смене сезона.** На апрельских кадрах она
   отделяет верное место от смещённых окон **идеально** (AUC 1.000, 0.190 против
   0.051). Рабочая гипотеза «сезон убивает дискриминатор» **опровергнута**: сезон
   двигает шкалу (медиана верных 0.38 → 0.19), а различать не мешает.
2. **Главный разброс NCC — не между сезонами, а между кадрами.** На ВЕРНЫХ парах
   она даёт от −0.031 (`00049`, немецкое поле) до 0.664 (`Volgograd3`) — размах
   0.70 против сезонного сдвига 0.19. Поэтому единого порога у неё нет и не будет:
   у `00049` верная пара (−0.031) лежит **ниже** его же ложной (0.419), и это
   ровно тот кейс, который гейт режет сегодня.
3. **CFOG и NGF, фавориты обзора, кросс-сезон не берут** (AUC 0.500 — монета).
   NGF при этом лучший в сезон (0.955) и с самой ровной шкалой (0.95) — то есть
   ровная шкала сама по себе ничего не стоит, если мера не различает.

**Победитель — косинус плотных патч-токенов DINOv2**: единственная мера, которая
и различает в обоих режимах (1.000 / 0.909), и держит шкалу (0.81), и выигрывает
внутри кейса 13 раз из 14. Проигрывает только `train_SB_0023` — известный кейс
информационного дефицита (52 м AGL, кадр в 8 раз детальнее подложки). Ставка
обзора оправдалась ровно по заявленному основанию: **на этом же наборе** MegaLoc
того же семейства держит апрельские кадры на ранге 1–2.

**E2 — честный отрицательный результат.** Геометрические сигналы
(`inlier_spread`, `bootstrap_center_scatter_px` в `aero_geoloc/pose.py`) на 42
позах, собранных матчером: из 6 по-настоящему ложных поз **все имеют ≤8
инлайеров**, то есть действующий жёсткий порог `MIN_INLIERS_HARD = 8` их и так
отсекает. AUC: инлайеры 0.945, NCC 0.948, разброс центра 0.733, разброс инлайеров
0.557. **Добавлять их в связку смысла нет** — они не приносят ничего сверх
счётчика, а стоят вычислений. В пайплайн не заведены сознательно.

Два побочных результата E2 ценнее основного:

* **RMSE репроекции анти-коррелирован** (AUC 0.048): у ложных поз он МЕНЬШЕ.
  Прежний вывод «RMSE бесполезен» (Юден 0) уточняется — он вреден как
  положительный сигнал.
* **24 из 30 поз, собранных на сдвинутых окнах, вывели к ВЕРНОМУ месту.** Это
  прямое измерение того, ради чего сделано перекрытие сетки индекса.

**Ловушка, стоившая двух перепрогонов.** Первая разметка E2 считала ложной любую
позу из сдвинутого окна. Но окно, сдвинутое на 150 м при отпечатке 240 м, всё ещё
**содержит** истинное место, и матчер находит там верное совмещение; NCC у таких
«ложных» вышел 0.442 против 0.444 у верных — шум вместо сигнала. Метка ставится
по положению позы **на земле** через `Georef`, а не по пикселям окна.

**Следствие.**

* Следующий шаг трека B — не поиск ещё одной меры, а **E3**: заменить в связке
  качества NCC на косинус плотных DINO-фич и перекалибровать пороги. Ожидание
  прямое: `00049` перестаёт резаться гейтом (его dino 0.427 против лучшей ложной
  0.392), нуль ложных сохраняется.
* Кросс-сезон остаётся **задачей трека A**: E2 показал, что на `Ufa2` поза не
  собирается даже при оракульном выравнивании (0 инлайеров), а на `Ufa3` — 6
  инлайеров при пороге 8. Проверять нечего, пока матчер не даст позу.

**Чего эти числа не доказывают.** Кросс-сезонных позитивов всего два (`Ufa2`,
`Ufa3`) — на такой выборке AUC 1.000 означает «ни разу не ошиблась», а не
«надёжна». Негативы — смещённые окна той же сцены, а не реальные кандидаты
ретривала, которые могут быть похожее. И сезон в наборе по-прежнему сцеплен с
масштабом: у апрельских кадров ресемпл 0.24 (кадр вчетверо детальнее подложки),
у летних кадров Уфы — 1.16.

## 2026-07-28 — Сводный план дальнейшей доработки (ROADMAP)

**Что.** Открытые треки (оценка, скорость, кросс-сезонное исследование) сведены в
один упорядоченный план — [ROADMAP.md](ROADMAP.md). Порядок: регрессия (этап F) →
дешёвая часть трека B (E1 оракульное выравнивание, E2 геометрические сигналы) →
связка сигналов → подмены весов матчера (LoFTR на всех кейсах, GIM, MINIMA) →
RoMa v2 на замороженном DINOv3 → смычка треков → бэклог.

**Зачем.** После возврата обзоров по направлениям A (чем матчить) и B (чем
проверять) появилось больше кандидатов, чем ресурса, и разнородные критерии
успеха. Нужен был один порядок с явным обоснованием, почему именно такой.

**Результат — три решения и их основания:**

1. **Регрессия первой.** Дальше меняется ядро матчинга — самый нагруженный
   компонент. За сессию дважды едва не прошла тихая регрессия: авто-перекрытие
   потеряло `Volgograd3` (0.8 м → отказ), а ключ кэша карты молча отдавал чужую
   карту и «доказывал», что эксперимент не помог. Оба раза ловила ручная сверка;
   при подмене матчера этого не хватит.
2. **Трек B раньше трека A** (выбор был оставлен на меня). B считается на уже
   собранных данных, не требует внешних весов и чинит живой дефект: `00049`
   режется гейтом при NCC 0.113 против порога 0.12. Внутри B первым — E1: обзор
   верно разделил две работы NCC (метрика выравнивания и дискриминатор); какая
   из них ломается сезоном — вопрос эмпирический, и оракульное выравнивание по
   известной истине отвечает на него без единого нового матча.
3. **RoMa v2 — отдельной фазой** (по указанию владельца). Обоснование сильное:
   стоит на том же классе foundation-фич, что измеренно переживает сезон у нас на
   Этаже 1 (MegaLoc держит ранг 1–2 на апрельских кадрах), оценён на SatAst —
   ближайшем публичном аналоге нашей геометрии, и отдаёт попиксельную certainty,
   то есть попутно даёт кандидат-сигнал для трека B.

**Следствие.** Введён общий критерий отсева для трека A: кандидат обязан
**сдвинуть `Ufa2` с нуля инлайеров**, иначе не рассматривается дальше. Записаны
ловушки измерения, дважды сработавшие на LoFTR (полное разрешение вместо рабочего;
раздельный ресайз кадра и окна, вносящий расхождение масштабов 1.5× — 11 инлайеров
вместо 103), и риск, что все кандидаты A не возьмут кросс-сезон: тогда честный
ответ — подложка под сезон кадра, то есть смена данных, а не алгоритма.

## 2026-07-28 — Уфа: виноват сезон, а не координаты. Контролируемая пара

**Что.** Владелец добавил в `test_images/Ufa/` четыре **летних** снимка с GSD и
координатами, а также дал координаты к старым апрельским кадрам, предположив, что
те могут быть неверными. Ключевое: **`Ufa_sample4` снят в том же месте, что
`Ufa2`** — получилась контролируемая пара «одно место, разные съёмки».

**Зачем.** До сих пор провал уфимских кадров объяснялся сезоном, но это была
**гипотеза**: нельзя было исключить, что координаты промахиваются, или что дело в
пайплайне. Пара снимает неоднозначность.

**Результат — координаты верны.**

| Кадр | EXIF | Координаты владельца | Расхождение |
|---|---|---|---|

## 2026-07-28 — Трек скорости: офлайн ~×3, онлайн ~×3.2, качество не тронуто

**Что.** Выполнен трек [OPTIMIZATION_PLAN.md](OPTIMIZATION_PLAN.md): параллельная
загрузка тайлов, батчинг кодирования, FP16, приведение `top-K` к измеренному рангу,
один ECC на победителя вместо ECC на каждом кандидате.

**Зачем.** Сборка карт выглядела непропорционально дорогой, а свип приора (этап E)
без ускорения шёл бы часами. Условие трека — **не менять результат**: каждая
оптимизация сверялась прогоном `eval_dataset.py` против зафиксированных чисел.

**Результат.**

| | Оптимизация | Итог |
|---|---|---|
| офлайн | параллельная загрузка тайлов | ×5.9 (18.4 → 3.1 с, 4 новых района) |
| офлайн | батчинг кодирования (батч 8) | ×1.89 (10.9 → 5.8 мс/вектор) |
| офлайн | FP16 через `autocast` | ×1.91 сборки |
| онлайн | `top-K` 25 → 15 | −27% (502 → 365 с) |
| онлайн | один ECC на победителя | ×2.4 (365 → 155 с) |

**Совокупно офлайн ~×3, онлайн ~×3.2.** Качество неизменно: 8/8 верных, 0 ложных,
у последней оптимизации ошибки совпали **до десятых** по всем восьми кейсам.

**Следствие — четыре раза интуиция разошлась с замером.**
1. **Дорога не нейросеть, а сеть.** На новом районе ~95% сборки карты уходило в
   последовательную загрузку тайлов (у одной карты 850 с из 897 при ~46 с
   вычислений). Приоритеты трека определил именно этот замер.
2. **Половина стоимости `encode` — препроцессинг, а не GPU.** Батчить только прямой
   проход дало бы ×1.3 вместо ×1.9; пришлось слать на устройство uint8 в один канал
   вместо float32 RGB (в 12 раз меньше данных) и разворачивать каналы broadcast-ом.
3. **FP16 дал скорость, но не память.** `autocast` приводит лишь вычисления, веса
   остаются FP32 (0.91 ГБ из 1.78 ГБ пика). Полный `model.half()` дал бы и память,
   но на MegaLoc падает — внутри есть слои, жёстко работающие во float32.
4. **В веере 90% времени — ECC, а не LightGlue** (тот занимает 1%). Вопрос «можно ли
   распараллелить веер» привёл не к параллелизму: ECC не влияет на выбор победителя
   (инлайеры отбирает RANSAC до него), поэтому достаточно одного вызова вместо шести.

**Что отклонено — тоже с числами.** Слияние карт по серии экономит 7.8% сборки, но
объединённый регион содержит больше клеток, то есть больше дистракторов, а рост
ранга верной клетки — известный режим отказа проекта. Плюс общая решётка клеток,
привязанная к мировым пикселям, не выравнивается с границей региона (100 клеток
вместо 121 на стенде) — это меняет покрытие, что запрещено условием трека. Пробная
реализация откачена. Квантование индекса снято владельцем как ненужное.

**Также.** `top-K` 25 был перерасходом: верная клетка лежит на ранге ≤ 11 у 11 кейсов
из 12, кандидаты с 12-го не пригодились ни разу. Попутно вскрылось, что метрика
«ранг ближайшей клетки» **пессимистична**: у `Volgograd3` ранг 15 при `top-K=14`, и
кейс всё равно локализовался на 0.8 м — клетки идут с перекрытием 75%, истинное
место накрывает несколько, и годится не только ближайшая.

## 2026-07-27 — Калибровка дискриминатора качества на реальных данных

**Что.** `scripts/calibrate_quality.py` — сбор размеченных матчей по `for_binding`:
позитивы = кадр↔референс **на истине**, трудные негативы = кадр↔**похожие клетки из

**Зачем.** В поиске по карте гейт позиции не помогает; отделять верный матч от
ложного должно КАЧЕСТВО матча, а грубый `min_inliers` не справляется (веха про
офлайн-карту: ложняк 2126 м). Нужны калиброванные пороги на реальных данных.

**Данные (честная граница `for_binding`).** Из ~649 снимков: `images`+`quary_images`
(367) — **без GPS**, непригодны. `ufa*` (267) — GPS есть, но кадр↔Esri — экстремальный
**кросс-сезон** (дрон=ранняя весна, голые деревья; Esri=лето): матчится на ~5
инлайерах, **0 успешных позитивов**. Реально размечено: **11 верных / 26 ложных**,
практически только DRZ (Германия). Случайно сдвинутый референс матчер и так отвергает
— ложняки родятся лишь от appearance-похожих клеток ретривала (это и подтвердилось).

**Результат (разделяющая сила).**

| Сигнал | Порог (Юден) | Youden | медиана верн / лож |
|---|---|---|---|
| n_inliers | ≥ 10 | 0.82 | 16 / 4 |
| ellipse_major_m | ≤ 0.23 | 0.61 | 0.22 / 0.37 |
| photometric_ncc | ≥ 0.19 | 0.48 | 0.20 / 0.02 |
| inlier_ratio | ≥ 0.33 | 0.42 | 0.23 / 0.15 |
| reprojection_rmse_px | — | **0.00** | 3.49 / 2.54 |

**Следствие.**
1. **Ни один сигнал по отдельности не идеален.** Негативы упираются в 4–9 инлайеров;
   NCC разделяет в среднем (0.20 vs 0.02), но шумит — есть негативы с NCC 0.19–0.64
   (повторяющийся паттерн на чужой клетке коррелирует). RMSE **бесполезен** (Youden 0).
2. **Лучшее — конъюнкция:** `n_inliers ≥ 8 И NCC ≥ 0.12` → **6/11 верных, 1/26 ложных
   (~96% точности)**. Это калиброванная замена мягкому `min_inliers=6 + min_ncc=0.05`
   (который и пропустил ложняк 2126 м): требовать связку инлайеров **и** NCC, а не одно.
3. **Предел данных:** 2 самых слабых верных (по 5 инлайеров, низкая высота/кросс-дата)
   неотделимы от негативов **никаким** сигналом — честный исход для них `NOT_LOCALIZED`.
4. **Позитивный класс мал и «немецкий»** (Ufa кросс-сезон вне локализуемости по Esri).
   Пороги firm-up требуют больше Esri-совместимых GPS-кадров; харнесс
   `calibrate_quality.py` переиспользуем, когда такие данные появятся.

Практическая рекомендация в `quality.assess`: LOCALIZED ⇐ `n_inliers ≥ 8` **И**
`NCC ≥ 0.12` **И** эллипс ≤ порога; RMSE из решения убрать. Это поднимет точность
без опоры на один хрупкий счётчик.

**Внедрено.** `quality.assess` — калиброванные дефолты связки: `min_inliers_hard 6→8`,
`min_ncc 0.3→0.12` (RMSE в `signals`, но не в решении — как и было). Кросс-доменные
вызовы (`localize_wide`, `map_benchmark`, `localize_real`, `run_ladder`) переведены

  Т.е. время поиска определяется числом кандидатов, доходящих до полного уточнения.

**Следствие (честный компромисс).**

| min_inliers | Локализовано | Ложных | Медиана ошибки | Ср. время |
|---|---|---|---|---|

## 2026-07-27 — Тайминги стадий (что сколько занимает) + поле 00049 на 2–3 км

**Что.** `localize_wide.py` печатает разбивку таймингов с разделением **офлайн
(индекс — одноразово, кэшируется)** vs **онлайн (запрос + поза — на каждый кадр)**.
Прогнан городской DRZ_19206 и полевой 00049 из приора 2–3 км (MegaLoc+PCA1024+FAISS).

**Результат (RTX 4090, MegaLoc, реальные прогоны).**

| Стадия | 00049 2 км (6241 кл, top-60) | 00049 3 км (12321 кл, top-15) |
|---|---|---|
| ОФЛАЙН — кодирование индекса | 97 с (16 мс/кл) | 511 с (41 мс/кл) |
| ОФЛАЙН — PCA-сжатие 8448→1024 | 3.9 с | 5.9 с |
| ОФЛАЙН — построение FAISS/HNSW | 0.2 с | 0.7 с |
| ОНЛАЙН — ретривал-запрос (Этаж 1) | 47 мс | 69 мс |
| ОНЛАЙН — точный уровень (Этаж 2) | 266 с (top-60) | 52 с (top-15) |

Локализация: 00049 2 км → **9.0 м** (retrieval top-1), 3 км → **8.1 м** (top-2).

**Следствие (где живёт время).**
1. **Офлайн определяется кодированием клеток** (O(N) прогонов энкодера). ВАЖНО: эта
   цифра *включает докачку тайлов* — 41 мс/кл на 3 км против 16 мс/кл на 2 км не рост
   GPU, а сетевой fetch новых тайлов, вплетённый в `build`. Чистое кодирование ~16
   мс/кл. Строится **один раз**, кэшируется на диск (`save/load`) — на запрос не
   повторяется. PCA (4–6 с) и FAISS (<1 с) — ничтожны на фоне кодирования.
2. **Онлайн определяется Этажом 2** — веером LightGlue по top-K (O(K), ~1–4 с/кандидат).
   Ретривал-запрос (Этаж 1) — десятки мс, ничтожен; PCA/FAISS онлайн ≈ 0. Прямое
   следствие: **266 с (top-60) → 52 с (top-15)** при том же качестве — онлайн-время
   режется уменьшением K, т.е. лучшим рангом (плата за плохой ранг — линейна по K).
3. **Два независимых рычага:** офлайн ускоряется только кэшем индекса; онлайн — только
   меньшим top-K (ранг). Ни PCA, ни FAISS онлайн-время матчинга не трогают.
4. **00049 (поле) ретривится отлично** (top-1/top-2, уник. 0.03–0.08) — лучше, чем
   городской DRZ (ранг 15/41). С MegaLoc «поле = трудно» больше не аксиома: трудность
   ретривала зависит от конкретного кадра и его близости к подложке, а не от ландшафта.

## 2026-07-27 — Реализация PCA→1024 + FAISS для Этажа 1 (и опровержение whitening)

**Что.** `PCAReducer` (рандомизированный SVD на numpy, детерминированный) и сменный
`AnnBackend` (`NumpyAnn` — точный, по умолчанию; `FaissAnn` — HNSW/Flat, gated) за
неизменным `TerrainIndex.query`. Включаются `compress()` / `use_faiss()` после
`build()`; сжатые векторы + состояние PCA пишутся в `.npz`. Флаги в `localize_wide.py`
(`--pca-dim`, `--whiten`, `--faiss`). Дефолтный путь (без вызовов) — прежний numpy.

**Зачем.** Инфраструктура честного ±5 км (см. веху про три издержки): память индекса
и скорость поиска. Заодно проверяли книжную гипотезу VPR, что whitening поднимает Recall.

**Результат (измерено на реальном MegaLoc, DRZ_19206, приор 2 км, 6084 клетки, тёплый замер).**

| Вариант | Ранг верной клетки | Память | Запрос |
|---|---|---|---|
| raw MegaLoc 8448 (numpy) | 49 | 206 МБ | 20.5 мс |
| **PCA1024 plain (numpy)** | **15** | **25 МБ** | 17.1 мс |
| PCA1024 **whiten** (numpy) | **334** | 25 МБ | 17.4 мс |
| PCA1024 + FAISS/flat | 15 | 25 МБ | 17.9 мс |
| PCA1024 + FAISS/hnsw | 15 | 25 МБ | 16.6 мс |

Сквозняком (MegaLoc + PCA1024 + FAISS/HNSW), plain PCA срезает нужный top-K почти вдвое:

| Приор | Клеток | Ранг raw → PCA | top-K (PCA) | Ошибка |
|---|---|---|---|---|
| 2 км | 6084 | 49 → **15** | 25 | 6.5 м |
| 3 км | 12100 | 73 → **41** | 50 | 6.8 м |

**Следствие.**
1. **Plain PCA не просто сжимает — поднимает ранг 49→15** (отбрасывает шумовой хвост
   компонент) и режет память ÷8.2. Ранг 15 ⇒ пайплайну хватает **top-25 вместо top-60**
   — втрое дешевле доминирующий веер LightGlue. Это лечит и память, и (побочно) ранг.
2. **Whitening опровергнут измерением.** Вопреки книжной эвристике VPR, на нашем
   дескрипторе он *вредит* (ранг 49→334): малые сингулярные хвоста оценены плохо,
   деление на них раздувает шум. **Дефолт `whiten=False`** (оставлен опцией). Прошлая
   веха и код, где whitening подавался как «немного поднимает Recall», исправлены.
3. **FAISS на 6 тыс. клетках ≈ numpy по времени** — запрос определяет кодирование
   кадра (GPU ~17 мс), не поиск. Выигрыш O(log N) проявится на 10⁵–10⁶ клеток и при
   ротационной аугментации; FAISS/HNSW при этом сохранил ранг 15 (recall идеален).
4. Уточнение к прошлой вехе о рангах: «PCA ранг напрямую не лечит, whitening лишь
   немного» — **неверно в обе стороны**. Измерено: plain PCA ранг *улучшает*, whitening
   *ухудшает*. Роль домен-адаптации (пункт 2 дорожной карты) остаётся, но plain PCA
   оказался бесплатным бонусом к рангу, а не нейтральным к нему.

Коммит ядра: `4e68fa8`.

## 2026-07-27 — Регламент начальной погрешности приора от высоты полёта

**Что.** Допустимая неопределённость приора (σ позиции) регламентируется по высоте,
а не берётся плоские «±5 км» всегда:

| Высота полёта | Начальная ошибка (σ приора) |
|---|---|
| ~100 м | ~500 м |
| ~300 м | ~2 км |
| ~600 м | ~5 км |

**Зачем.** Footprint кадра ∝ высоте (у нашей камеры 100 м → ~150 м, 300 м → ~450 м,
600 м → ~900 м), а клетка индекса Этажа 1 берётся ≈ footprint кадра (иначе эмбеддинги
несопоставимы по масштабу). Поэтому число клеток в диске радиуса R ∝ (R/footprint)².
Регламент держит отношение **R/footprint ≈ 3–5.5** постоянным по порядку → число
клеток в регионе **ограничено (~200–500)**, а не растёт неконтролируемо с высотой.
Это ровно тот режим, где Этаж 1 (MegaLoc) держит верную клетку в практичном top-K
(замерено: ранг 2 при 2116 клетках; деградирует к 49 при 6084, ≤150 при 12100).
Физический смысл: на низкой высоте footprint мал, каждая клетка различает меньше
местности — значит и допустимая неопределённость честно меньше.

**Результат/следствие.**
- Уточняет плоское «±5 км» из [README.md](README.md): ±5 км — это фигура для ~600 м;
  на 100 м честный конверт — **~500 м**, на 300 м — **~2 км**.
- Согласуется с измерениями: на 100 м (DRZ_19206) широкий приор технически дотянул
  до 3 км, но ценой top-150 (дорогой веер LightGlue) — это **вне** надёжного конверта.
  Регламент фиксирует **надёжную** зону (малый top-K), а не предельно достижимую.
- Практически: из высоты по таблице задаётся радиус региона индексации (где ожидается
  истина); σ приора выставляется так, чтобы гейт ±3σ покрывал этот радиус, и ретривал
  остаётся в своём режиме. Между узлами таблицы — линейная интерполяция по высоте.

## 2026-07-27 — Уточнение: PCA+FAISS ≠ лечение ранга; развести три издержки

**Что.** Правка формулировки предыдущей вехи и дорожной карты. Ранее пункт «PCA→1024
+ FAISS/HNSW» был свален с «деградацией ранга» в один — это неточно.

**Зачем.** На широком приоре живут **три независимые издержки**, и путать их —
значит целить оптимизацию не туда:

| # | Издержка | Порядок | Кто снимает |
|---|---|---|---|
| 1 | Построение индекса (энкодер по каждой клетке) | O(N), offline | персистентность (`save/load`), кэш — **не** PCA/FAISS |
| 2 | Поиск в индексе (сравнить запрос со всеми) | O(N)/запрос | **FAISS/HNSW** → O(log N) |
| — | Память индекса | O(N·dim) | **PCA** (8448→1024, ÷8) + PQ/int8 (÷4–32) |
| 3 | Веер матчинга (LightGlue на top-K) | O(K) | **ранг** верной клетки → малый K |

**Результат (корректное распределение).**
- **FAISS/HNSW** снимает O(N) *поиска* (#2) и делает ротационную аугментацию (×8–12)
  и рост территории бесплатными по поиску. Мс вместо секунд.
- **PCA→~1024** снимает **память** (жёсткий блокер ±5 км: аугментированный индекс
  8448-мерных векторов не влезает в RAM) и удешевляет каждую операцию сравнения ~×8.
- **Деградация ранга** (верная клетка 2→49→≤150 с ростом числа дистракторов) — это
  **статистика числа конкурентов**, а не размерность. Голый PCA её не лечит.
  *PCA-whitening* немного поднимает ранг (уравнивает анизотропные оси дескриптора),
  но радикально — только **доменная адаптация** (пункт 2 дорожной карты: словарь
  AnyLoc-aerial / дообучение, «до 4× Recall@1»).

**Следствие.** Доминирующая стоимость широкого приора по времени — **веер #3**
(top-150 LightGlue ≈ 4.5 мин против долей секунды на скан). FAISS/PCA его **напрямую
не сокращают** — он падает только когда верная клетка стоит выше и можно взять
меньший K. Поэтому PCA+FAISS — **необходимая инфраструктура** (память, скорость
поиска, масштаб территории), но «дёшевым по времени» ±5 км делает **в паре** с
улучшением дескриптора (ранг). Разводим: *PCA+FAISS = память/скорость/масштаб*;
*ранг = whitening (немного) + доменный дескриптор (много)*.

## 2026-07-27 — VPR-энкодер MegaLoc: снят предел Этажа 1 на кросс-домене

**Зачем.** Замерено ранее: узкое место широкого приора (±2–5 км) — не матчер, а

([RESEARCH_VPR.md](RESEARCH_VPR.md)) рекомендовало обученную агрегацию поверх
сильного бэкбона; MegaLoc — первый кандидат.

**Результат (A/B на едином стенде, меняется только Encoder).**

| Кадр | DINOv2 (сырой) | MegaLoc (VPR) |
|---|---|---|
| DRZ_19206 (город), приор 1 км | ранг 506/2116 → отказ | ранг 2 → **4.2 м** |
| 00049 (поле), приор 1 км | ранг 139/2209 | ранг 1 → лок. |
| DRZ_19206, приор 2 км | ранг 398/6084 | ранг 49 |

Дальность приора (DRZ_19206, MegaLoc, сквозняком до позы):

| Приор | Ранг верной клетки | Клеток | top-K | Ошибка позы |
|---|---|---|---|---|
| 1 км | 2 | 2116 | 5 | 4.2 м |
| 2 км | 49 | 6084 | 60 | 3.7 м |
| 3 км | ≤150 | 12100 | 150 | 3.6 м |

**Следствие.**
1. Городской кадр, ранее `not_localized` из-за провала ретривала, локализуется из
   приора **3 км на 3.6 м**. Гипотеза «обученная агрегация поднимает верную клетку
   в top-K» подтверждена измерением.
2. Попутно вскрыт порог Этажа 2: низковысотный (100 м) кросс-дата кадр даёт всего
   ~7–8 similarity-инлайеров при **верной** позе (3–4 м); `min_inliers=10` их
   отвергал → нужен 6. Изоляция: прямой матч DRZ↔Esri z19 = 18 инлайеров по
   гомографии, значит матчер работает, дело в пороге.
3. Новый предел широкого приора — **различительность дескриптора при росте числа
   дистракторов**: ранг верной клетки растёт с регионом (2 → 49 → ≤150). Брутфорс
   `--top-k` компенсирует ценой **O(K) матчей LightGlue**; чистое масштабирование
   до ±5 км — это PCA→~1024 + доменный словарь/FAISS, а не расширение top-K.
4. Точность позы стабильна ~3.6–4.2 м независимо от дальности приора — Этаж 2
   точен, как только клетка доставлена. Вся сложность живёт на Этаже 1.

**Лицензия/масштаб (открытые вопросы).** Веса MegaLoc — MIT, но код репо содержит
GPL-фрагменты (из SALAD): для проприетарного продукта нужна чистая реализация
инференса или переход на BoQ (чистый MIT). Для ±5 км без PCA индекс неподъёмен
(dim 8448 × десятки тысяч клеток × аугментация).

Коммиты: `f160d1f` (энкодер + A/B), `bf1478e` (`--top-k`), `15eb774` (STATUS).

## Рабочий конверт приора (высота → допустимая σ)

Допустимая неопределённость приора регламентирована по высоте — footprint кадра ∝
высоте, клетка индекса ≈ footprint, поэтому σ, растущая с высотой, держит число
клеток (и ранг Этажа 1) в надёжной зоне. Детали и обоснование — веха от 2026-07-27.

| Высота | Начальная ошибка (радиус региона) | footprint кадра | клеток в регионе |
|---|---|---|---|
| ~100 м | ~500 м | ~150 м | ~200 |
| ~300 м | ~2 км | ~450 м | ~350 |
| ~600 м | ~5 км | ~900 м | ~500 |

**Подтверждено замером** (2026-07-29, `DRZ_00755`, 90 м AGL, независимая сцена в
Германии): σ = 2 км — вчетверо за конвертом — даёт 10 000 клеток, уникальность
0.009 и верный отказ в 2275 м от истины; σ = 0.5 км, то есть ровно по регламенту,
даёт **1.7 м**. Регламент выводился аналитически и до этого на границе не проверялся.

Начальная ошибка = радиус, на котором строится индекс и внутри которого гейт
принимает кандидата; footprint ∝ высоте, клетка ≈ footprint, поэтому клеток остаётся
~200–500 (надёжный, малый top-K) вместо неконтролируемого роста. Между узлами —
линейная интерполяция по высоте. Предельно приор дотягивается дальше, но ценой
дорогого веера LightGlue.

## Преимущества

- **Двухэтажная схема со сменными ядрами доказана практикой, а не декларацией.**
  За сессию ядро матчинга менялось **семь раз** — включая переход с разреженного
  на плотное, — и ни разу не потребовало правок в георефе, позе, стенде или
  ретривале. MegaLoc в своё время встал заменой одной строки. Это и есть
  способность подхватывать SOTA по мере выхода.
- **Этаж 2 больше не узкое место.** С плотным ядром поза находится на **всех 30
  кейсах**: отказов «поза не сошлась» нет вовсе. Решение теперь принимает связка
  качества.
- **Выводы переживают перепроверку.** Три ревизии трека A за один день
  (2026-08-21) сняли шесть экземпляров ошибки «порог чужой калибровки»; два
  записанных вывода оказались артефактами измерения, один — устоял, и главная
  опора аргумента о дообучении **выдержала целенаправленную попытку её сломать**
  (334 инлайера против нуля поз). Закреплён регламент приёмки чекпоинтов: сводка
  распределения сигнала при снятых порогах + доля точек, не дошедших до выхода.
  Отчёты: RESEARCH_A_{ROMAV2, LOFTR, LIGHTGLUE}_REPORT.md.
- **Честный отказ, а не уверенно-неверная точка.** `NOT_LOCALIZED` легитимен;
  приор — ограничение (гейт ±3σ), а не подсказка; ковариация и эллипс
  откалиброваны. Инвариант выдержал полную замену ядра семь раз.
- **Пустая подложка распознаётся до сборки карты.** `max_zoom` провайдера — предел
  пирамиды, а не гарантия покрытия: вне городов Esri отдаёт заглушку вместо
  снимка. Проба из девяти тайлов ловит это по байтовому равенству и отсутствию
  структуры, инструмент спускается на уровень со съёмкой либо честно отказывает.
- **Изменения нельзя протащить молча.** Золотой набор + сторож сверяют прогон по
  классу исхода; ложное срабатывание рушит сборку безусловно; конфигурация
  заморожена вместе с результатом, и при её расхождении вердикт не выдаётся.
- **Провенанс внешних весов под контролем**: адрес, размер, лицензия и **число
  реально совпавших тензоров** — в `aero_geoloc/weights.py`; несовпадение
  архитектуры падает с внятной ошибкой, а не откатывается на базовые веса.
- **Тяжёлые ядра gated**: пакет импортируется и оффлайн-тесты зелены без torch/сети.

## Сложности

- **Кросс-сезон решён наполовину.** `Ufa3` взят сквозным трактом двумя ядрами;
  `Ufa2` в тракте не берёт ни одно из восьми ядер — соответствия есть (почти две
  тысячи), подобия нет; в оракуле его впервые взял MINIMA-LoFTR (6 инлайеров,
  4.2 м — запас тонкий). И самих кросс-сезонных кадров в наборе **два**, одной
  сцены — выборка не позволяет сделать вывод.
- **Пороги держатся на тонких запасах.** Порог плотного ядра (185 инлайеров)
  стоит в 13 инлайерах от ложных поз, и `Volgograd4` колеблется вокруг него между
  прогонами (осциллятор уже дважды давал ложную тревогу сторожа). Порог сигнала
  качества (dino 0.35) держится на одном кадре.
- **Линия LightGlue недоизмерена на низковысотных кадрах.** Дефолтный
  `filter_threshold = 0.1` пакета душит контроль DRZ даже у штатных весов
  (14 пар, позы нет; при 0 — поза у всех трёх ядер линии). Исторические 11/16
  снимались на наборе без DRZ. Перекалибровка линии — отдельная задача.
- **Передача Этаж 1 → Этаж 2 содержит известный дефект**: запас окна берётся как
  «полклетки» и не зависит от перекрытия сетки, отчего окно вдвое шире нужного.
  Лечение реализовано, измерено и **не принято** (10/16 против 11/16, нестабильно):
  связка оказалась тройной — окно ↔ плотность сетки ↔ `top_k`.
- **Стоимость плотного ядра.** ~24 с на кадр против 8.4 с у `lightglue`. Для
  одиночного кадра приемлемо, для потока — нет; поэтому оба ядра оставлены.
- **Различительность дескриптора Этажа 1** остаётся пределом широкого приора:
  ранг верной клетки растёт с числом дистракторов, а на низкой высоте
  (`train_SB_0023`, 52 м AGL) уходит за практичный top-K.
- **Самоподобная местность** (поля) — низкая уникальность, ретривал слаб.
- **Покрытие подложки не везде доходит до нужной детальности.** Вне городов Esri
  обрывается на z18 и грубее; кадр с GSD 6.5 см приходится ресемплить в 5 раз, и
  вся разница в деталях теряется. Это не лечится алгоритмом — только другой
  подложкой.
- **Ротация** снимается предповоротом на −yaw — нужен надёжный курс; иначе
  аугментация индекса ×8–12 (дороже).
- **Лицензии.** MegaLoc — GPL-фрагменты в коде при MIT-весах; MINIMA — Apache-2.0;
  GIM и RoMa — MIT, но веса DINOv3 внутри чекпоинта RoMa v2 остаются под
  собственной лицензией Meta. Для проприетарного продукта проверять отдельно.

## Предлагаемое дальнейшее развитие

Порядок и обоснование — [ROADMAP.md](ROADMAP.md). Коротко, по убыванию отдачи:

1. **Данные, а не идеи.** Больше кросс-сезонных сцен и регионов: два кадра одной
   местности не дают права на вывод, а все текущие пороги калиброваны на тонких
   запасах. Это блокирует почти всё остальное.
2. **Дообучение под наш домен** (линия MINIMA на парах надир↔подложка). Перебор
   готовых ядер исчерпан, и он же показал, что выигрывает именно дообучение под
   вид, а не сила ядра, — посылка 2026-08-21 выдержала целенаправленную
   перепроверку (пара LightGlue: 334 инлайера против нуля поз у GIM при
   полностью снятых порогах). **Выбор базы решён треком F** (2026-08-24):
   дообучать **линию v1** (ванильная v1 сквозняком 25 верных против 16 у v2);
   залипания v2 — данные + контекст, не архитектура (`RESEARCH_F_REPORT.md`).
   **Величину вклада дообучения уточнил F2**: на RoMa (дообучен только
   декодер) MINIMA дала +1 верное место, на LoFTR (дообучена целиком) —
   **+5 верных и −3 ложных** (`RESEARCH_F2_REPORT.md`); эффект
   пропорционален доле перестроенной сети, поэтому ожидания собственного
   дообучения — вверх при достаточной разморозке, и «сколько слоёв
   размораживать» — главная ручка. Перед обучением — измерительный набор G.
3. **Быстрый режим на калиброванных порогах.** MINIMA-LoFTR: 27/29 верных при
   **2.5 с/кадр** (вдесятеро быстрее базы) — нужен свой порог инлайеров, полный
   regress и заморозка; второй кандидат — перекалибровка LightGlue-линии.
4. **Сезонная подложка** — вторая половина решения кросс-сезона, лежащая в
   данных, а не в алгоритме.
5. **Тройка «окно ↔ плотность сетки ↔ top-K» целиком.** По одному менять
   измеренно хуже; известный дефект передачи закрывается только так.
6. **certainty как предфильтр кандидатов** — рычаг скорости: она отделяет
   безнадёжные окна на порядок ещё до дорогого точного прохода.
7. **Доменный словарь / дообучение Этажа 1** — рычаг ранга на трудных кадрах
   (низкая высота, кросс-дата), а значит и меньший веер.
8. **Многомасштабный индекс** — покрыть 100–800 м (footprint гуляет ~6×).
9. **Калибровка доверия на объёме** — reliability-диаграмма `confidence`.
10. **Учёт рельефа** (DEM/DSM) против параллакса на низких высотах.
11. **Продуктовая чистота ядер** — если целевой продукт проприетарный.
