# Аэро-геолокализация надирных снимков

Сервис-прототип для **уточнения географического положения** снимка, сделанного примерно в надир (с борта БПЛА/самолёта), по картографической подложке. На вход подаётся кадр и грубое начальное приближение (координаты с погрешностью, зависящей от высоты — до ±5 км на ~600 м, высота, углы ориентации, параметры камеры); на выходе — уточнённые координаты центра кадра, курс, оценка высоты, полигон отпечатка на карте и **честная оценка качества локализации** (эллипс ошибки + статус, вплоть до отказа).

По сути это задача **итеративного georeferencing через image registration**: спутниковая подложка вокруг приора → сопоставление кадра с ней → геометрическое преобразование → перевод в координаты.

> Статус: **все фазы 0–5 реализованы и пайплайн проверен на реальных бортовых снимках**. Измеримый тест по манифесту `datasets/test_images.yaml` (**30 кейсов**, истина у всех): **30/30 поз найдено, 26 верных мест, 0 ложных срабатываний**, медиана ошибки **4.4 м** — при этом «0 ложных» верно **только внутри регламента «высота → σ»**: за его пределами система выдаёт уверенно-неверные точки, а не отказы (замер на `DRZ_06262`). Ядро матчинга по умолчанию — **MINIMA-RoMa** (плотное); `lightglue` втрое быстрее и доступен одним флагом. Связка качества — эллипс ∧ инлайеры ∧ косинус плотных DINOv2-фич. Впервые взят **кросс-сезонный кадр** (апрельская съёмка против летней Esri): `Ufa3` за 4.9 м. Инструмент владельца прогнан по всему набору: **13 верных, 0 ложных**, 4 верных отказа. Подложка проверяется на наличие съёмки до сборки карты (`max_zoom` провайдера ≠ покрытие). Поведение заморожено в `datasets/golden.yaml`, сторож регрессии — `scripts/regress.py`. Что осталось: `Ufa2` не берёт ни одно из семи проверенных ядер; кросс-сезонных кадров в наборе всего два, поэтому вывод остаётся направлением, а не доказательством. Детали и числа — [STATUS.md](STATUS.md).

## Что делает сервис

**Вход**
- Снимок местности ~1024×1024, примерно надир (допускается небольшой pitch/roll).
- Начальное приближение центра: `lat/lon`. Допустимая погрешность **зависит от высоты** (footprint кадра ∝ высоте, клетка индекса ≈ footprint → регион остаётся в надёжном режиме Этажа 1; обоснование — рабочий конверт в [JOURNAL.md](JOURNAL.md)):

  | Высота | Начальная ошибка |
  |---|---|
  | ~100 м | ~500 м |
  | ~300 м | ~2 км |
  | ~600 м | ~5 км |

  Плоское «±5 км» ниже по тексту — это фигура для верхней части диапазона (~600 м); на низкой высоте честный допуск пропорционально меньше.
- Высота: приблизительная, диапазон **400–800 м** (базовый режим), с погрешностью; расширенный режим — до **100 м**.
- Углы ориентации камеры: `yaw, pitch, roll`.
- Параметры камеры: `focal` + размер сенсора, либо `FOV`.

**Выход**
- Уточнённые координаты центра кадра (`lat/lon`).
- Курс (поворот кадра относительно севера).
- Оценка высоты (побочный продукт восстановленного масштаба).
- Полигон отпечатка кадра на карте (4 угла).
- **Оценка качества**: ковариация/эллипс ошибки в метрах + статус `LOCALIZED / LOW_CONFIDENCE / NOT_LOCALIZED`.

**Подложка** — любой открытый источник XYZ-тайлов. Базовый: **Esri World Imagery** (спутник, без ключа). Опционально Mapbox/Google (выше разрешение), OSM (карта, не для надирных фото).

## Как это работает (обзор)

Система **двухэтажная**. Это принципиально: один механизм отвечает за «ГДЕ примерно» (retrieval), другой — за «ГДЕ точно» (pose). Эмбеддинги физически не дают метровую точность (их разрешение = размер клетки), поэтому они не заменяют матчер, а снимают с него самую дорогую часть — грубый поиск в диске ±5 км.

```
                 ┌────────────────────────────────────────────────────────┐
   OFFLINE       │  подложка → нарезка на тайлы → DINOv2 → ANN-индекс      │
  (индексация)   │            (многомасштабный «хеш местности»)            │
                 └────────────────────────────────────────────────────────┘
                                          │
   RUNTIME                                ▼
   ┌────────┐   ┌─────────────┐   ┌──────────────┐   ┌─────────────────────┐
   │ кадр + │──►│ нормализация │──►│ ЭТАЖ 1        │──►│ ЭТАЖ 2               │
   │ приор  │   │ GSD, CLAHE,  │   │ retrieval:    │   │ геом. матчинг на     │
   │        │   │ ректификация │   │ top-K клеток  │   │ top-K → поза         │
   └────────┘   └─────────────┘   │ (ГДЕ примерно)│   │ (ГДЕ точно, метры)   │
                                  └──────────────┘   └─────────────────────┘
                                                              │
                                                              ▼
                                          ┌────────────────────────────────┐
                                          │ refinement (субпиксель) +       │
                                          │ цикл переуточнения масштаба +   │
                                          │ ковариация + статус/отказ       │
                                          └────────────────────────────────┘
                                                              │
                                                              ▼
                                    center lat/lon · heading · altitude · ellipse · status
```

Ключевое инженерное решение — **сменное ядро матчинга**. Всё вокруг него (георефа, оценка, refinement, стенд) не зависит от того, какой матчер стоит внутри:

- **Классика** — SIFT/AKAZE + RANSAC: не требует torch, годится для синтетического стенда и как быстрый запасной вариант.
- **Разреженные обучаемые** — SuperPoint+LightGlue и LoFTR, в том числе с весами GIM и MINIMA: одна строка конфигурации меняет обучение, архитектура та же.
- **Плотные** — MINIMA-RoMa (по умолчанию) и RoMa v2: детектора нет вовсе, поэтому на смене сезона не рассыпается повторяемость ключевых точек.

Перебор всех семи проверенных ядер с измеренными числами — [RESEARCH_A_RESULTS.md](RESEARCH_A_RESULTS.md). Главный вывод: **целевое дообучение на инвариантность вида решает больше, чем сила общего матчера**.

Подробнее: [ARCHITECTURE.md](ARCHITECTURE.md), [PIPELINE.md](PIPELINE.md).

## Возможности

- Уточнение центра из грубого приора ±5 км до метрового уровня (на синтетике — практически до потолка георефы подложки).
- Восстановление **поворота** (курса) и **масштаба** → попутная оценка высоты, т.к. высота задана с погрешностью.
- **Многомасштабность** по высоте: базово 400–800 м, с оговорками — до 100–250 м (см. ограничения).
- **Честная неопределённость**: не просто точка, а точка + эллипс ошибки + возможность отказа `NOT_LOCALIZED` вместо уверенно-неверного ответа.
- **Мультигипотезность**: несколько кандидатов на грубом уровне для детекции неоднозначности на самоподобной местности.
- **Измеримый переход синтетика→борт**: стенд с лестницей возмущений внешнего вида показывает, при каком уровне appearance gap классика ломается и пора включать обученный матчер.
- **Замеренная работа на реальных снимках**: одна команда прогоняет набор с подтверждённой истиной и даёт таблицу с разделением вины этажей, CSV и оверлеи; поведение заморожено золотым набором, сторож ловит регрессии поимённо.

## Ограничения

Честный список — эти границы **не лечатся «лучшим матчером»**, это свойства задачи:

1. **Потолок абсолютной точности задаёт подложка.** Esri/Mapbox/Google имеют собственную ошибку геопривязки порядка единиц метров. На синтетике ты упрёшься не в алгоритм, а в то, насколько точно сама подложка знает свои координаты. Относительная точность (кадр↔подложка) выше абсолютной. Для суб-метровой абсолютной точности нужны контрольные точки/калибровка.

2. **Appearance gap на реальных снимках.** Сезон (снег/зелень/убранные поля), освещение и тени, возраст подложки (новые дома/дороги), дымка, спектральные различия сенсора. Классический SIFT по сырой яркости на этом разваливается.

   **Что измерено (2026-07-29).** Смена сезона — самый тяжёлый случай, и он поддался только плотному ядру с дообучением под инвариантность вида: апрельский кадр против летней Esri взят за 4.9 м там, где базовое ядро даёт 6 инлайеров. Но взят **один кросс-сезонный кадр из двух**, а самих таких кадров в наборе всего два — этого мало для вывода. Перебор семи ядер с числами — [RESEARCH_A_RESULTS.md](RESEARCH_A_RESULTS.md). Границу лечит не только матчер: вторая половина решения — подложка, снятая в сезон кадра.

3. **Низкие высоты (100–250 м) — информационный дефицит.** С падением высоты footprint сжимается (на 100 м ≈ 34 м земли), и такой участок часто просто не содержит уникальной структуры: поле, крыша, отрезок дороги, лес, вода выглядят одинаково в тысячах мест. Одиночная абсолютная локализация из широкого приора ±5 км в однородных сценах на низкой высоте **принципиально плохо поставлена**. Правильное поведение — чаще отказывать. Практическое решение — последовательностный режим (VO + периодическая привязка) или более узкий приор — отсюда и регламент допустимой погрешности от высоты (рабочий конверт в [JOURNAL.md](JOURNAL.md)): на 100 м это ~500 м, а не ±5 км.

4. **Разрыв разрешений на низких высотах.** На 100 м GSD кадра ~3 см/px против ~0.3–1 м/px у открытой подложки — кадр в 5–15 раз детальнее. Вся высокочастотная детализация выбрасывается при приведении к разрешению подложки; совпадают только те частоты, что есть в референсе.

5. **Параллакс и рельеф.** Допущение плоской земли деградирует с понижением высоты: здание 20 м — это 3% от 600 м, но 20% от 100 м. Высокие объекты «заваливаются», крыши смещены относительно оснований — систематические (не случайные) невязки, которые RANSAC не вычищает. Нужен DEM/DSM или опора на планарно-доминантные области.

6. **Самоподобная / повторяющаяся местность.** Регулярная застройка, поля, лес, вода дают ложные совпадения. Смягчается приором позиции как ограничением и мультигипотезностью, но полностью не устраняется.

7. **Ротационная инвариантность retrieval.** DINO/CLIP не инвариантны к повороту из коробки — это надо закладывать осознанно (аугментация индекса), иначе кадр под большим yaw не найдётся.

## Точность: чего ожидать (ориентировочно)

| Режим | Условия | Ожидаемая ошибка центра |
|---|---|---|
| Синтетика, 400–800 м | кроп из той же подложки | до потолка георефы подложки (единицы м), относительно — субпиксель |
| Синтетика, 100–250 м | кроп из той же подложки | так же высоко (разрыва разрешений нет) |
| Борт, 400–800 м, уникальная сцена | плотное ядро, свежая подложка | **измерено: медиана 8.4 м** на 16 кейсах, лучшие 1–4 м |
| Борт, 400–800 м, смена сезона | плотное ядро с дообучением под вид | **измерено: 4.9 м** на одном кадре из двух; на втором — честный отказ |
| Борт, 100–250 м, однородная сцена, приор ±5 км (**вне конверта** для этой высоты) | одиночный кадр | часто `NOT_LOCALIZED` (дефицит информации) |
| Борт, низкая высота, последовательность | VO + периодическая привязка | стабильная траектория, точность на якорях |

Числа ориентировочные и зависят от местности; итоговый арбитр — [синтетический стенд](TESTING.md) на твоих данных.

## Стек и требования

- **Python 3.10+**, NumPy, OpenCV (геометрия, классический матчинг, ECC-refinement), Pillow.
- **PyTorch** + torchvision (DINOv2/MegaLoc, обученные матчеры), опц. TensorRT для ускорения инференса.
- **Плотные ядра** (`romatch`, `romav2`) — ставятся с `--no-deps`: их штатный список тянет `opencv-python`, конфликтующий с нужным проекту `opencv-contrib-python`.
- **FAISS** (ANN-индекс retrieval), опц. hnswlib.
- **requests** (загрузка тайлов подложки).
- **GPU**: NVIDIA RTX 4090 (24 GB) — тянет плотные матчеры (RoMa/LoFTR), батчевый retrieval и мультигипотезность; латентность не является ограничением, приоритет — точность.

Классический пайплайн (фаза «синтетика») работает и без GPU.

from aero_geoloc import localize, Camera, Prior

result = localize(
    image="frame.jpg",
    camera=Camera(image_width=1024, image_height=1024, focal_mm=16, sensor_width_mm=23.5),
    prior=Prior(lat=55.751, lon=37.618, sigma_m=5000,

## Дорожная карта / направления доработки

Актуальный порядок работ и обоснование приоритетов — [ROADMAP.md](ROADMAP.md);
ниже сводка направлений.

**Сделано** (было в этом списке как план): боевые веса матчеров и энкодера
подключены и **перебраны** — LoFTR, GIM×2, MINIMA×3, RoMa v2
([RESEARCH_A_RESULTS.md](RESEARCH_A_RESULTS.md)); реальные бортовые кадры с
подтверждённой истиной стали измеримым тестом на 16 кейсов; плотное ядро стало
базой; плотные DINOv2-фичи применены — но не как матчер, а как **сигнал качества**
вместо NCC.

**Осталось:**

- **Кросс-сезон целиком.** Взят один кадр из двух; направление «искать ядро
  посильнее» исчерпано. Дальше — дообучение под наш домен либо подложка, снятая
  в сезон кадра.
- **Пороги на объёме данных.** Порог плотного ядра держится на запасе в 13
  инлайеров, порог сигнала качества — на одном кадре. Нужны данные, а не идеи.
- **Учёт рельефа** (DEM/DSM) для коррекции параллакса высоких объектов на низких
  высотах (в `sequence.py` заложено, данных рельефа пока нет).
- **Калибровка абсолютной точности** по наземным контрольным точкам
  (пол `systematic_floor_m` в `quality.py` уже есть) — если нужен суб-метр.
- **Сервисная обвязка**: REST/gRPC API, батч-обработка, кэш индекса по регионам.
