# Данные в хранилище obs://orto (cloud.ru OBS)

Инвентаризация бакета `orto` объектного хранилища cloud.ru (endpoint
`obs.ru-moscow-1.hc.sbercloud.ru`) по состоянию на 21.08.2026. Доступ настроен
с `sbermainframe` через obsutil (см. инструкцию в конце документа). Данные
относятся к проекту optical-navigation (см.
[AUDIT_OPTICAL_NAVIGATION.md](AUDIT_OPTICAL_NAVIGATION.md)) и пригодны для
обучения/оценки матчеров в нашем `image_localization`.

## 1. Обзор бакета

| Префикс | Объём | Файлов | Содержимое |
|---|---:|---:|---|
| `obs://orto/frame-dataset/` | 149.5 ГБ | 47 640 | Синтетические кадры камеры БПЛА (PNG) + артефакты прогонов |
| `obs://orto/orto/` | 876.9 ГБ | 163 | Исходные ортофотопланы GeoPackage (~147 растров + aux.xml) |

(не инвентаризировались).

## 2. frame-dataset — синтетические кадры (149.5 ГБ)

Кадры отрендерены симулятором optical-navigation из ортофотопланов раздела 3:
по маршруту и позе камеры из растра вырезается вид «как с борта». Структура:

```text
frame-dataset/
├── <raster>/                        # 12 наборов съёмок
│   └── focal16_22.3_14.9_<h>_pitch<p>_v50_dt0.2/   # ~20 конфигураций
│       └── frame_NNNNNN.png         # ~200 кадров, шаг нумерации 27
├── _match_artifacts/                # визуальные артефакты прогонов (0.4 ГБ)
└── *_summary.xlsx                   # сводки eval разных конфигураций
```

### 2.2. Сетка конфигураций внутри набора

Имя папки кодирует параметры: `focal16_22.3_14.9_<высота>_pitch<наклон>_v50_dt0.2`
(фокус 16 мм, сенсор 22.3×14.9 мм, скорость 50, шаг 0.2 с).

- **Высоты**: 75, 100, 150, 200, 300, 500, 700 м.
- **Наклоны (pitch)**: 0, 15, 30, 40° — большие наклоны только на высотах ≤ 200 м.
- Итого ~20 конфигураций × ~200 кадров = ~4 000 PNG на набор.

Сетка заметно шире того, что прогнано в eval на sbermainframe (там покрыты
только 100–300 м при pitch 0–15°): высоты 500–700 м и наклоны 30–40° ещё
не оценивались.

**Ground truth**: координаты в PNG не зашиты — pose CSV
(`step,height_m,lat,lon,yaw_deg,pitch_deg,roll_deg`) лежат в репозитории
optical-navigation, `simulator/output/video-dataset/<raster>/<experiment>/`.
Номер в имени кадра (`frame_002210.png`) соответствует `step=2210` в CSV.

### 2.3. Прочее в frame-dataset

- `_match_artifacts/real/…` — визуальные артефакты прогонов на **реальных**
  полётных данных (например, `h_1400_pitch_60_ins0_100_range_20.0-300.0`:
  высота 1400 м, pitch 60°), по шагам: `map.png` и др. Полезно как референс
  того, что сервис видит на реальных, а не синтетических кадрах.
- `*_summary.xlsx` в корне — сводки eval-конфигураций, которых нет в локальных
  результатах на sbermainframe: `nowarp`, `imgsize_1024`, `min_inliers_10`.

## 3. orto — исходные ортофотопланы (876.9 ГБ)

145 геопривязанных растров GeoPackage по 0.6–28.4 ГБ на **66 площадках**
(в таблицах ниже — 844 ГБ; остаток до 876.9 ГБ — служебные объекты и
`*.aux.xml`). Даты съёмок — 2019–2023, представлены **все четыре сезона**,
включая зимние (январь–март: 20 растров).

### 3.1. Схема имени файла

```text
<ID площадки>_<F|GNSS>_<дата>_<индексы участка>_<серия>_<№>_<камера>_<фокус>.gpkg
Пример: 47_F_2022.10.16_14.0_1_4_SA6000_20mm.gpkg
```

- **ID площадки** — номер 2–99 либо код города (`GTKAZ`, `GTNN`, `GTUH`);
- **F / GNSS** — тип съёмки (фотограмметрия / с GNSS-привязкой);
- **индексы участка** (`14.0`, `2.0-3.0`, `5.1-5.2`…) — зона внутри площадки.
  **Важно:** одинаковый ID ещё не значит одинаковую территорию — у площадки
  бывают разные участки (например, `4_F` 2021 г. — участок 6.0, а 2023 г. —
  10.2). Для кросс-сезонных пар сверять и участок; окончательно пересечение
  проверяется по bounds растров;
- **камера_фокус**: SA6000 20/21 мм (основная, ~110 файлов),
  SRX1/SRX1R2/SRX1RM2 35 мм, Leica Q2 28 мм, единичные SN5 и KS (архив
  2019–2020 гг.).

## 4. Что с этим делать (рекомендации)

1. **`frame-dataset` тянуть целиком** — 150 ГБ помещаются на диск sbermainframe
   (свободно ~700 ГБ) и нужны для воспроизведения/расширения eval.
2. **`orto/` качать точечно** — целиком не влезет; в первую очередь нужны

   материал для следующего раунда eval, в том числе для сравнения их

## 5. Инструкция: как работать с obs://orto

### 5.1. Что уже настроено

На `sbermainframe` установлен **obsutil 5.8.3** (`~/.local/bin/obsutil`) и
настроен конфиг `~/.obsutilconfig` (endpoint + AK/SK; права 600). Исходные
креды лежат в `~/projects/ml/optical-navigation/obsutilconfig/` — каталог
добавлен в `.gitignore`, **в git не коммитить**. Рабочая пара ключей — из
`obsutilconfig_aws.txt` (AK 20 символов / SK 40); 64-символьные значения из
первого файла к OBS не подходят.

Если `obsutil` не в PATH текущей сессии — вызывать по полному пути
`~/.local/bin/obsutil` или добавить `export PATH=$HOME/.local/bin:$PATH`.

### 5.2. Базовые команды

```bash
# проверить доступ (список бакетов)
obsutil ls -s

# верхний уровень префикса (только папки и файлы первого уровня)
obsutil ls obs://orto/frame-dataset/ -d

# рекурсивный список (осторожно: 47 тыс. объектов)
obsutil ls obs://orto/frame-dataset/ -limit=100

# скачать один файл
obsutil cp obs://orto/orto/GTNN_F_2023.10.25_2.0_2_1_SA6000_20mm.gpkg \
  ~/projects/ml/optical-navigation/data/orto/ -p=4

# синхронизировать префикс (докачивает недостающее, можно перезапускать)
obsutil sync obs://orto/frame-dataset/GTNN_F_2023.10.25_2.0_2_1_SA6000_20mm \
  ~/projects/ml/optical-navigation/data/frame-dataset/GTNN_F_2023.10.25_2.0_2_1_SA6000_20mm \
  -p=4 -j=4
```

Ключи: `-p` — потоков на файл, `-j` — параллельных файлов, `-limit` — предел
списка (`-limit=0` — без предела), `-d` — не рекурсивно.

### 5.3. Правила при больших загрузках

1. **Только в tmux** — канал идёт через гостевой Wi-Fi, обрывы вероятны;
   `obsutil sync` при перезапуске докачивает недостающее:

   ```bash
   tmux new -s obs-sync
   obsutil sync obs://orto/frame-dataset ~/projects/ml/optical-navigation/data/frame-dataset -p=4 -j=4
   # Ctrl+B, D — отсоединиться; tmux attach -t obs-sync — вернуться
   ```

2. **Оценивать объём заранее** (свободно ~700 ГБ): полный `frame-dataset` —
   150 ГБ (~4–5 ч при 10 МБ/с), полный `orto/` — 877 ГБ, не влезет.
3. **Один эксперимент для smoke-теста** — это ~200 PNG (~0.7 ГБ), качается
   минуты: удобно для проверки пайплайна перед полной синхронизацией.
4. Прямое чтение из OBS в eval-ноутбуках (obsfs) в документации
   optical-navigation помечено как медленное — для прогонов данные сначала
   скачивать на локальный диск.
5. Логи obsutil — `~/.obsutil_log/`, при странностях смотреть туда.

### 5.4. Откуда взялись креды

AK/SK выпускаются в консоли cloud.ru: *IAM → Мои учётные данные → Ключи
доступа*. При смене ключей — обновить `ak=` и `sk=` в `~/.obsutilconfig`
(или положить новый файл в `obsutilconfig/` и повторить настройку).
