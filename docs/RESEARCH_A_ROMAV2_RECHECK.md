## 1. Гипотеза

**Отрицательный результат RoMa v2 — артефакт фильтра, а не свойство модели.
Порог `min_conf = 0.5`, унаследованный от v1, обрезает распределение `overlap`,
которое у v2 живёт на другой шкале. Модель не была измерена.**

### 1.1. Доказательная база

**(а) Код.** `aero_geoloc/matcher.py`, класс `RoMaV2Matcher`:

```python
def __init__(self, *, max_samples: int = 2048, min_conf: float = 0.5, ...)
...
corr = Correspondences(pts_q, pts_r, overlaps.reshape(-1), evidence=evidence)
keep = corr.conf >= self.min_conf          # ← overlap >= 0.5
return corr.take(keep) if not keep.all() else corr
```

**(б) Наши же измерения.** `RESEARCH_A_RESULTS.md` §4: «`overlap` **0.03–0.08**»
и «на реальных парах — **0–29 соответствий** и ни одной позы». Всё распределение
лежит на порядок ниже порога — «0–29» есть в точности хвост, случайно проскочивший
0.5. RANSAC получает горсть некоррелированных точек, позы нет по построению.

**(в) Первоисточник.** RoMa v2, раздел 4.1, ур. 6:
`p̂^{A↦B} = max(𝟙_{p^{A↦B} > 0.05}, p^{A↦B})`.
**Авторский порог — 0.05.** Мы поставили в 10 раз выше. Вдобавок выше порога
распределение у авторов **плоское**: значение `overlap` как вес не используется
вовсе, из него только сэмплируют.

**(г) Почему контроль не поймал.** На паре «шум со сдвигом» медиана `overlap`
**0.97** при минимуме 0.20 — фильтр пропускает почти всё, интеграция выглядит
исправной. Контроль проверил `to_pixel_coordinates` и геометрию, но не диапазон
шкалы. Это дыра в контроле, а не в интеграции.

**(д) Почему у v1 та же строка безобидна.** У `RoMaMatcher` после `sample` `conf` —
**константа 1.0** (задокументировано в docstring класса), и `keep` пропускает всё.
Один и тот же порог: для v1 — no-op, для v2 — глушилка.

**(е) Расхождение с литературой.** По собственным числам авторов v2 на нашем классе
данных заметно **сильнее** v1: AerialMegaDepth EPE 4.12 против 25.05 (−84%),
SatAst AUC@10px 37.0 против 23.5. У нас записано: v2 — ноль поз на всех 16 кейсах,
v1+MINIMA — 16/16. Ноль поз **на лёгких внутрисезонных кейсах**, где даже
LightGlue даёт десятки инлайеров, для SOTA-матчера физически неправдоподобен.

### 1.2. Что ещё под вопросом из-за той же строки

- Вывод «`overlap` антикоррелирован с верностью» (`Ufa3`: 0.053 у верной пары
  против 0.082 у ложной) считался на обрезанном хвосте — **невалиден**.
- Проверка гипотезы про цвет («с настоящим цветом хуже: 0.010 против 0.057») шла
  через тот же фильтр — **невалидна**. Заодно снимается сама гипотеза: v2
  обучался с grayscale-аугментацией p = 0.1, серый вход для него штатен.
- Главный вывод трека A — «обучение важнее архитектуры» — опирается на три пары.
  Пара «MINIMA-RoMa 1437 против RoMa v2 0» под вопросом; две другие
  (MINIMA-LightGlue 173 против GIM-LightGlue 0; MINIMA-LoFTR против LoFTR)
  не затронуты. **Вывод не рушится, но одна из трёх опор шатается.**

### 1.3. Оговорка против самообмана

Гипотеза не гарантирована. Наблюдённое `overlap_mean = 0.03–0.08` — среднее по
2048 сэмплированным парам **до** фильтра, и оно ниже даже авторского порога 0.05.
Это может означать и то, что модель честно не считает пару ко-видимой — что
согласуется с признанием авторов «**satellite images are OOD for most matchers
(including RoMa v2)**». Поэтому Э1 меряет **распределение целиком**, а не среднее,
и обязательно включает лёгкий внутрисезонный контроль: только он разделяет
«фильтр съел» и «модель не видит».

## 2. Патч

Минимальный, только `aero_geoloc/matcher.py`, только `RoMaV2Matcher`.

**П1. Развести пороги v1 и v2.** Не наследовать 0.5. Ввести отдельную константу
модуля с комментарием-ссылкой на ур. 6 статьи:

```python
#: Авторский порог overlap в RoMa v2 (arXiv:2511.15706, §4.1, ур. 6). НЕ 0.5:
#: у v1 conf после sample — константа 1.0, и порог 0.5 там no-op, а здесь
#: overlap живёт в районе сотых и порог 0.5 обрезает всё.
ROMAV2_MIN_OVERLAP = 0.05
```

и `min_conf: float = ROMAV2_MIN_OVERLAP` в `RoMaV2Matcher.__init__`.
`RoMaMatcher` (v1, `minima_roma`) **не трогать**.

**П2. Логировать распределение `overlap` до фильтра.** В `evidence` рядом с
`overlap_mean` добавить перцентили и доли — среднее по определению не показывает,
съел ли фильтр хвост:

```python
ov = overlaps.detach().float().reshape(-1)
q = self._torch.quantile(ov, self._torch.tensor([0.1, 0.5, 0.9, 0.99], device=ov.device))
evidence.update({
    "overlap_p10": float(q[0]), "overlap_p50": float(q[1]),
    "overlap_p90": float(q[2]), "overlap_p99": float(q[3]),
    "overlap_frac_gt005": float((ov > 0.05).float().mean()),
    "overlap_frac_gt050": float((ov > 0.50).float().mean()),
    "n_sampled": int(ov.numel()),
})
```

**П3. Не выбрасывать четвёртый выход `sample()`.** Сейчас
`matches, overlaps, precision_ab, _ = self._model.sample(...)`. По архитектуре
модель предсказывает Σ⁻¹ в обе стороны, и приложение E статьи использует обе —
почти наверняка это `precision_ba`. Проверить по сигнатуре в установленном
`romav2`, залогировать имя и форму. **Не заводить пока в pose** — это отдельный
эксперимент (см. §7).

**П4. Проверить рабочие разрешения.** Сейчас модель создаётся как
`RoMaV2(RoMaV2.Cfg(compile=self.compile))` — разрешения не задаются вовсе.
Авторы для оценки позы используют **coarse 800×800, fine 1024×1024**; для чистого
dense matching — 640×640. Выяснить дефолты `RoMaV2.Cfg` в установленной версии,
записать их в docstring и вынести в параметры конструктора, как это сделано у
`RoMaMatcher` (`coarse_res`, `upsample_res`). **Значения по умолчанию менять
только если дефолты пакета расходятся с авторскими для pose.**

**П5. Тест против ловушки.** Юнит-тест уровня «пороги v1 и v2 — разные
константы», чтобы правка не уехала обратно при следующем рефакторинге. Тест
пишется против числа из статьи, а не против «как получилось» (принцип из CLAUDE.md).

## 3. Инструмент: `scripts/probe_matcher.py`

Оракульная проба сейчас ad-hoc, а сравнивать надо с таблицей
`RESEARCH_A_RESULTS.md` §3 — значит нужен воспроизводимый прогон.

Вход: `--manifest`, `--cases`, `--matcher`, `--min-conf` (переопределение порога).
Действие: `oracle.alignment_for` → `north_up_crop` кадра → окно подложки того же
размера и центра → `matcher.match()` → `pose.estimate_similarity` → ошибка центра
против истины.
Выход: CSV со столбцами
`case, matcher, min_conf, n_sampled, n_pairs_after_filter, n_inliers, err_m,
overlap_p10, overlap_p50, overlap_p90, overlap_frac_gt005, precision_median, sec`.

Проба даёт матчеру **заведомо верное выравнивание** — она меряет ядро, а не тракт.
Именно поэтому её числа сопоставимы с §3 предыдущего отчёта.

## 5. Критерии

**Гипотеза подтверждена** (баг реален), если на `DRZ_00755`:
доля `overlap > 0.05` — десятки процентов, при `min_conf = 0.05` собирается поза
с ошибкой единиц метров и **сотнями** инлайеров. Тогда весь трек A по части
RoMa v2 открывается заново, и v2 становится кандидатом в базу под дообучение.

**Гипотеза не подтверждена** (провал реален), если даже при `min_conf = 0.0`
и авторских разрешениях v2 на `DRZ_00755` даёт < 50 инлайеров. Тогда искать
дальше по списку: разрешения `Cfg`, нормализация входа, порядок аргументов A/B,
масштабный разрыв кадр/окно. Только после этого объявлять отрицательный результат —
и уже честно, с ссылкой на признание авторов про OOD спутниковых снимков.

**Промежуточный исход**: позы есть, но слабее MINIMA-RoMa. Значит v2 работает,
а домен ему чужой — что согласуется и со статьёй, и с нашим главным выводом трека.
База под дообучение тогда остаётся MINIMA-RoMa, но Σ⁻¹ из v2 (см. §7) всё равно
стоит попробовать.

## 6. Чего не делать

- **Не менять `MIN_INLIERS_DENSE` на глаз.** Порог считается по распределению из
  Э3, ложное срабатывание рушит сборку безусловно.
- **Не трогать `RoMaMatcher` / `minima_roma`.** Ядро по умолчанию не меняется до
  результата Э3.
- **Не переписывать `RESEARCH_A_RESULTS.md` задним числом.** Прежний вывод
  пометить как невалидный с указанием причины и даты, но не удалять: он часть
  трека «как пришли», и сама ловушка ценнее вывода.
- **Не смешивать с Σ⁻¹** (§7) — иначе непонятно, что дало эффект.

## 7. Отложенное: Σ⁻¹ во взвешенном RANSAC

> **Исполнено 2026-08-21, результат отрицательный** — эффект статьи не
> переносится на 4-DoF подобие с ECC; как сигнал качества Σ⁻¹ не разделяет
> верную и ложную пары на трудной части набора. Числа и разбор —
> `RESEARCH_A_RESULTS.md` §8.

Отдельный эксперимент, после Э3, применим к любой конфигурации на v2.

RoMa v2 отдаёт на каждую пару матрицу точности 2×2 — обратную ковариацию ошибки
координаты. Авторы заводят её в **скоринг MSAC внутри LO-RANSAC** и в
пост-рефайнмент; на Hypersim это даёт **AUC@1° 54.9 → 76.4** (+21.5). У нас Σ⁻¹
уже приходит наружу и сводится к `precision_median` в диагностике.

Два ограничения из статьи: Σ⁻¹ обучена только на ко-видимых участках с
`‖r‖ < 8 px` — для грубых выбросов бессмысленна, отбраковку по-прежнему делают
`overlap` и RANSAC; полная 4×4 ковариация аппроксимируется блочно-диагональной
через обратное направление.

Потенциальный побочный выигрыш, важный именно нам: Σ⁻¹ — кандидат в связку
качества, где сейчас `dino ≥ 0.35` держится с запасом 0.027 на одном кадре.

## 9. Дополнения по итогам второго ревью (2026-08-21, перед исполнением)

Утверждения §1.1 сверены с кодом — все подтвердились (`min_conf = 0.5` на
`matcher.py:637`, фильтр на :680, `Cfg` без разрешений на :648, четвёртый выход
выброшен на :660). Плюс четыре дополнения к плану и находки из исходников
установленного пакета `romav2`, от которых зависит интерпретация Э1–Э2.

**Д1. Порог ур. 6 живёт в модели, а не в `sample()`.** По исходникам пакета:
`sample()` порога **не применяет** — сэмплирует `torch.multinomial`
пропорционально сырому overlap с KDE-балансировкой. Уплощение ур. 6
(`overlap[overlap > t] = 1.0`) сидит в `_map_confidence` внутри `match()` и
управляется `model.threshold`, который задаётся `apply_setting`:
у бенчмарк-настроек (`mega1500`/`satast`/…) он равен **0.05**, у дефолтного
`precise` — **None**. Мы работали в `precise`: уплощения не было, сэмплирование
шло по сырым сотым, а сверху резал наш фильтр 0.5. Следствие для патча:
воспроизводить авторский режим надо **двумя** ручками — `model.threshold = 0.05`
(веса сэмплирования) и внешний `min_conf = 0.05` (фильтр), а сырое поле мерить
при `model_threshold = None`.

**Д2. Сводку мерить по полному полю, а не только по сэмплам.** `preds` отдаёт
сырые логиты головы (`confidence_AB`), так что перцентили П2 считаются от
**всего поля** до сэмплирования и до уплощения — только они разделяют «модель
не видит» и «фильтр съел». Перцентили по 2048 сэмплированным парам оставить
рядом: они показывают, что реально получает поза.

**Д3. Разрешения пакета.** `precise` = вход 800×800, уточнение **1280×1280**,
bidirectional — не грубее авторского режима позы (800/1024). Менять дефолт
незачем; `setting` вынесен в параметр конструктора.

**Д4. К Э1 добавлен четвёртый кейс — большой кадр (`Volgograd3`).** Тройка
плана целиком из малых окон (~430 px); окно Волгограда ~1300 px проверяет
поведение внутреннего ресайза v2 на наших больших окнах. Истина у кейса
ручная — оракульный курс берётся из позы пайплайна (`--poses eval_out/eval.csv`).

**Д5. Прецедент ловушки уже есть в проекте — в обратную сторону.**
`MIN_INLIERS_HARD = 8`, перенесённый с разреженных ядер на плотное, пропустил
два ложных срабатывания, из чего родился `MIN_INLIERS_DENSE = 185`
(веха в `docs/JOURNAL.md`). Класс ошибки «порог, перенесённый между иначе
откалиброванными величинами» подтверждён теперь двумя экземплярами.

**Д6. Уточнение к Э3.** Жёсткий порог 185 сидит не в CLI, а в `quality.assess`
(`hard_inlier_threshold` распознаёт плотное ядро по `hasattr(matcher,
"max_samples")` — у `RoMaV2Matcher` он есть). Флаги «безгейтового» прогона его
не отключают: статусы будут `low_confidence`, и это нормально — распределения
считать по столбцам `n_inliers`/`err_m`, которые пишутся независимо от статуса.
