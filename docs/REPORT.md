## 1. Задача и принципы

**Вход:** надирный (вертикально вниз) снимок с БПЛА, приблизительные координаты
съёмки с известной погрешностью σ, масштаб кадра (GSD напрямую, либо высота и
параметры камеры, либо EXIF).
**Выход:** координаты центра кадра, курс, оценка высоты, полигон отпечатка на
карте — и **основания этому верить**: эллипс ошибки и статус.

Архитектура двухэтажная:

```
снимок ──► Этаж 1 (retrieval)              ──► top-K клеток-кандидатов
           MegaLoc → PCA→1024 → FAISS/HNSW

       ──► Этаж 2 (точная поза)            ──► преобразование кадр→подложка
           матчер → RANSAC-подобие → ECC

       ──► связка качества                  ──► LOCALIZED / LOW_CONFIDENCE /
           эллипс ∧ инлайеры ∧ dino-косинус     NOT_LOCALIZED
```

Принципы, на которых всё держится (полный список — [ARCHITECTURE.md](ARCHITECTURE.md)):

1. **`Georef` — единственный мост «пиксель ↔ координата».** Никакой географии в
   других модулях.
2. **Приоры — ограничения, а не подсказки.** Решение вне диска ±3σ или с
   масштабом вне допуска отбрасывается целиком; «подтянуть к приору» запрещено —
   именно это порождает уверенно-неверные точки.
3. **Матчер сменный.** Всё выше него не зависит от реализации; за проект ядро
   менялось семь раз без правок в геометрии, стенде и ретривале.
4. **Честный отказ дороже красивой точки.** `NOT_LOCALIZED` — легитимный исход.
5. Пиксельные координаты — «центр пикселя», как в OpenCV.
6. Доверие не подделывается: статусы калиброваны измерениями, а не желаемым.

### 1.1. Полная схема: от снимка до отчёта

Каждый блок отсылает к разделу статьи; ветки `└─` — точки, где пайплайн честно
останавливается вместо того, чтобы выдать сомнительную точку.

```
ВХОД ································································· §2
  снимок · приор lat/lon ± σ · масштаб: GSD | высота+камера | EXIF
        │  request.py: footprint = GSD·W; GPS из EXIF ≠ приор; контроль надира
        ▼
ПОДЛОЖКА ····························································· §3
  проба покрытия (9 тайлов) → выбор z_fine: mpp(z) ≈ GSD, спуск с заглушки
  └─ съёмки нет до z14 ────────────────────────────────► NOT_LOCALIZED
        │  resample_to_mpp (INTER_AREA): 4000×3000 @ 3 см → ~330×250 @ 0.37 м
        ▼
ЭТАЖ 1 · RETRIEVAL ··················································· §5
  офлайн (кэш .npz): район 1.5σ → клетки ≈ footprint (перекрытие 50%,
    ×8 поворотов без курса) → MegaLoc 8448-D → PCA 1024-D → FAISS/HNSW
  онлайн: кадр (−yaw) → тот же энкодер → PCA → k-NN → top-15 + уникальность
  └─ уникальность < порога (самоподобие) ──────────────► NOT_LOCALIZED
        │  15 кандидатов с готовыми георефами
        ▼
ЭТАЖ 2 · ПОЗА — цикл по всем 15 кандидатам ··························· §6–7
  окно из тайлов ~430…3600 px (потолок 4000)
  → матчер MINIMA-RoMa: плотное поле warp + certainty → 2048 пар
  → RANSAC-подобие 4 DoF (порог 6 px) → инлайеры
  → гейты кандидата: ≥ 6 инлайеров · масштаб в допуске · центр в ±3σ
  └─ ни один кандидат не прошёл ───────────────────────► NOT_LOCALIZED
        │  победитель = максимум инлайеров
        ▼
REFINEMENT — только победителю ······································· §8
  ECC-субпиксель (0.505 → 0.011 px) + цикл масштаба → H_est = s·H_prior
  └─ финальный гейт: центр вне ±3σ исходного приора ────► NOT_LOCALIZED
        │
        ▼
СВЯЗКА КАЧЕСТВА ······················································ §10
  эллипс ≤ 3 м  ∧  инлайеры ≥ 185 (плотное ядро) / 8  ∧  dino-косинус ≥ 0.35
  └─ хотя бы один сигнал не прошёл ────────────────────► LOW_CONFIDENCE
        │  LOCALIZED
        ▼
СЧИТЫВАНИЕ · GEOREF ·················································· §9
  центр lat/lon · курс θ · высота H_est · полигон отпечатка · эллипс 1σ
        │
        ▼
ОТЧЁТ ································································ §13
  report.html (вердикт + 4 панели проверки глазами) · result.json
  footprint.kml (Google Earth) · footprint.geojson (QGIS)
```

Замечание к веткам: отказ на любом уровне — это не «пустой» выход, а такой же
полноценный отчёт с причиной и советом, что поменять во входных данных (§13).

## 2. Вход: снимок и что о нём известно

Модуль `aero_geoloc/request.py` собирает вход из трёх источников по убыванию
надёжности (подробно — [TOOL_PLAN.md](TOOL_PLAN.md), этап T2):

1. **Явный GSD** (`--gsd`, м/пиксель) — прямо задаёт масштаб.
2. **Высота + камера**: `f_px = focal_mm · W / sensor_mm` (или из FOV:
   `f_px = (W/2)/tan(FOV/2)`), затем `GSD = H / f_px`.
3. **EXIF/XMP снимка** (`aero_geoloc/drone.py`): GPS-тройки «градусы-минуты-секунды»,
   `FocalLengthIn35mmFilm`, DJI-теги `RelativeAltitude`/`GimbalYawDegree`/
   `GimbalPitchDegree`.

**Footprint** (покрытие кадра на земле): `footprint = GSD × W`. Это число печатается
до запуска — неверный GSD даёт не отказ, а уверенно-неверный масштаб, и отпечаток
в метрах — единственное место, где такую ошибку видно сразу.

Два защитных правила, оба выстраданы живыми запусками:

- **GPS из EXIF никогда молча не становится приором.** Иначе система ищет кадр
  там, куда ей же указали, и успех ничего не доказывает. Нужен явный `--from-exif`,
  и отчёт помечает такой запуск как не-проверку.
- **Кадры вне надирной модели** (|наклон от надира| > 10°) помечаются до запуска:
  модель плоской земли и подобия к ним неприменима.

## 3. Подложка: XYZ-тайлы, загрузка и целостность

Модуль `aero_geoloc/basemap.py`. Источник — **Esri World Imagery**
(атрибуция: Esri, Maxar, Earthstar Geographics, and the GIS User Community),
стандартная XYZ-пирамида Web Mercator, тайлы 256×256, порядок `{z}/{y}/{x}`.

**Геометрия.** Истинное разрешение подложки на широте `lat` и зуме `z`:

```
mpp(lat, z) = 156543.034 · cos(lat) / 2^z     [м/пиксель]
```

**Сшивка окна без интерполяции.** Окно подложки собирается из целых тайлов и
вырезается **целочисленно**; `Georef` строится от фактического (выровненного)
центра. Подложка остаётся пиксель-в-пиксель настоящими тайлами — точную привязку
всегда даёт `pixel_to_lonlat`, а не приближение.

**Кэш** (`tiles/<провайдер>/<z>/<x>/<y>.jpg`) хранит сырые байты. Правила
целостности, каждое из которых закрывает реальную аварию:

- пустой файл читается как **промах**, а не как данные;
- готовый тайл **никогда не переписывается**: содержимое `(z,x,y)` неизменяемо,
  и это убирает целый класс гонок Windows (измерено: `os.replace` под
  одновременным чтением падает в 228 случаях из 300);
- битый тайл перекачивается ровно один раз, а не хоронит всю сборку карты.

**«Тайл есть, съёмки нет».** `max_zoom` провайдера — предел пирамиды, а не
гарантия покрытия: вне городов Esri на глубоких уровнях отдаёт HTTP 200 и серую
заглушку. Порог по дисперсии эту заглушку не отличает от воды (std заглушки 5.4
лежит внутри хвоста настоящей съёмки, минимум 3.0), поэтому `probe_imagery`
ставит **девять проб** — центр района и кольцо по краю — и признаёт уровень
пустым по двум независимым признакам: все пробы байт-идентичны (подпись
заглушки) либо ни одна не несёт структуры. `deepest_imagery_zoom` спускается до
уровня со съёмкой; нет нигде до z14 — честный отказ **до** сборки карты.

## 4. Выбор параметров поиска

Все параметры выводятся из входа; вручную крутить ничего не нужно
(`aero_geoloc/region.py`, `scripts/locate.py`).

| параметр | правило | почему |
|---|---|---|
| зум точного уровня `z_fine` | `mpp(z) ≈ GSD` кадра (ближайший) | матчер сравнивает сравнимое |
| зум карты района | грубее `z_fine`, клетка ≈ footprint | клетка = «один кадр земли» |
| клетка индекса | ≈ footprint кадра, перекрытие 50% | кадр не «падает между клеток» |
| радиус района | `clamp(1.5σ, 0.5…5 км)` | район обязан накрыть диск ±3σ приора |
| повороты клеток | ×8 (шаг 45°), если курс неизвестен; ×1, если известен | DINO-вектор не инвариантен к повороту |
| σ приора | регламент «высота → σ»: 100 м → 0.5 км, 300 м → 2 км, 600 м → 5 км | держит район в 200–500 клеток |

Регламент «высота → σ» — не эвристика, а измеренная граница гарантии: клетка ≈
footprint ∝ высоте, поэтому σ обязана расти с высотой, иначе число почти
одинаковых клеток выходит из надёжной зоны (см. [раздел 12](#12-границы-применимости)).

Карта района кэшируется в `.npz` с тегом конфигурации
(`tool_51.2100_6.1600_z18_r750_c321_o50_rot1_pca1024.npz`): вторая локализация в
том же районе идёт из кэша за секунды.

## 5. Этаж 1 — retrieval: «где примерно»

Задача — не точность, а отсечь 99% карты: превратить диск ±σ в **top-K = 15**
клеток-кандидатов. Разрешение этажа равно размеру клетки по построению — точность
рождается на Этаже 2. Полное обоснование — [RETRIEVAL.md](RETRIEVAL.md); код —
`aero_geoloc/retrieval.py` (`MegaLocEncoder`, `PCAReducer`, `TerrainIndex`,
`NumpyAnn`/`FaissAnn`).

### 5.1. Что происходит с кадром: НЕ режется, а сжимается в один вектор

Частый вопрос — «кадр тоже делится на тайлы?». **Нет.** На клетки нарезается
только **район подложки** (офлайн). Кадр целиком превращается в один
вектор-запрос за четыре шага:

1. **Приведение масштаба.** Кадр уже ресемплирован к разрешению подложки
   (`resample_to_mpp`, см. §6.1): например, 4000×3000 @ 3.1 см/пкс →
   ~330×250 @ 0.37 м/пкс. Этаж 1 работает с этой уменьшенной версией.
2. **Предповорот** (если курс известен): `warpAffine` вокруг центра на −yaw,
   края добиваются зеркальным отражением (`BORDER_REFLECT_101`) — кадр
   становится «севером вверх», как клетки индекса. Если курс неизвестен, кадр
   не крутится — вместо этого повёрнуты клетки (см. 5.3).
3. **Подготовка под ViT**: серый кадр реплицируется в 3 канала и ресайзится
   `INTER_AREA` в квадрат **322×322** (322 = 14·23 — сторона обязана быть
   кратной патчу ViT), затем ImageNet-нормализация.
4. **Энкодер → вектор 8448-D**, L2-нормированный.

### 5.2. MegaLoc изнутри: откуда размерность 8448

MegaLoc — готовая VPR-модель (visual place recognition), загружаемая через
`torch.hub` из `gmberton/MegaLoc`. Устройство:

- **Бэкбон DINOv2-B/14** режет вход 322×322 на патчи 14×14 → сетка 23×23 = 529
  патч-токенов, каждый — вектор признаков. Патч-фичи DINOv2 семантичны и
  устойчивы к освещению/сезону — то, что нужно для «кадр ↔ спутник».
- **Агрегация SALAD** (Sinkhorn-назначение поверх идеи NetVLAD): каждый из 529
  патч-токенов мягко распределяется по **64 обученным «словам»-кластерам**;
  на кластер накапливается остаток размерности **128**. Плюс отдельный
  глобальный токен **256-D**.
- Итог: `64 × 128 + 256 = 8448` — конкатенация, L2-нормализация. Косинус двух
  таких векторов — мера «то же ли это место», толерантная к умеренному сдвигу,
  сезону и экспозиции, но **не** к повороту (отсюда предповорот/аугментация).

Почему не сырой CLS-токен DINOv2: измерено, что на кросс-домене он топит верную
клетку в хвост ранжирования (ранг 506 из 2116 на `DRZ_19206`); MegaLoc с
обученной агрегацией поднимает её в top-2.

### 5.3. Нарезка района на клетки (офлайн)

`TerrainIndex.build` идёт регулярной сеткой по растру района:

- **клетка — квадрат `cell_px × cell_px`** на зуме карты района, где
  `cell_px · mpp ≈ footprint` кадра (например 321 px ≈ 120 м для съёмки с 90 м);
- **шаг сетки** `cell_px · (1 − overlap)` при перекрытии 50% — кадр, попавший
  «между клеток», всё равно накрыт какой-то клеткой почти целиком;
- каждая клетка тянется через тот же `basemap`-интерфейс (то есть сшивается из
  XYZ-тайлов), переводится в grayscale;
- при неизвестном курсе каждая клетка кодируется **8 раз** (повороты с шагом
  45°) — по записи на поворот; при известном курсе — 1 раз (карта в 8 раз
  дешевле, поэтому `--yaw` так важен);
- кодирование идёт **батчами по 8** (измерено: 10.0 → 5.1 мс/вектор);
- вместе с вектором сохраняются **гео-метаданные клетки**: центр lon/lat, зум,
  размер в пикселях, угол поворота. Именно они делают top-K сразу пригодным для
  Этажа 2 — каждый кандидат приходит с готовым геореференсом.

### 5.4. Как прямоугольный кадр сравнивается с квадратной клеткой

Ресайз в 322×322 (шаг 3 из 5.1) **анизотропно сжимает** прямоугольный кадр 4:3 —
одна ось «худеет» в ~1.33 раза. Клетка — настоящий квадрат со стороной ≈ большей
стороне footprint, то есть покрывает кадр плюс полосы сверху и снизу. Строгого
геометрического соответствия здесь нет и **не требуется**: VPR-дескриптор
агрегирует патчи в мешок «слов» и к такой деформации толерантен — это
подтверждено измеренными рангами верной клетки (top-1…top-15 на наборе), а
перекрытие 50% гарантирует существование клетки, где кадр лежит почти целиком.
Точную геометрию восстановит Этаж 2, где никакого сжатия в квадрат нет.

### 5.5. PCA: что на входе, что на выходе

- **Вход `fit`**: матрица `N × 8448` — сырые дескрипторы **всех клеток района**
  (например, 5184 × 8448). PCA обучается на клетках этого же района
  (randomized SVD), центр и компоненты сохраняются в `.npz` рядом с векторами.
- **Выход**: матрица `N × 1024` — проекция клеток на первые 1024 главные
  компоненты; поиск идёт по ней.
- **Запрос**: вектор кадра 8448-D проходит **тот же** редуктор (то же среднее,
  те же компоненты) → 1024-D. Совместимость проверяется при загрузке индекса по
  входной размерности PCA.
- Эффект измерен: память ÷8.2 (206→25 МБ на район), ранг верной клетки 49→15 —
  plain PCA отбрасывает шумовой хвост компонент. **Whitening выключен**: вопреки
  книжной эвристике VPR, здесь он вредит (ранг 49→334) — малые сингулярные числа
  хвоста оценены плохо, деление на них раздувает шум.

### 5.6. Поиск и сигнал уникальности

- **NumpyAnn** (по умолчанию): точный косинусный top-k через `argpartition` —
  O(N), на районных объёмах (сотни–тысячи клеток) неотличим по времени от ANN.
- **FaissAnn**: HNSW-граф (`M=32`, `efConstruction=200`), метрика inner product
  по L2-нормированным векторам ≡ косинус; O(log N) — для больших территорий и
  ротационной аугментации.
- **Уникальность** — зазор близости между top-1 и лучшим конкурентом, отстоящим
  дальше радиуса подавления (≈ footprint клетки): соседняя перекрывающаяся
  клетка — то же место, а не двойник, и не должна занижать сигнал. Кучный top-K
  на самоподобной местности (поля, лес, вода) даёт флаг отказа ещё до матчинга;
  порог калибруется по индексу Юдена на размеченном наборе.

## 6. Этаж 2 — матчинг: «где точно»

### 6.1. Детальный кадр против грубой подложки: 3–6 см на пиксель против 0.3–0.6 м

Это штатная, а не исключительная ситуация: у Esri самый детальный реальный
уровень — z19 ≈ 0.19 м/пкс (а вне городов чаще z18 ≈ 0.37 м/пкс), тогда как
кадр с 90 м имеет GSD ~3 см. Разрыв в детальности — **6–12 раз** по линейному
размеру.

Что делает пайплайн:

1. **Выбирается зум `z_fine`** — ближайший к GSD кадра, но не глубже реального
   покрытия: `zoom_for_mpp(GSD)` клампится потолком провайдера, а проба
   `probe_imagery` дополнительно опускает потолок там, где вместо съёмки
   заглушка (и цикл масштаба потом не может залезть обратно в пустоту).
2. **Кадр ресемплится вниз один раз** — `resample_to_mpp` (`camera.py`):
   коэффициент `scale = GSD / mpp(z_fine)` (например 0.031/0.375 ≈ 1/12),
   интерполяция `INTER_AREA` — площадное усреднение, корректный фильтр для
   даунсемпла без алиасинга. Кадр 4000×3000 @ 3.1 см превращается в
   ~330×250 @ 0.37 м/пкс; камера пересобирается под новый размер с тем же FOV.
3. **Избыточная детальность сознательно выбрасывается.** Матчинг идёт на
   разрешении подложки: разметка, машины, мелкая фактура крыш исчезают из обеих
   картинок одинаково, и матчер сравнивает крупную структуру — здания, дороги,
   контуры полей, теневой рисунок. Измеренно этого достаточно: кадры DRZ с GSD
   3.1 см сажаются по подложке z18 (в 12 раз грубее) с ошибкой 1–8 м.
4. **Ожидаемый масштаб после ресемпла ≈ 1**, поэтому гейт
   `Prior.scale_bounds` становится жёстким фильтром: поза с `s`, ушедшим от 1
   дальше допуска по высоте, отбрасывается.

Что при этом происходит с точностью. Поза оценивается в **пикселях подложки** и
переводится в метры через её mpp; субпиксельный ECC даёт невязки в доли пикселя,
то есть потолок случайной ошибки — доли mpp подложки (сантиметры–дециметры при
z18), а не GSD кадра. Практический пол точности задаёт не детальность кадра, а
**геопривязка самой подложки** — единицы метров. Иными словами: сверхдетальный
кадр не улучшает точность сверх подложки, но и грубая подложка не мешает
метровой точности — пока на ней различима структура.

Обратная сторона: чем грубее подложка относительно кадра, тем меньше остаётся
информации после даунсемпла — на однородной местности это приближает отказ по
самоподобию. Это честная цена, и лечится она только более детальной подложкой
(см. §12, п. 3).

### 6.2. Окно подложки: сколько грузим и с каким запасом

Продолжим сквозной пример: кадр после ресемпла — **~330×250 px** @ 0.375 м/пкс
(съёмка с 90 м, GSD 3.1 см, z18). Retrieval вернул 15 клеток-кандидатов; для
каждой строится своё окно.

**Формула размера** (`fine_margin_m` + `_fine_pass`, `localize.py`):

```
margin_m  = max(6·coarse_mpp, 0.15·footprint)      # запас вокруг кандидата
окно_px   = 2·(footprint/2 + margin_m) / mpp_fine  # квадрат, чётная сторона
потолок   = max_fine_window_px = 4000 px           # запас урезается, если не влезает
```

Запас решает две задачи. Во-первых, **центр кандидата — не центр кадра**: retrieval
знает место с точностью до клетки, истинный центр может лежать где угодно внутри
неё; слагаемое `6·coarse_mpp` — полклетки в метрах. Во-вторых, минимум `0.15·footprint`
не даёт окну выродиться. Верхний потолок 4000 px — измеренный предел: у матчера
бюджет точек фиксирован, и на слишком большом окне их плотность падает так, что
матч разваливается (кадр 2783 px: окно 3339 px → 21 инлайер, 3895 → 31, 5008 → **5**).

Числа для двух краёв набора:

| съёмка | кадр после ресемпла | margin | окно подложки |
|---|---|---|---|
| 90 м, GSD 3.1 см (DRZ) | ~330×250 px | ~19 м | **~430×430 px** |
| 500 м, GSD 6.5 см (Саратов) | ~2780×1860 px | ~78 м | **~3600×3600 px** (у потолка) |

Окно **сшивается из XYZ-тайлов** тем же путём, что и всё остальное (§3): берутся
все тайлы 256×256, пересекающие прямоугольник окна (для окна 430 px это ~4–9
тайлов, для 3600 px — ~15×15), выкладываются в мозаику, из неё целочисленно
вырезается квадрат — без интерполяции, с `Georef` от фактического центра.
Соседние тайлы «с запасом» отдельно не грузятся: запас уже заложен в размер окна,
а тайлы на его границе входят целиком в мозаику по построению.

Матчер получает две картинки в **одном масштабе**: кадр ~330×250 и окно ~430×430
(оба @ 0.375 м/пкс). Опциональный колпак `ResizedMatcher` (общий фактор на обе
картинки, точки возвращаются делением на фактор) в боевой конфигурации выключен —
у плотного ядра свой внутренний ресайз.

### 6.3. Что делает матчер: контракт и два устройства

Контракт один для всех десяти ядер реестра:

```python
corr = matcher.match(query_gray, ref_window_gray)
# → corr.pts_q [N×2], corr.pts_r [N×2]  — пары «пиксель кадра ↔ пиксель окна»
#   corr.conf [N]                        — уверенность каждой пары
#   corr.evidence                        — сводка матчера (например certainty-поле RoMa)
```

Реестр (`aero_geoloc/matcher.py`): `sift`, `akaze` (классика, без torch),
`lightglue`, `loftr`, `gim_lightglue`, `minima_lightglue`, `minima_loftr`,
`minima_roma`, `roma`, `romav2`. Веса скачиваются с проверкой провенанса
(`aero_geoloc/weights.py`): адрес, размер, лицензия и **число совпавших
тензоров** — несовпадение архитектуры падает с ошибкой, а не откатывается молча
на базовые веса. Внутри контракта живут два принципиально разных устройства.

**LightGlue (разреженный, «сначала точки — потом пары»).** Три шага:

1. **SuperPoint** независимо на кадре и на окне детектирует до **2048 ключевых
   точек** на каждом — углы, перекрёстки, контрастные пятна — и вычисляет каждой
   дескриптор.
2. **LightGlue** — трансформер с self- и cross-вниманием — сопоставляет два
   набора точек как задачу назначения: каждая точка кадра «смотрит» на все точки
   окна, и матрица совместимости даёт пары с уверенностью.
3. Наружу выходят только взаимно согласованные пары — обычно **сотни** на
   похожей паре картинок и единицы–десятки на трудной.

Слабое звено — шаг 1: пара существует, только если SuperPoint **повторил** одну
и ту же точку на обеих картинках. Кадр и спутниковая подложка сняты в разные
сезоны разными сенсорами — угол крыши, найденный на кадре, на подложке может
просто не задетектироваться. На кросс-сезонном `Ufa3` из-за этого вся цепочка
даёт 24 пары и 6 инлайеров — позы нет.

**MINIMA-RoMa (плотный, «поле соответствий без детектора»).** Устройство:

1. Обе картинки независимо приводятся к внутренним квадратам RoMa (грубый
   уровень **560×560**, уточнение **864×864**; координаты потом возвращаются в
   исходные пиксели через `to_pixel_coordinates`, поэтому раздельный ресайз
   геометрию не портит).
2. Сеть предсказывает **warp — плотное поле**: для *каждого* пикселя кадра —
   куда он попадает в окне, плюс попиксельная **certainty** (уверенность).
   Детектора нет вовсе: нечему «не повториться».
3. Из поля **сэмплируются 2048 пар** с вероятностью, пропорциональной certainty
   (`max_samples = 2048`); сводка поля до сэмплирования (`certainty_mean`,
   `certainty_cover`) уходит в диагностику.

Ядро дообучено проектом MINIMA на модально-инвариантных парах (RGB↔ИК,
RGB↔глубина, RGB↔рисунок…) — сеть учили считать «одним и тем же» изображения
радикально разного вида. Ровно это и нужно паре «летний спутник ↔ апрельский
кадр».

### 6.4. Почему победил MINIMA-RoMa, а не LightGlue

Сравнение измерено, а не предположено ([RESEARCH_A_RESULTS.md](RESEARCH_A_RESULTS.md)):

| | LightGlue | MINIMA-RoMa |
|---|---|---|
| поз найдено (16 кейсов) | 11/16 | **16/16** |
| кросс-сезон `Ufa3` (оракул) | 24 пары → 6 инлайеров | **2037 → 1437** |
| ложных | 0 | 0 |
| время на кадр | **8.4 с** | 22.6 с |

Причин две, и они разделяются экспериментом:

1. **Отсутствие детектора.** У разреженных ядер на кросс-домене рассыпается
   повторяемость ключевых точек — самый хрупкий этап всей цепочки. У плотного
   ядра этого этапа нет: соответствие предсказывается для каждого пикселя.
2. **Обучение, а не архитектура.** Тот же RoMa, но с обычным обучением
   (RoMa v2, даже с более сильным бэкбоном DINOv3) даёт на `Ufa3` **0** пар —
   а MINIMA-дообученный тот же самый RoMa даёт 1437 инлайеров. Аналогично
   MINIMA-LightGlue против GIM-LightGlue: 173 против 0. Вывод трека: **целевое
   дообучение на инвариантность вида даёт больше, чем сила общего матчера.**

Цена — втрое медленнее (~24 с против ~8 с на кадр), поэтому LightGlue оставлен
за флагом `--fast`.

### 6.5. Воронка отсева: сколько точек остаётся на каждом шаге

Сквозные числа реальных прогонов (MINIMA-RoMa):

```
плотное поле warp            ~всё изображение (каждый пиксель кадра)
  │  сэмплирование по certainty
  ▼
2048 пар                     (max_samples; меньше — если уверенных пикселей мало)
  │  порог conf ≥ 0.5
  ▼
~1500–2050 пар               n_correspondences в диагностике
  │  RANSAC-подобие, порог репроекции 6 px + гейты приора (масштаб, диск ±3σ)
  ▼
инлайеры                     ← ЗДЕСЬ разделяются верное и неверное место
  │  жёсткий порог качества: ≥185 (плотное ядро) / ≥8 (разреженное)
  ▼
принято → ECC-уточнение по инлайерам → эллипс, dino-косинус, статус
```

Что такое «инлайер» и как именно RANSAC его определяет — [§7.1](#71-что-такое-инлайер-и-по-какому-признаку-он-определяется).

Как выглядит эта воронка на верном и неверном месте — из диагностики реальных
запусков:

| случай | пар | инлайеров | доля | исход |
|---|---|---|---|---|
| верное место (`DRZ_00755`) | ~1900 | **876** | 46% | LOCALIZED, 1.4 м |
| верное место (`DRZ_06262`) | ~1900 | **1089** | 57% | LOCALIZED, 1.2 м |
| чужое похожее место (`DRZ_06262`, широкий приор) | 1508 | 154 | 10% | отказ гейта |
| пустая подложка (`DSC00045`, z19-заглушка) | 1920 | 22 | 1% | отказ гейта |

Ключевое свойство: **число пар почти не информативно** — RoMa честно сэмплирует
~2000 пар и на верном месте, и на заглушке. Информация в том, складываются ли
пары в **одно жёсткое подобие**: на верном месте согласованы 46–57%, на чужом —
1–10%. Поэтому решает RANSAC-воронка и порог 185, а не количество соответствий;
у LightGlue пропорции те же, но абсолютные числа на порядок меньше (сотни пар →
десятки–сотни инлайеров), и порог качества для него — 8.

### 6.6. Как выбирается финальное место из top-K кандидатов

Цикл по кандидатам (`localize`, `aero_geoloc/localize.py`) устроен так:

1. **Обрабатываются все 15 кандидатов, без раннего выхода.** Для каждого — своё
   окно (§6.2), матч, RANSAC, гейты: `min_inliers = 6`, масштаб в
   `scale_bounds`, центр в диске приора. Кандидат, не прошедший хотя бы один
   гейт, выбывает.
2. **Победитель — максимум инлайеров** среди выживших. Не «первый прошедший» и
   не «ближайший к приору»: сравниваются все, берётся поза с наибольшим числом
   геометрически согласованных пар.
3. **Дорогое уточнение — только победителю.** ECC и цикл масштаба гоняются один
   раз, на лучшем кандидате, а не на всех пятнадцати (если уточнённый проход
   вдруг не сошёлся, остаётся неуточнённая поза — отказываться от найденного
   места из-за refinement нельзя).
4. **Финальный гейт против исходного приора**: центр победителя обязан лежать в
   диске ±3σ, иначе отказ «решение вне диска приора».
5. Победитель уходит в **связку качества** (§10) — она может перевести его в
   `LOW_CONFIDENCE`, и тогда финального места нет.

**Что, если порог проходят несколько кандидатов?** Это норма, а не исключение, и
случая два:

- **Чаще всего это одно и то же место в нескольких копиях.** Клетки перекрыты на
  50%, и верный кадр «виден» из двух–четырёх соседних клеток сразу; их позы
  совпадают с точностью до сантиметров, и какая из копий победит — безразлично.
- **Опасный случай — два далёких места, оба прошедшие гейты.** Тогда побеждает
  то, где инлайеров больше, и **зазор между первым и вторым сейчас не
  проверяется** — это честное ограничение текущей версии. Защита от него
  трёхслойная и стоит *до* и *после* выбора: сигнал уникальности Этажа 1
  отказывает по самоподобию ещё до матчинга; конверт приора держит число
  почти одинаковых кандидатов малым; связка качества режет слабого победителя.
  Измеренный провал этой защиты известен ровно один — за конвертом приора
  (§12, п. 1): в переполненном районе чужое место набрало 268 инлайеров при
  пороге 185 и победило, притом что верное место лежало в карте.

**А если брать не top-15, а top-100?** Разобрано и не принято, по трём причинам:

1. **Цена линейна.** Каждый кандидат — это окно подложки плюс полный проход
   плотного матчера, ~1.5–2 с; top-15 укладывается в ~24 с на кадр, top-100 —
   минуты.
2. **Выигрыш почти нулевой: ранг верной клетки бимодален.** На измеренном наборе
   верная клетка либо в первых десятках (top-15 берёт), либо за сотнями —
   `train_SB_0023` даёт ранг 509–725, `DRZ_03642` в дефектном прогоне — 423.
   Диапазон 16–100, который top-100 добавляет, почти пуст: если Этаж 1
   промахнулся, он промахнулся сильно, и лечится это качеством дескриптора, а
   не глубиной перебора.
3. **Каждый лишний кандидат — лотерейный билет для ложной позы.** Гейты
   вероятностные: на 100 попытках шанс, что чужое место соберёт пороговое число
   инлайеров, выше, чем на 15. Есть и прямое измерение родственного эффекта:
   уплотнение сетки превратило top-15 в «15 копий одного места» и стоило потери
   `Volgograd3` — рост числа почти одинаковых кандидатов снижает разнообразие
   ровно тогда, когда оно нужнее всего. Связка «окно ↔ плотность сетки ↔ top-K»
   записана как открытая тройная задача ([ROADMAP.md](ROADMAP.md)): менять эти
   параметры поодиночке — измеренно хуже.

## 7. RANSAC-подобие (4 DoF) с приором-ограничением

Модель преобразования «кадр → подложка» — **подобие**: поворот θ, единый масштаб
s, сдвиг (tx, ty). Для пары надир↔надир это физически правильная модель, и её
ограниченность — сама по себе фильтр выбросов.

### 7.1. Что такое инлайер и по какому признаку он определяется

Матчер отдал N пар «пиксель кадра ↔ пиксель окна». Среди них есть верные, а есть
мусор — **аутлаеры**: пары, где сеть зацепилась за похожую текстуру, повторяющийся
узор застройки, тень или движущийся объект. Заранее неизвестно, какие есть какие,
и ни одна отдельная пара сама о себе этого не скажет.

Признак — **геометрическая согласованность с общей гипотезой**. Пусть `M` —
кандидатное подобие «кадр → окно». Пара `(p_q, p_r)` — инлайер, если точка
кадра, переведённая этим преобразованием, попадает почти точно в свою пару:

```
‖ M(p_q) − p_r ‖ ≤ 6 px          # порог репроекции (ransac_threshold_px)
```

Левая часть называется **репроекционной ошибкой** пары. 6 px на подложке z18 —
это ≈ 2.2 м на земле; всё, что промахивается дальше, — аутлаер: в подсчёт и в
финальную оценку позы такая пара не входит.

Остаётся вопрос: откуда взять `M`, если неизвестно, какие пары верные? Это и
решает **RANSAC** (RANdom SAmple Consensus, `cv2.estimateAffinePartial2D`):

1. случайно берётся **минимальный набор** — для подобия 4 DoF достаточно
   **двух** пар;
2. по ним аналитически строится гипотеза `M`;
3. считается, сколько из всех N пар согласованы с этой `M` по критерию выше, —
   это и есть **число инлайеров** гипотезы;
4. шаги 1–3 повторяются сотни раз; побеждает гипотеза с максимумом инлайеров;
5. финальное `M` пересчитывается методом наименьших квадратов уже **по всем
   инлайерам** победившей гипотезы — мусор на неё больше не влияет.

Почему это разделяет верное место и чужое. Верные пары порождены одной
физической сценой — они согласованы с одним и тем же подобием **все сразу**.
Ошибочные пары разбросаны хаотично: случайной гипотезе почти невозможно собрать
из них большой согласованный кластер, потому что жёсткая 4-параметрическая
модель не оставляет мусору свободы «сговориться». Отсюда картина из §6.5: на
верном месте согласованы 46–57% пар, на чужом похожем — 1–10% при том же общем
количестве.

Число инлайеров поэтому — главный геометрический дискриминатор пайплайна, и
используется он трижды: минимум `min_inliers = 6`, чтобы кандидат вообще
считался позой; выбор лучшего кандидата среди top-K; жёсткий порог связки
качества — 185 для плотного ядра / 8 для разреженного (§10).

### 7.2. Извлечение позы и гейты приора

Из матрицы `M = [[a, −b, tx], [b, a, ty]]`:

```
s = √(a² + b²)          θ = atan2(b, a)
```

**Приор работает как ограничение, а не подсказка:**

- **масштаб**: ожидаемое `s* = GSD / mpp`; решение вне `Prior.scale_bounds`
  (допуск от погрешности высоты, типично ±30%) отбрасывается целиком;
- **позиция**: центр решения вне диска ±3σ приора → решение отбрасывается;
- **курс** (если известен): используется для предповорота, остаточный θ мал.

Ни в одном месте решение не «подтягивается» к приору — оно либо проходит гейт,
либо гибнет. Это и есть механизм, дающий строку «0 ложных» в таблице результатов.

## 8. Refinement: субпиксель и цикл масштаба

**ECC-уточнение** (`cv2.findTransformECC`, максимизация enhanced correlation
coefficient) фотометрически дотягивает робастную позу в области инлайеров.
Это главный рычаг точности: медиана ошибки центра на стенде **0.505 px → 0.011 px**;
после ECC точность перестаёт зависеть от матчера (SIFT ≡ AKAZE = 0.011 px).

**Цикл переуточнения масштаба** закрывает погрешность высоты:

```
если |s − s*| велико:                 # масштабы разошлись → высота была неточна
    H_est = s · H_prior               # уточнить высоту (GSD ∝ H)
    z_fine ← зум под новый GSD        # перетянуть окно подложки
    заново match + pose               # инлайеров и точности больше
повторять 1–2 итерации (потолок зума ограничен реальным покрытием подложки)
```

Восстановленный масштаб напрямую даёт **оценку высоты съёмки** `H_est = s · H_prior`
— измерено на стенде: при ошибке высоты ×2 цикл возвращает и точность
(4.48 см → 0.30 см), и саму высоту.

## 9. Считывание результата через Georef

Из финального преобразования `M` и привязки окна `Georef` (единственного моста
«пиксель ↔ координата», соглашение «центр пикселя»):

- **Центр**: центральный пиксель кадра `((W−1)/2, (H−1)/2)` → через `M` → пиксель
  подложки → `georef.pixel_to_lonlat` → lat/lon.
- **Отпечаток**: четыре угла кадра тем же путём → полигон; пишется в
  `footprint.kml` (Google Earth) и `footprint.geojson` (QGIS).
- **Курс**: из θ — поворот кадра относительно севера (с учётом предповорота).
- **Высота**: `H_est = s · H_prior` из цикла масштаба.

Абсолютную точность дополнительно ограничивает геопривязка самой подложки —
единицы метров; это записано в отчёте рядом с эллипсом.

## 10. Оценка точности и связка качества

Результат — распределение, а не точка (`aero_geoloc/quality.py`).

**Ковариация центра.** Из остаточных невязок инлайеров и их пространственного
разброса пропагируется ковариация 2×2 (в метрах) → **эллипс ошибки** (большая и
малая полуоси 1σ, угол). Калибровка Монте-Карло на стенде: покрытие 1σ/2σ =
0.384/0.857 против номинала 0.393/0.865 — эллипс честный для случайной части
ошибки. Эллипс показывается **только у принятой позы**: у отвергнутой он
описывает разброс подгонки, а не верность места.

**Связка качества** — конъюнкция независимых сигналов; статус `LOCALIZED` требует
всех сразу:

| сигнал | порог | что ловит |
|---|---|---|
| эллипс, большая полуось | ≤ 3 м | геометрическая расшатанность решения |
| инлайеры RANSAC | ≥ 8 (разреженные ядра) / ≥ 185 (плотные) | случайные структуры; у плотного ядра 2048 сэмплов, и 8 инлайеров ничего не значат |
| фотометрический сигнал | **dino-косинус ≥ 0.35** | «то ли это место по виду» |
| гейт приора | центр в ±3σ, масштаб в допуске | уверенно-неверные точки вне области знания |

Фотометрический сигнал — косинус **плотных DINOv2-фич** выровненного кадра и
подложки. Он заменил NCC по измерению (веха E3 в [JOURNAL.md](JOURNAL.md)): шкала
NCC «едет» между кадрами сильнее, чем между сезонами, а dino-косинус ровнее и
перестал резать верные локализации. Одного его недостаточно — трижды за
испытания dino проходил порог на заведомо неверном месте («любая деревня похожа
на деревню»), и спасала геометрия. Отсюда принцип: **связку нельзя ослаблять до
одного сигнала**.

**Статусы:**

- `LOCALIZED` — все сигналы прошли; сверьте панели отчёта глазами.
- `LOW_CONFIDENCE` — поза найдена, но связка её не пропустила.
- `NOT_LOCALIZED` — честный отказ с причиной (нет кандидатов, самоподобие,
  вне диска приора, нет съёмки у подложки, поза не собралась).

**Сторож регрессии** (`aero_geoloc/regression.py`, `scripts/regress.py`):
поведение на 30 кейсах заморожено в `datasets/golden.yaml` вместе с конфигурацией;
сравнение идёт по **классу исхода** (не по плавающим числам), ложное срабатывание
рушит сборку безусловно, а расхождение конфигурации отменяет вердикт. Изменение
нельзя протащить молча.

## 12. Границы применимости

Записанные и **измеренные** границы; это самая важная часть документа для
пользователя.

1. **«0 ложных» верно только внутри регламента «высота → σ».** Контрольная пара
   на `DRZ_06262` (90 м AGL, отпечаток 124 м), центр приора один и тот же в 247 м
   от истины, менялась только σ: σ = 0.5 км → **1.2 м, верно**; σ = 1.5 км
   (втрое шире регламента) → **принято, 1883 м — ложное**. За конвертом система
   выдаёт уверенно-неверные точки, а не отказы. σ — это **обещание** «центр верен
   с такой точностью», а не ручка настройки: сужать её под неверным центром —
   значит вынести верное место за пределы карты.
2. **Кросс-сезон решён наполовину**: один кадр из двух; кросс-сезонных сцен в
   наборе мало для выводов. Направление «ядро посильнее» исчерпано; дальше —
   дообучение под домен либо сезонная подложка.
3. **Покрытие подложки не везде доходит до нужной детальности**: вне городов Esri
   обрывается на z18 (≈0.3 м/пкс) и грубее; кадр с GSD 3 см теряет детальность в
   ~10 раз. Не лечится алгоритмом — только другой подложкой.
4. **Съёмка не в надир** (>10° от вертикали) — вне модели; такие кадры
   отсеиваются на входе.
5. **Самоподобная местность** (поля, лес, вода) — честный отказ по сигналу
   уникальности; информации в кадре объективно мало.
6. **Порог плотного ядра (185 инлайеров)** стоит двух верных поз на наборе
   (155 и 163 инлайера) — цена нуля ложных; калибровка на большем объёме данных —
   первая задача очереди.

## 13. Инструмент владельца

```bash
python scripts/locate.py --image кадр.JPG --lat 51.21 --lon 6.16 --sigma-km 0.5 --gsd 0.03 --yaw -26
```

Выход: `out/<имя>/report.html` (самодостаточный: вердикт, четыре панели
проверки глазами, советы при отказе), `result.json`, `footprint.kml`,
`footprint.geojson`. Пакетный режим по папке даёт `summary.html`.

пересчётом «градусы-минуты-секунды»), высота, курс, GSD и **готовая команда** на
каждый снимок; приор в командах намеренно сдвинут от истины на полсигмы, чтобы
запуск оставался проверкой, а не подсказкой самому себе
(`datasets/test_images_exif.txt`, `datasets/DRZ_geolocation.txt`).
